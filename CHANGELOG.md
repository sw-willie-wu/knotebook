# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Knotebook follows Keep a Changelog conventions: unreleased work accumulates under [Unreleased] and moves into a dated version section once it ships. The first release is v0.1.0.

Releases before 0.16 are in [`docs/changelog/`](docs/changelog/), one file per minor series: [0.15](docs/changelog/0.15.md), [0.14](docs/changelog/0.14.md), [0.13](docs/changelog/0.13.md), [0.12](docs/changelog/0.12.md), [0.11](docs/changelog/0.11.md), [0.10](docs/changelog/0.10.md), [0.9](docs/changelog/0.9.md), [0.8](docs/changelog/0.8.md), [0.7](docs/changelog/0.7.md), [0.6](docs/changelog/0.6.md), [0.5](docs/changelog/0.5.md), [0.4](docs/changelog/0.4.md), [0.3](docs/changelog/0.3.md), [0.2](docs/changelog/0.2.md), [0.1](docs/changelog/0.1.md).

## [Unreleased]

### Added

- **The server accepts audio, video, documents and text files as attachments** (#249). `POST /api/notes/:id/uploads`, and the MCP upload token, take images (PNG, JPEG, GIF, WebP and SVG), audio (MP3, M4A, Ogg/Opus, WAV, FLAC), video (MP4, WebM, Ogg, MOV), PDFs, Word, Excel and PowerPoint files, OpenDocument files and text files, judged by their content, and answer `{id, url, mime, kind}`. Audio and video have their own size limit in **Site admin → Site limits** (100 MiB by default, up to 1 TiB); downloads support `Range` and `HEAD`.

- **Audio, video, documents and text files can be added to notes in the browser** (#249). Drop or paste an audio, video, PDF, Office, OpenDocument or text file into a note and it becomes the matching block (a file block for documents, whose name opens the file); every file block's panel has an **Upload** tab. The block shows progress, the reason a file was refused or failed, and **Retry** where it can help; size, room and type are checked before anything is sent. Uploads carry on in the background while you open other notes, a pill next to the bell lists them (progress, the note each goes into, failures and **Retry**), and leaving the page during an upload asks first. When a file finishes while its note isn't open in front of you, the bell gets an **Upload finished** notification naming the file and the note; it opens the note at the file. It is yours only, never an agent's (MCP's `list_notifications` doesn't list it), and is kept and deleted like the other notifications; the web app reports the finished upload with the new `POST /api/uploads/:id/finished`. Public pages and presentations play audio and video and link files. See [Known limitations](docs/known-limitations/uploads.md).

- **Agents read and write audio, video and file blocks as HTML** (#249). `read_note_section`, the REST content endpoint and bulk-transfer downloads give an audio block as `<audio src="/api/uploads/<id>" data-name="NAME"></audio>`, a video block as `<video … width="W"></video>` and a file block as `<embed src="/api/uploads/<id>" data-name="NAME">`, inside a `<figure>` with a `<figcaption>` when it has a caption; writing the same HTML back gives the same block, and `create_transfer_token`'s upload reply tells agents which form to insert for each kind. A plain link to an upload stays a link. See [AI editing](docs/ai-editing.md#audio-video-and-files) and [MCP](docs/mcp.md#create_transfer_token).

- **Notes in the trash can be previewed read-only without restoring them first** (#327). Clicking a note in the sidebar's **Trash** tab (outside select mode) opens `/trash/:id` with a read-only preview of its content and own uploaded images, its deletion and retention info, and **Restore** and **Delete permanently** buttons — without connecting to live collaboration. Directly visiting a trashed note's URL as someone with trash access shows the same read-only preview alongside **Go to trash**, while users without trash access still see the existing not-found behaviour with no content leak. Select mode in the Trash tab continues to toggle check boxes. On the server, session-only `GET /api/trash/:id` and `GET /api/trash/:id/uploads/:uploadId` serve the preview and the trashed note's own uploads only to users with trash permission (the owner of a personal note, or a group member whose role can both edit and delete); `GET /api/uploads/:id`, search, lists, public links, backlinks, collaboration and MCP continue to hide trashed notes. See [Sharing → Notes in the trash](docs/sharing.md#notes-in-the-trash), [API contract summary](docs/api.md) and [Known limitations → Trash](docs/known-limitations/trash.md).

- **Search with several keywords** (#399). Separate keywords with spaces, or put a phrase in double quotes; up to 8. By default a note must contain every keyword, each in its title or body, and the sidebar works this way. `GET /api/search` and MCP's `search_notes` also take `keywords=any` to match notes with any of the keywords, those with more of them first. Results rank by how many keywords match, then title matches before body matches as before; each note's sections are picked by how many different keywords they contain, and the sidebar highlights every keyword. Replies for a query with several keywords carry `matchedTerms` on each note and each match. A one-keyword search behaves exactly as before. CJK keywords need spaces between them too, since there is no word segmentation. See [MCP → Keywords](docs/mcp.md#keywords) and [API contract summary](docs/api.md).

- **Moving a note into a group can bring its version history along.** The move dialogs for a single note and for several selected notes have a **Bring its version history and comments along** box (**Bring their version history and comments along** for several notes), unchecked by default. When you check it, the note's versions, their names and their numbering stay, and the group's editors see them and who edited them; its comments stay too. When you leave it unchecked, the history and the comments are cleared. Over the API, `POST /api/notes/:id/move` takes `keepHistory`, and the MCP `move_note_to_group` tool takes `keep_history`; leaving them out clears the history and the comments. See [Version history](docs/versions.md#moving-copying-and-transferring) and [Known limitations](docs/known-limitations/version-history.md).

- **Site admins choose which knowledge info fields headings carry** (#565). The new **Site admin → Knowledge fields** page turns each built-in field (**When to read**, **Conclusion**, **Basis**, **Last verified**, **Replaced by**) on or off, and edits the options of **Basis**: rename them, hide them, change their order or add new ones, up to 30 (a new option's key is made from its name, can be edited until you save, and can't be changed after that). The settings apply to every space, your own notes and every group. A field that is off isn't shown in the form, on the card or in the index, and isn't in the Markdown that agents, downloaded files and the editor's AI actions read; its values stay in the notes, and turning it back on shows them again. A hidden option stays on the knowledge that has it, shown as its name followed by **(turned off)**, and is no longer offered. Over the API there are `GET /api/knowledge/fields` and `GET`/`PUT /api/admin/knowledge-fields`, and the knowledge index answers with the space's `fields`; `read_note_outline` (on its first page) and `create_note` return `knowledgeFields`, the fields an agent can write, and a bulk download's manifest has `knowledgeFieldSets`. See [Knowledge info](docs/knowledge.md#choosing-the-fields), [Self-hosting](docs/self-hosting.md#knowledge-fields) and [Known limitations](docs/known-limitations/knowledge.md).

- **Site admins can add custom knowledge fields** (#565). **Add custom field** in **Site admin → Knowledge fields** adds a field with a name and one of five types: **Text** (one line, up to 300 characters), **Single choice** (with options set up like those of **Basis**), **Date**, **Link** (an `http://` or `https://` address or a path on this site) and **Person** (yourself, or someone the web app suggests when sharing: the members of your groups and the people you shared one of your notes with). Custom fields come after the built-in ones in the form and on the card, in the order the admin sets; up to 20 can be on and 100 can exist. A field's key is made from its name and can be edited until you save; after that its key and type can't be changed, and a field can't be deleted, only turned off, which keeps its values in the notes. The card shows a person by name, and a link opens only when it is such an address. The index doesn't show custom fields. Agents read and write them as `x-<key>: <value>` lines in the knowledge comment, a person by handle, and `knowledgeFields` lists them; a value that doesn't fit is left out and listed as for the built-in fields, with `bad_link` for a link and `unresolved_member` for a person the writer can't name. Over the API, `PUT /api/admin/knowledge-fields` takes custom fields, and `POST /api/knowledge/members` names the people in them. See [Knowledge info](docs/knowledge.md#custom-fields), [AI editing](docs/ai-editing.md#knowledge-info) and [Known limitations](docs/known-limitations/knowledge.md).

- **A knowledge comment line that can't be written is left out and listed, and the rest of the write goes through** (#565). A key the site doesn't have, a field it turned off, a value that isn't one of the field's options, a status it doesn't know, a date that doesn't exist, a `superseded_by` that isn't a knowledge reference or names the knowledge itself, and a value that is too long or has a line break are each left out with a reason; that field keeps the value it had (none for new knowledge), and the reply lists the line under `knowledge.ignored` as `{heading, key, value, reason}`. This applies to `edit_note`, `create_note`, `POST /api/notes/:id/edits` and a file sent back; `POST /api/notes` with `content` adds `knowledgeIgnored` to the note it returns. A malformed comment (see [AI editing](docs/ai-editing.md#knowledge-info) for what counts) or an `id` that isn't valid still refuses the write with `400 invalid_knowledge`. The editor's AI actions list such lines in their preview and don't apply that result by themselves. See [AI editing](docs/ai-editing.md#knowledge-info) and [MCP](docs/mcp.md#knowledge-info).

- **Code blocks in presentation mode are now syntax-highlighted** (#232). Presentations use the same language list and light/dark syntax colors as the editor, switching automatically with the theme without re-highlighting. The highlighter loads on demand only when a presentation contains a supported non-plain-text code block, and tokenized blocks are cached so live edits elsewhere on the slide redraw without flashing; plain text blocks and unsupported languages stay uncolored.

- **Storage pages show how much space notes and version history take** (#480). **Settings → Storage** and a group's **Storage** page list **Notes** as a row in **By type**, with the size of the space's note content, and the **Version history** group shows the current size of saved versions and automatic backups. **Site admin → Users** and **Groups** show the total under each space's usage. The numbers are shown only: they don't count toward the storage limit and nothing is blocked. Notes in the trash are included until they are permanently deleted, and AI edit records are left out. In the API, `GET /api/storage` and `GET /api/groups/:id/storage` return `content: {noteBytes, historyBytes}`, and the admin users and groups lists return `contentBytes` in each `storage`.

- **Notes have comments with @mentions, over the API and MCP** (#289). Anyone who can see a note can comment on it, about the whole note or about a passage, and answer another comment. `@handle` notifies a person who can see the note and `@handle/label` one of their agents, and the author of the comment being answered is notified too. Notifications are kept for 30 days unless a site admin sets another number of days or keeps them for good. AI agents read and post comments and list what was addressed to them with three new MCP tools, `read_comments`, `post_comment` and `list_notifications`. See [Comments](docs/comments.md).

- **A notification bell shows mentions and replies as they happen** (#289). The bell in the sidebar's bottom row (on a phone, in the top bar) has a badge with the number of notifications you haven't seen; it opens them newest first, marks them seen, and each one opens the note at its comment. A notification can be deleted, or all of them cleared (which also clears those addressed to your agents). New ones arrive without reloading over a WebSocket at `/collab/notifications`, which the existing proxy rule for `/collab` already forwards; its `Origin` check needs `PUBLIC_URL` to be the address people open. A site admin sets how long notifications are kept in **Site admin → Storage plans**. See [Comments](docs/comments.md).
- **Notes have a comments panel in the web app** (#289). The **Comments** bubble in a note's corner shows how many comments others posted since you last looked and opens the thread beside the note; it sits above the version history bubble, both stay while either panel is open so one press switches between them, and a button below them hides or shows them (on a phone, **Comments** in the note's ⋮ menu opens the thread as a full page, with a switch to the version history at the top). A comment you haven't sent is kept when you switch or close the thread; new comments appear without reloading, and typing `@` suggests people who can see the note. Select text and press **Comment** in the toolbar above it to comment on that passage, as an editor or as a reader; the comment quotes it, and pressing the quote takes you back to it. Passage comments can't be started on a phone. See [Comments](docs/comments.md#in-the-web-app).
- **LaTeX code blocks are highlighted** (#338). **LaTeX** is now in a code block's language list; math such as inside `$…$`, `$$…$$`, `\[…\]` and `\begin{equation}…\end{equation}` has its own color in light and dark, in the editor and in presentations. A LaTeX code block is highlighted, not rendered.

- **Notes can now upload SVG images** (#389). Image blocks accept `.svg` files through the Upload tab, paste, drag-and-drop and `POST /api/notes/:id/uploads` (validated as well-formed XML with an `<svg>` root element declaring `xmlns="http://www.w3.org/2000/svg"`, and every namespace prefix used on an element or its ancestors declared, such as `xmlns:xlink` for `xlink:href`; a refused SVG shows what to check). SVG uploads work alongside PNG, JPEG, GIF and WebP; a file counts as SVG only under a `.svg` name, and SVG markup under a text extension (`.txt`, `.xml` and the like) is stored as plain text, while under any other name it is refused with `415`. Uploaded SVGs are displayed via `<img>` in the editor, on public pages and in presentations — scripts and external fetches inside the SVG do not run, while embedded `<style>` CSS animations keep running — and upload responses (`GET /api/uploads/:id`, `GET /api/public/notes/:token/uploads/:uploadId` and `GET /api/public/notes/:handle/:slug/uploads/:uploadId`) now send `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; sandbox` alongside `X-Content-Type-Options: nosniff` so opening an upload URL directly cannot execute script in the site's origin. Over MCP, `read_note_image` now accepts `image/svg+xml` and returns SVGs up to 102 400 bytes (100 KiB) as UTF-8 XML text (instead of an image block; larger SVGs answer `file_too_large` and can be downloaded with `create_transfer_token`), and `create_transfer_token`'s upload instructions list SVG among the accepted formats. Profile pictures and sign-in service icons still accept only PNG, JPEG and WebP. See [API contract summary](docs/api.md), [MCP](docs/mcp.md#read_note_image) and [Known limitations](docs/known-limitations/uploads.md).

### Changed

- **Knowledge has a status of its own: Verified, Needs review or Outdated** (#565). The form shows it first, for every piece of knowledge, and new knowledge starts as **Needs review**. Picking **Verified** fills in today's date as the last verified date while that field is on (you can change it); **Mark verified today** became **Today** next to the date, which fills in the date only; **Mark as verified** in the phone sheet sets the status to **Verified** and, while the field is on, the date to today. The gray *i* for knowledge with no last verified date is gone: there are three icons, a green check for verified, an amber ! for needs review and a red slash for outdated, and the counts on a card and in the index, and the index's **Status** filter, have the same three. Knowledge saved before the upgrade without a stored status reads as verified when it has a last verified date and as needs review when it doesn't; nothing in the notes is rewritten. See [Knowledge info](docs/knowledge.md#the-fields).

- **Knowledge needs nothing but a status, and outdated knowledge doesn't need a replacement** (#565). A piece of knowledge can be saved with every field empty, and **Replaced by** is optional. Emptying every field of existing knowledge and saving it as **Needs review** still asks you to fill in a field, so a slip doesn't leave an empty entry behind; **Remove knowledge info** takes the info off.

- **Basis no longer has an Unconfirmed option** (#565). It was stored the same as no basis. The card now says **Not filled** for an empty basis and an empty last verified date, where it said **Unconfirmed** and **Not verified**. Agents can still write `evidence: unconfirmed`, which means none.

- **Every knowledge comment in the Markdown agents read has a `status` line, with the new names** (#565). `status` is `verified`, `needs-verify` or `obsolete`; the older `unverified` and `outdated` are still read, and a comment without `status` reads from the last verified date as above. Only the fields the space has turned on are written.

- **Two-finger zoom now works on slides in presentation mode on touch screens** (#235). Slides that fit on screen, short code blocks and vertical sub-slides used to turn pinch-zoom off along with the browser's own panning, so that a swipe would change slides. They now allow pinch-zoom while still leaving one-finger swipes to the presentation; slides that scroll keep scrolling as before.

### Fixed

- **Code block fence languages match without regard to case (```` ```Python ````, ```` ```TS ````, ```` ```Mermaid ````), and are stored under their lowercase id** (#590). Existing notes with mixed-case or alias language names also highlight and match the language menu.

- **Typing ```` ```mermaid ```` and pressing Enter or Space now makes a diagram block** and opens its source for editing. It used to make a code block with the language `mermaid`; pasting already made a diagram.

### Upgrade notes

- **Audio, video and file blocks read differently.** For a note that contains an audio, video or file block, the Markdown that reading gives changes — an audio or video block no longer reads as a link or a bare `<audio>` / `<video>`, and a file block no longer reads as a link — and a bulk-transfer download's text for such a note differs from an earlier download. Fingerprints are computed from the blocks, not the text, so they don't change: text read before the upgrade and written back with its fingerprint is accepted, and turns those blocks into links as before. Have agents read the note again before editing a note with audio, video or file blocks. Notes without audio, video or file blocks read exactly as before.

- **A search with spaces in it now means several keywords.** `deploy prod` used to look for that exact text and now finds notes containing both words; put it in double quotes (`"deploy prod"`) to search for the exact text as before. This applies to the sidebar, `GET /api/search` and `search_notes`.

- **Knowledge with no last verified date now shows the amber needs-review icon instead of the gray *i*.** Nothing in the note changed: knowledge that was current but never dated now reads as needing review, because nothing says it was checked. Mark it as verified to clear it.

- **The form's Current status is now called Verified, and the card says Not filled where it said Unconfirmed or Not verified.** The **Unconfirmed** basis option is gone; knowledge that had it has no basis, which is how it was stored all along.

- **Outdated knowledge no longer needs a replacement, and knowledge no longer needs any field filled in.**

- **The counts of the knowledge under a heading, on the card and in the index, and the index's Status filter have three kinds instead of four.** Over the API, `icon` is never `noVerifiedDate` any more, `summary` is `{total, verified, needsReview, outdated}`, index entries carry `state`, and the index's `status` parameter takes `verified`, `needsReview` or `outdated` (`noVerifiedDate` is read as `needsReview`, so older links still work); an entry's `evidence` can be any option key.

- **The knowledge card and form show only the fields the site has turned on.** All five are on after the upgrade, so nothing changes until an admin turns one off.

- **Knowledge comments now always have a `status` line, written with the new names** (`verified`, `needs-verify`, `obsolete`), and once an admin adds custom fields, `x-<key>:` lines after the built-in ones. A script that parses them has to accept both; the older `unverified` and `outdated` are still read when written.

- **REST and MCP writes no longer refuse a knowledge value that doesn't fit.** They no longer return `bad_evidence`, `bad_status`, `empty`, `superseded_required`, `too_long`, `line_break`, `bad_date`, `bad_ref` or `superseded_self`: the write goes through without that line, and the reply lists it under `knowledge.ignored` (`knowledgeIgnored` for `POST /api/notes`). A comment line whose key version 0.18 didn't accept, such as one with a hyphen or a capital letter, no longer refuses the whole comment either: it is listed as `unknown_field`, and so is any other key the site doesn't have, which version 0.18 dropped without a word. A client that counted on the error to stop a bad write should check `knowledge.ignored` instead.

- **Migration 0047 only widens two checks on the knowledge index** (`nk_status_chk` also accepts `verified`, `nk_evidence_chk` accepts any option key) and changes no row. **Migration 0048 only adds two tables**, `knowledge_field_defs` and `knowledge_field_overrides`, for the knowledge field settings; with no rows the settings are the defaults, so the upgrade writes no data. The knowledge index is built again in the background after the first start. See [Self-hosting](docs/self-hosting.md#upgrading-and-rolling-back).

- **Migration 0049 only adds one nullable column**, `note_knowledge.custom`, which holds the custom field values in the knowledge index, and changes no row. Rolling back leaves it in place and the previous version doesn't read it. See [Self-hosting](docs/self-hosting.md#upgrading-and-rolling-back).

- **Rolling back to 0.18: if anyone has saved knowledge info since the upgrade, or changed the knowledge field settings, restore the database backup taken before the upgrade.** Saving includes the form, **Mark as verified**, MCP, the API, a file sent back and the editor's AI actions. Don't just switch back to the 0.18 image: it starts, because the migrations only widen and add, but then
  - knowledge marked **Verified** reads as current (a green check with a last verified date, a gray *i* without one), and a basis option an admin added reads as **Unconfirmed**;
  - MCP `replace_section` and `replace_all`, and the editor's AI rewrites, are refused with `bad_status` or `bad_evidence` over any part that holds knowledge marked verified or with an added basis option, even when they don't touch that knowledge;
  - outdated knowledge without a replacement, and knowledge with only a status, fall under 0.18's `superseded_required` and `empty` rules: changing them through MCP is refused and saving them in the form is blocked;
  - the knowledge field settings aren't read, so every built-in field and the default basis options are back, and custom fields aren't shown;
  - custom field values aren't shown, and a heading changed there, by a person or an agent, can lose them, because 0.18 has no place for them; headings left alone keep them;
  - the knowledge index is built again by 0.18's own background run.

- **Notes you have open in a tab ask to be reloaded after the upgrade** (**Reload required** in the note's header), because headings gained a property for custom field values. Changes in that tab that hadn't synced are lost; reload the tab.

- **Restart your MCP clients.** The descriptions and output schemas of the MCP tools changed: `read_note_outline` and `create_note` return `knowledgeFields`, custom fields included, the `knowledge` part of a reply can carry `ignored`, the tools describe only `id` and `status` themselves and point to `knowledgeFields` for the rest; `search_notes` has a new `keywords` input, new optional `matchedTerms` fields and an updated description; `read_note_image`'s output schema (`mimeType` now includes `image/svg+xml`) and description changed, and `create_transfer_token`'s `next` instructions list SVG. A client that cached the tool list keeps the old descriptions until it is restarted.

## [0.18.0] - 2026-11-22

### Added

- **Tags for notes** (#105). A note can carry any number of tags, shown in a row above its text. Type `/tag` in a note or choose **Add tag** in its `⋮` menu to add the first one; once there are tags, the **+** at the end of the row adds more, and the × on a tag takes it off. A tag belongs to the space the note is in (your own notes, or one group), names are not case-sensitive, and each tag has one of nine preset colors, the same as the editor's text colors, or a custom color picked with **Custom…** (it looks the same in the light and dark themes). A note's row in the sidebar shows up to three colored dots, and a funnel button in **My notes** and **Groups** lists only the notes that have all the tags you tick (in **Groups**, one group at a time). **Settings → Tags**, and **Tags** in a group's window for roles that can manage the group, rename, recolor, merge and delete tags. Moving or copying a note to another space, and deleting a group and giving its notes to an admin, carry the tags over by name. Tags don't change a note's last modified time, are not part of its text or version history, and are not shown on public pages. Someone who has a note through an editor share sees its tags but can't change them. Over the API, `GET /api/notes` gives each note its `tags`, and there are new tag endpoints (session only); agents see and set tags through markdown, as described below. See [Sharing](docs/sharing.md#tags) and [Known limitations](docs/known-limitations.md).

- **Tags can be added and searched without leaving the keyboard** (#105). Type `#name` and a space in the first line of a note, when that line is an ordinary paragraph, to add the tag (a notice offers **Undo**; Ctrl+Z only puts the text back), or paste a line such as `#alpha #beta` followed by a blank line into the empty first block of a note. In the sidebar's search box, `#` and part of a name lists the tags of each space; choosing one makes a token in front of the box, and only notes that have every token are listed, narrowed further by any keyword you type after them. What you type is still searched as text, so `#105` finds the notes that contain it. For someone who can change the note's tags, clicking a tag in its row opens a menu with **Remove from this note** and, for those who can manage the space's tags, rename and color. `GET /api/search` takes a `tags` parameter (a comma-separated list of tag ids of one space; any list that doesn't qualify gets `400 invalid_tags`), and `POST /api/notes/:id/tags` returns the `tag` it attached and `attached`. See [Sharing](docs/sharing.md#tags) and [Known limitations](docs/known-limitations.md).

- **Headings can carry knowledge info: when to read it, a one-line conclusion, its basis, when it was last verified, and whether it is current, needs review or has been replaced.** A top-level heading that carries knowledge info gets one small status icon after its text: a green check when it is verified, a gray *i* when it has no verified date, an amber ! when it needs review, and a red slash when it is outdated, which includes any knowledge heading under an outdated one. An outdated heading and the knowledge under it are dimmed and struck through. The icon is faded until you point at it; pointing at it, or tapping it on a phone, shows a card with the fields, and on a phone a bottom sheet with **Mark as verified** and **Edit**. Someone who can edit the note adds the info by typing `/info` in a heading or from the drag handle menu (**Knowledge info…**), and edits it later by clicking the icon; someone who can only read it sees the icons and cards but can't change them. An outdated heading names the knowledge heading that replaced it, in the same note or in another one you can see. A version preview shows the icons its version had. Public pages and presentations don't show knowledge info, and the server takes it off before it sends a public note. See [Knowledge info](docs/knowledge.md) and [Known limitations](docs/known-limitations.md).

- **Each folder, group and your own notes have an index of their knowledge: when to read each piece, its conclusion, and a link to that heading.** An index button shows when you point at a folder or group row or the **My notes** title (always on a touch screen), and the `⋮` menu of a folder or group has **Open index**; they appear only where there is knowledge. The page lists the knowledge in the notes you can see, with a folder's subfolders included and the trash left out, grouped by folder or by tag; **Tags**, **Status** and **Basis** filters narrow it and are kept in the address. Only members of a space can open its index, and notes shared with you are in no index. In the form, **Replaced by** can name knowledge in another note: type to search your other notes, and the card and the index show that heading's name and link to it, or **knowledge in another note** when you can't see it. That search shares the text search's per-minute budget. Over the API there are `GET /api/knowledge/index/me`, `/groups/:id` and `/folders/:id`, `GET /api/knowledge/refs` and `GET /api/knowledge/refs/:id/:knowledgeId`; `GET /api/notes` also gives each note `hasKnowledge`. See [Knowledge info](docs/knowledge.md#the-index) and [Known limitations](docs/known-limitations.md).

- **Agents read and write tags and knowledge info through markdown.** A heading that carries knowledge info is followed by a `<!-- knotebook:knowledge … -->` comment in what `read_note_section`, `GET /api/notes/:id/content`, a downloaded file and the editor's AI actions read. `edit_note`, `create_note`, `POST /api/notes`, `POST /api/notes/:id/edits` and a file sent back read the same comment: write it back as it is to keep the info, change a line to change it, or add one under a heading to make it knowledge. With `replace_section` and `replace_all`, a heading sent without a comment keeps the info of the heading with the same level and text it replaces; a file is the whole content, so a heading whose comment is taken out loses its info. A comment that isn't valid answers `400 invalid_knowledge` and writes nothing, and the reply of `edit_note`, `create_note`, `POST /api/notes/:id/edits` and a file sent back lists what was kept, created, removed and renewed under `knowledge` (the reply of `POST /api/notes` is the note itself and has no `knowledge`). A downloaded file also has a `tags:` line, and sending it back with a different line sets the note's tags (a new name is created in the space; it needs edit rights in the note's own space, so a person who has only a share gets `403`); the reply carries `tagsChanged`, `tagsFailed` and, for a file that changed only the tags, `result: "tagged"`. `read_note_outline` returns the note's `tags`. See [AI editing](docs/ai-editing.md#knowledge-info), [MCP](docs/mcp.md#sending-a-file-back) and [Known limitations](docs/known-limitations.md).

### Changed

- **Searching for three or more letters or digits in a row is much faster on a site with many notes.** Search used to read the text of every note you can see; now a search such as `kubernetes` or `資料庫` looks the words up in an index first, so a rare word, or one that isn't anywhere, comes back quickly however many notes there are (measured with a million sections of note text: from about 2.7 seconds to about 0.15). Results are the same as before. Searches for one or two characters, such as most two-character Chinese words, work as before. ### Fixed

- **Links to a paragraph or heading keep working after an agent rewrites the part of the note around it** (#551). When `edit_note` with `replace_section` or `replace_all`, `POST /api/notes/:id/edits`, or a file sent back over bulk transfer replaced a stretch of blocks, every block in it got a new id, so `#b-<id>` links and a heading's "#" link to any of them stopped working even when that block hadn't changed. Now a block whose type and text are unchanged keeps its id, and so does a single block of the same type whose text was edited between two such blocks (or between one and the start or end of the stretch); blocks nested in an unchanged block keep theirs too. A block that is split, merged, changed to another type or moved in a larger reorder, or two edited blocks next to each other, still get new ids, and so does applying a version or the in-app AI replacing a selection. Two side effects: an earlier AI edit whose blocks a later rewrite left as they were stays revertable (and an edit whose removed blocks are back at the top level is no longer offered for revert), and an `edit_note` that rewrote a section with the same content no longer makes a file downloaded before it fail with `note_changed`. See [AI editing](docs/ai-editing.md#which-blocks-keep-their-ids).

- **Replacing or deleting thousands of blocks in one write no longer takes quadratic time** (#553). Working out a rewrite used to remove the old blocks one at a time, so the cost grew with the number of blocks removed times the number of blocks in the note. Now the old blocks are removed in one step once the edit session closes, so working out the change grows with the blocks written and removed. This covers `edit_note` and `POST /api/notes/:id/edits` with `replace_all`, `replace_section` or `delete_section`, a file sent back over bulk transfer, reverting an AI edit, applying a version, and creating a note with content. On one Windows development machine, replacing all of a 2,500-block note through a parse worker at the default limits took 1.7 seconds and a 5,000-block note failed with `too_complex` (the worker ran out of memory); with this fix, in a worker with 1 GiB of memory, 5,000 blocks took 1.1 seconds, 10,000 took 3.8 and 15,000 took 7.3. The resulting documents, block ids and history are the same as before, with one difference in reverts: when you had added a paragraph between the blocks an AI edit wrote, reverting that edit now leaves your paragraph where it is, where it used to end up above the restored blocks. Inserting a very large number of blocks in one write, merging a large deletion into the open note, and applying a version of a large note still take longer than their size suggests; see [Limits](docs/known-limitations/limits.md).

- **Site admins can adjust 17 limits in the browser, without restarting the server** (#397). **Site admin → Site limits** has the upload size limit, the note size limit, the four parse worker settings and the nine per-person request rates (API and MCP reads and writes, note content reads and writes, searches, uploads and copies, AI actions, bulk downloads, bulk write-backs); **Site admin → Sign-in → Session and tokens** has how long a web sign-in lasts (1 hour to 30 days, 7 days by default) and the number of active API tokens one person can hold. A limit can be lowered from its default (the number of parse workers, the memory per worker and the sign-in period can also be raised); the parse time limit goes down to 4 seconds and the memory per worker to 512 MiB, and the page says what lowering them can break. A change applies to the next request, upload or write; a new sign-in period only to people who sign in afterwards, and a lower token limit doesn't revoke any token. The page lists the 50 most recent changes with who made them, and shows a setting that an environment variable sets as locked. `GET /api/admin/limits` and `PATCH /api/admin/limits` are the API behind it, `GET /api/auth/config` now includes `maxUploadBytes`, and the editor checks files against the site's upload limit instead of a fixed 10 MiB. See [Self-hosting](docs/self-hosting.md#site-limits).
- **Drag blocks side by side.** Drag a block by its ⋮⋮ to the left or right edge of another block to make a row of two columns, or onto the edge of a block in a row of fewer than four columns to add a column next to it. When every column of the resulting row holds a single picture, the columns are sized so the pictures come out the same height. One Ctrl+Z undoes the drop. Widening an image in a column past the column's width now widens the column and squeezes the other columns, down to 200 pixels, or 96 for a column that holds only images. The ⋮⋮ inside a column is 16 pixels wide, and the keyboard shortcut list has an entry for the divider keys. A file dropped on a divider is added next to the nearest block, as anywhere else in the gap.
- **The API, MCP, bulk transfer and the in-app AI accept hex colors.** Text and background colors can be written as `#rgb` or `#rrggbb`, for example `<span style="color:#ff6600">`, besides the ten color names; they are stored and read back as lowercase `#rrggbb` (#378).

- **Table cells can be colored in the editor.** Hovering over a cell shows a small menu button whose menu has Colors, and the row and column handle menus have Colors too, which apply to the whole row or column; both offer the ten colors and Custom… (#378).
- **Install Knotebook as an app.** Knotebook can be added to a phone's or computer's home screen, or installed from Chrome or Edge, and then opens in its own window without the browser's address bar, with the italic "K" icon (including a maskable version for Android's icon shapes). In browsers that colour the window's top bar, it follows the theme you pick in Knotebook's settings. An open Knotebook, installed app or browser tab, that has been in the background notices when the site has been updated and shows **Knotebook has been updated** with a **Reload** button; it checks only when you come back to it at least 30 minutes after the last check, shows the notice once per load, and never reloads by itself. Public share pages don't prompt readers to install it. It isn't an offline app: there is no service worker, so it needs the server just like a browser tab does, and in Chromium-based browsers installing needs the site to be served over HTTPS (or from `localhost`). **Settings → About** links to the new [Installing Knotebook as an app](docs/install-app.md); see also [Known limitations](docs/known-limitations.md) (#336; contributed by renhaohsuE7 in #340).

At the end you keep the sample note or move it to the trash. It never starts by itself. The note header has the title with a line under it holding the note's location (My notes › folder, group › folder, or Shared with me · @owner; tap it to see the note in the list with its folders open), the connection dot and, when others are viewing it, a +N button listing them, with **‹** and the star, share and `⋮` buttons centred beside that block; when it was last edited is read out to screen readers. The same two round buttons float at the bottom of a note: **Search** at the left (it opens the full-screen search over the note; Cancel returns to the note) and **New note** at the right, which creates the note in the same space and folder as the one you are reading and is left out for notes shared with you and where you can't create notes; both step aside while you edit text, search or have the on-screen keyboard up. - **MCP's instructions now say when to use `open_notes_as_files`.** Where the tool is offered — to a token or app credential, on a deployment with the collaboration component — a credential with `notes:write` is told to use it, if it has a shell, to change much of a note or many notes, and a read-only one to read many or whole notes. Its `next` now says that to work on one note you can fetch it without the download, and, with `notes:write`, that a file answered with `413 content_too_large` should be changed with `edit_note` instead — a note fetched on its own carries no `tooLargeToSend` mark (#417).

When your hourly downloads are used up, the message gives the wait in minutes, says the limit is per person so a new token doesn't reset it, and says that fetching single notes with the note command doesn't count toward it; when another export is running, it gives the wait in seconds. `open_notes_as_files`'s `next` no longer tells the assistant to read `Retry-After`, which its `curl` commands don't print: it now says what to do for each `429` from its message — fetch the notes it needs with `note.curl` (with where to find their ids) or wait the minutes given, wait the seconds given when another export is running, otherwise wait a minute — and to fetch later changes with `note.curl` instead of downloading again.
- **Removing a member asks for confirmation.** The trash button in a group's member table and in a note's share panel used to remove the person at once; now it first shows a confirmation with their email. In a group, removing yourself says you will lose access and can't add yourself back, and takes you out of the group's panel the way **Leave group** does. The last Admin's button stays disabled (#395).
- **Signing out signs out only that browser, and its cookie stops working on the server.** Before, signing out only cleared the cookie in the browser, so a copy of it kept working for up to 7 days, and the only way to end a session was to change the password, which signed out every browser. Now each sign-in is a session the server keeps, and signing out (or signing in to the same account again in the same browser) deletes it: the account's other browsers stay signed in, and a note the signed-out browser still had open stops accepting its edits within seconds. Changing or adding a password still signs out every other browser, resetting it with a link signs out every other browser too, and disabling an account ends all of its sessions. Expired sessions are deleted as people sign in (#388).

- **Static files are cached differently.** The web app's build files under `/assets/`, whose names change with their content, are now sent with `Cache-Control: public, max-age=31536000, immutable`, so the browser stops re-checking each of them on every start; the page itself, the app manifest, the icons and the favicon are sent with `no-cache`, so a new version is picked up on the next load.
