# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Knotebook follows Keep a Changelog conventions: unreleased work accumulates under [Unreleased] and moves into a dated version section once it ships. The first release is v0.1.0.

## [Unreleased]

### Upgrade notes

- **Notes with side-by-side columns read differently** over MCP and the REST API: a row now reads as `<div data-kb-columns …>` and `<div data-kb-column …>` lines with Markdown inside each column. Before, a row read as its columns' blocks one after another, without the column tags (or, when a block in the row had a color, as one block of HTML). Writing back that flattened text read from an earlier version still turns the row into ordinary blocks. See [AI editing](docs/ai-editing.md#columns).
- **Notes with a resized image or with table column widths read differently** over MCP and the REST API, and the in-app AI gets them in the same form: an image with a set width now reads as `<figure><img … width="W">…</figure>`, and a table with column widths as an HTML table with `colwidth` on its first row's cells, instead of `![name](url)` and a Markdown table. Two forms that were already HTML are stricter: a colored table with column widths used to have `colwidth` on every row, and a colored image with a set width carried more attributes than the `<figure>` form allows; writing back such text read from an earlier version is refused with `unsupported_size`. See [Sizes](docs/ai-editing.md#sizes).
- **Writes are stricter about sizes and layout.** A `width` on an `<img>` or a `colwidth` not written in the form reading gives, and a `<div>` whose `style` lays it out with `display:flex` or `display:grid` (other than a row or column of side-by-side columns), now reject the whole write with `unsupported_size` or `unsupported_columns`; such a `<div>` used to be accepted and its contents flattened into ordinary blocks. HTML with an event-handler attribute, such as `onerror` or `onclick`, now rejects the whole write with `unsupported_block`; the attribute used to be dropped. This applies to MCP, the REST API and the in-app AI's results. See [AI editing](docs/ai-editing.md#columns).

### Added

- **Folders** in the sidebar's **My notes** and **Workspace** tabs: create, rename and delete folders, nest them up to five levels, sort the notes in a folder by name, last modified or size, and create notes in a folder. Group folders are shared with the group. Deleting a folder asks first, moves its notes to the trash, and **Undo** brings them back into rebuilt folders.
- MCP, the REST API and the in-app AI read and write side-by-side columns as `<div data-kb-columns …>` and `<div data-kb-column …>` lines with Markdown inside each column (see [AI editing](docs/ai-editing.md#columns)); reading used to give the columns' blocks one after another without the column tags, and writing columns was refused. On a selection that reaches across columns, or into or out of a row, the in-app AI now works on the whole row, where it used to show no **AI** button. Dragging to make columns or change their widths is still not part of this. See [Side-by-side columns](docs/columns.md).
- Add several people to a group at once: on the group's **Members** page, type or paste many email addresses into the email box (separated by commas, semicolons, spaces or line breaks — full-width `，` `；` and `、` work too; `Name <address>` copied from an email's recipients works too), or press **Import from another group…** to pick people from another group you're in. Everyone gets the role picked next to the email box. A dialog counts them as it goes, with **Stop** to end it after the one being added, and then lists who was added, who was already a member, which addresses have no account and which aren't email addresses; the addresses that weren't added are put in the email box. There is no limit on how many at a time. Importing is a one-time copy — the groups don't stay in sync. See [Notes in a group](docs/sharing.md#notes-in-a-group).
- The email field for adding someone to a group (**Members**) or sharing a note (**Members only**) now suggests people as you type two or more characters of their email or name — only people you already know: members of your groups and people you've shared your own notes with, never everyone on the site. Pick one with the mouse or with ↑/↓ and Enter; typing a full email still works for anyone else. In the group's email box, which takes several addresses, the suggestions are for the address you're typing, and picking one replaces only that address and adds a comma after it unless a comma, semicolon or line break already follows. Backed by the new session-only `GET /api/users/suggest` (at most 8 results, 60 lookups per minute per user). See [Sharing](docs/sharing.md#the-three-access-levels).

### Changed

- Items in the sidebar's **Trash** tab show the folder each note was in, after its group's name.
- The location shown under notes in **Recent** and in search results includes the folder path.
- The group menu's items have icons.
- The sidebar's **Workspace** tab lists groups by your role in them: groups where you hold the built-in **Admin** role first, then those where you hold the built-in **Member** role, then those where you have a custom role, each by name. Before, all groups were listed by name, so groups you created could end up below ones others added you to. `GET /api/groups` returns them in the same order, and so do **Settings → Groups**, the group lists in **Move to…** and **Copy to…**, and **Move to** and **Copy to** in the sidebar's selection mode.
- The main buttons and the email, password and other text fields on the sign-in, create-account, reset-password, link-account and app-authorization pages, and on the change-password page you're sent to when a password change is required, are taller (44 pixels instead of 32) and the button text is larger (16 px instead of 14 px), so they are easier to hit; this includes each **Sign in with …** button. Other pages, including the change-password form in Settings, keep the 32-pixel controls.
- The in-app AI now gets the selected blocks as the same Markdown that MCP and the API read, so colors, side-by-side columns, image widths and table column widths go to the model with them. For every AI action, built-in or custom, the server puts a fixed instruction at the start of the action's system prompt asking the model to keep that markup; admins can't change or remove it. The result is checked before it is shown, with the same column, size and color checks as a write over MCP: one that writes columns or sizes in any other form isn't applied, and the AI box shows "The AI edit failed; the note was not changed."; one with a color outside the editor's ten names isn't applied either. See [AI](docs/ai.md).

### Fixed

- Rewriting part of a note over MCP (`edit_note`), the REST API (`POST /api/notes/:id/edits`) or with the in-app AI no longer resets the widths of the images and table columns in it: they now read as HTML that carries the widths, and writing that back unchanged keeps them. See [Sizes](docs/ai-editing.md#sizes) (#305).
- Rewriting a section that holds side-by-side columns over MCP (`edit_note`) or the REST API (`POST /api/notes/:id/edits`), sending back what was read, no longer turns the row into ordinary blocks: rows now read with their column tags, and writing that back unchanged keeps the row. See [AI editing](docs/ai-editing.md#columns).
- Writing over MCP, the REST API or with the in-app AI now saves an image, or another media block, whose address is a full address of one of this site's uploads (`https://<your site>/api/uploads/<id>`) with the relative address `/api/uploads/<id>`. An image inside a toggle heading or a toggle list item, written as HTML, used to be saved with the full address, and copying the note then didn't give the copy its own copy of that image. An image already saved that way keeps its full address until it is written again.
- The in-app AI no longer turns a diagram in the blocks it rewrites into a code block: a ```` ```mermaid ```` fence in its result becomes a [diagram](docs/diagrams.md) again, as it does over MCP.
- Markdown the editor fails to parse, such as `<div data-content-type="paragraph">`, is now refused with `400 unsupported_block` over the REST API (the tool error `unsupported_block` over MCP) instead of a server error; in the in-app AI, such a result shows an error instead of leaving the AI box in its streaming state.
- On narrow windows, a message that pops up while the sidebar drawer is open (for example **Moved to the trash** with its **Undo** button, after you delete another note from the drawer) can now be reached with the keyboard and by screen readers. Before, it could be seen and clicked, and screen readers announced it, but they couldn't move to it or its buttons and the keyboard couldn't reach them.

## [0.13.0] - 2026-10-26

### Upgrade notes

- Migration 0031 sets each existing sign-in service's **Creates accounts** to the value **Allow registration** had before the upgrade, so sign-in behaves as before after the upgrade. Services added afterwards start with it off (a service imported from `OIDC_*` takes over **Allow self-registration with a password** instead).
- **Rolling back:** the old version doesn't read the new setting, and there a first sign-in through a sign-in service creates accounts according to **Allow registration** (「允許註冊」; called **Allow self-registration with a password** in this version) for every enabled service at once, which can be more permissive than after the upgrade. If **Allow self-registration with a password** is on and **Creates accounts** is off for some open identity provider, turn **Allow registration** (「允許註冊」) off on the old version first after rolling back.
- **Upgrading again after a rollback:** check **Creates accounts** on each sign-in service — especially any whose issuer was changed during the rollback, since that change didn't go through the confirmation prompt — remember that services added during the rollback start with it off, and check whether **Allow self-registration with a password** needs to be turned back on.
- Migration 0032 changes the one-time link table for invitations. **Rolling back:** the old version has no invitations, so an unused invitation can't be used while it runs, and its **Site admin → Users** creates accounts with a temporary password again; accounts already made from an invitation keep working. After upgrading again, invitations that haven't expired work again.
- Migration 0033 adds the trash: a column recording who moved a note to the trash, a site setting for how many days notes stay there (7 by default), and their constraints and index; existing notes stay as they are. **Rolling back:** the old version doesn't know about the trash, so notes in it reappear as ordinary notes (with their shares and public links working again) but keep their trash marks. Before upgrading again, either run `UPDATE notes SET deleted_at = NULL, deleted_by = NULL WHERE deleted_at IS NOT NULL` to keep them, or empty the trash before rolling back — otherwise, after upgrading again, they go back to the trash and those past the retention period are permanently deleted, with their attachments and any edits made while rolled back, starting with the first clean-up pass about five minutes after the server starts (up to 2,000 notes per pass, one pass an hour). See [Upgrading and rolling back](docs/self-hosting.md#upgrading-and-rolling-back).
- Migration 0034 adds folders: a `folders` table, a `note_placements` table for filing notes shared with you, two nullable columns on `notes` (`folder_id`, `trash_folder_path`), their indexes and constraints, and three triggers with the functions they run. Existing notes stay at the top level. **Rolling back:** the old version shows every note without folders; folders and filed notes stay in the database and come back after upgrading again. While rolled back, moving a note into a group puts it at the group's top level; deleting a group, with **Give them to an admin** or **Delete everything**, also deletes the group's folders, and with **Give them to an admin** its notes end up at the top level of that person's notes; and removing a share removes where that person had filed the note. See [Upgrading and rolling back](docs/self-hosting.md#upgrading-and-rolling-back).
- Migration 0035 widens the scope checks on `api_tokens`, `oauth_requests` and `oauth_codes` so they also allow `notes:read notes:write notes:delete` and `notes:read notes:write notes:move notes:delete`. It changes no stored value, so no existing token or app gets `notes:delete`. **Rolling back:** the wider checks stay and the old version doesn't mind them; it treats a credential with `notes:delete` as if it didn't have it (read-write, or read-write-move), and changing such a credential's access there drops `notes:delete`. An app authorization that asked for `notes:delete` and is still pending when you roll back is granted only read access if it is approved on the old version; authorize the app again.
- **Rolling back** to an earlier version deletes side-by-side columns from notes, together with what is in them, the first time such a note is opened. Back up before rolling back. Tabs left open from before the upgrade ask to be reloaded.

### Added

- Notes can be shown at three content widths — Standard, Wide and Full width. A button in the note header (hidden when the note area is narrow) picks one; the choice is saved per note in this browser rather than in your account, so it doesn't carry over to other devices or change what collaborators see in their own browsers. A shared note's public page has its own width, set in the Share dialog by whoever manages the public link, and every reader sees that width. Includes a database migration (0028) that adds the public page width to notes (#297).
- An admin can reset someone's password with a one-time link. In **Site admin → Users**, press the key button in a person's row (**Actions** column), pick 1 to 24 hours, and send them the link. It works once; creating a new one replaces it, and an unused one can be cancelled. Finishing the reset signs the person in and signs out their other browser sessions, but not their API tokens or connected apps. Links can't be created or used while password sign-in is off, and disabling an account revokes its unused link. Includes a database migration (0030) that adds the `one_time_links` table (#286).
- An admin can invite someone with a one-time link. In **Site admin → Users**, press **Create invitation**, pick 1 to 7 days, optionally add a note only admins see, and send the person the link; it is shown once and cannot be read back. The person opens it, enters their own email and a password, and gets a regular-user account and is signed in. An invitation works once, can be revoked while unused, and isn't affected by **Allow self-registration with a password**. It can't be created or used while password sign-in is off; after it is turned back on, invitations that haven't expired work again. Includes a database migration (0032) that adds invitation fields and checks to the `one_time_links` table (#285).
- Side-by-side columns: type `/grid` (or `/columns`) and pick 2, 3 or 4 columns to put blocks next to each other. Any block can go in a column. In the second or a later column, Backspace at the start of the column's first block, when it is a paragraph, moves it to the end of the column before it; Delete at the end of a column's last block brings the first block of the next column up (except when that last block has blocks nested under it or is a code block). A column this leaves empty is removed (a row of two columns turns back into ordinary blocks); Backspace at the start of an empty column removes it. When the note is too narrow, the columns stack: a column needs at least 200 pixels (96 for a column that holds only images) plus 24 between columns. **Ungroup columns** in a block's ⋮⋮ menu turns them back into ordinary blocks. Public pages, presentations and version comparisons show them too. Rows can't be nested. Not part of this yet: dragging to make columns or change their widths; writing columns over MCP, the REST API or the in-app AI, which is refused for now; and the in-app AI on a selection that reaches across columns or into or out of a row, which shows no **AI** button for now. See [Side-by-side columns](docs/columns.md).
- The note header shows who else has the note open right now — owners, editors and viewers, plus any AI agent working on it — as a row of round avatars (initials, or a sparkle for an AI agent) next to **Connected**, each ringed in the color of that person's cursor. You aren't listed, and someone with the note open in several tabs appears once. Hover or focus one for their name and role; click it to scroll to their cursor (viewers have none). When more people are on the note than fit, a **+N** button opens the full list; on a touchscreen, press and hold anyone to open it (#293).
- Folders API: `/api/folders` to list, create, rename, move and delete folders in your notes, in a group's notes or in notes shared with you, and `PUT /api/notes/:id/folder` to file a note. Creating a note, copying it and moving it into a group can name a folder. Deleting a folder in your notes or a group's moves the notes in it to the trash; deleting one in notes shared with you only takes the notes out of it.
- A **Trash** tab, the fifth in the sidebar. It lists your personal notes and, for groups where your role can both edit and delete notes, the group's notes that were moved to the trash — personal notes first (under **My notes**), each part newest first, each with how many days are left before it's permanently deleted (or, with automatic deletion off, when it was deleted), and, for a group note, who deleted it. Restore or permanently delete a note from its row, select several (Shift-click selects a range) to restore or delete them together, or **Empty** to permanently delete everything listed. Opening the address of a note in the trash shows **Restore** and **Go to trash** instead of an error, for anyone who can restore it. Site admins set how long notes stay in the trash, or turn automatic deletion off, under **Site admin → Storage plans → Trash**.
- **Select** in the sidebar's **My notes**, **Workspace**, **Shared with me** and **Recent** tabs: tick several notes (Shift-click selects a range) and move them into a group (from **My notes**), copy them to My notes or a group, or move them to the trash (except from **Shared with me**) in one go, with a running count while it works. Moving and copying ask once for all of them; moving to the trash doesn't ask. Notes you aren't allowed to act on, or that no longer exist, are skipped, and the message at the end counts them; any other error stops it there instead, saying how many were done, and keeps the note it stopped at and those after it ticked. **Undo** after moving several to the trash brings them all back (if one of them is a group note your role can delete but not edit, there's no **Undo**, and the message says who can restore them).
- MCP: `list_trash` lists the notes in your trash (any credential), `delete_note` moves a note to the trash and `restore_note` brings one back. The last two need the new `notes:delete` scope, which only comes together with `notes:write`. No MCP tool deletes a note permanently or empties the trash (#181).
- The `notes:delete` scope — **Move notes to the trash and restore them** — can be turned on when creating a token, on a token's row in **Settings → Authorization**, and on the OAuth consent page. It is off unless you turn it on; existing tokens and apps don't get it until you turn it on for them or authorize the app again and tick it (#181).

### Changed

- The sidebar's **New note** button, which always creates a note of your own, now shows only on the **My notes** and **Recent** tabs (and while searching); it is gone from **Workspace** and **Shared with me**. To create a note in a group, use the **+** next to the group's name.
- Renaming your username now frees the old name: anyone, including you, can take it — going back to an earlier name counts as a rename against the limit of 5 per rolling 24 hours. Old links are still not forwarded to your new name; once someone else takes the name, old `/n/` and `/p/` links under it lead to their notes where the address matches (for `/n/`, only for people who can read the note). Includes a database migration that clears the names held by past renames (#291).
- Settings → Authorization → API tokens: an app's (OAuth) **Expires** date is now 30 days after the app was last used — or after you authorized it, if it hasn't been used yet — instead of when its current access token runs out, which is never more than a day away and made an app unused for a day show as *Expired*. The date moves forward on its own while the app is in use; an app unused for 30 days is removed (#298).
- Settings → Authorization → **Connect Claude with MCP** now shows two ways to connect: authorizing Claude Code or Claude Desktop (Windows) over OAuth, with no token to create — offered on `https://` sites only — and the personal-token snippets as before (#298).
- Adding a sign-in service no longer requires a client ID. Add the service first to get its callback URL, register that URL on the identity provider (GitLab, for example, gives you a client ID only after that), then enter the client ID and secret with **Edit**. A service without a client ID can't be turned on, and **Test connection** points it out. Includes a database migration (0029) that lets a sign-in service have no client ID yet (#299).
- **Allow registration** is split in two. It is renamed **Allow self-registration with a password** and only governs registering with an email and a password (it has no effect while password sign-in is off, but can still be switched then). Each sign-in service now has its own **Creates accounts** setting, a column in the service table: it decides whether someone with no account gets one on their first sign-in through that service. New services start with it off, changing a service's issuer asks whether to turn it off too, and the login page's **Create an account** button now appears only while registering with a password is available (password sign-in and **Allow self-registration with a password** both on); otherwise `/register` sends visitors to the login page (invitation links still open). The registration page no longer lists **Sign up with …**: someone with no account signs in with the service's **Sign in with …** button, which creates the account if the service has **Creates accounts** on. Includes a database migration (0031) that adds **Creates accounts** to sign-in services and carries over the current **Allow registration**; sign-in behaves as before after the upgrade.
- The sidebar shows one kind of note at a time, picked from a row of icon tabs under the search box: **Recent**, **My notes**, **Workspace** and **Shared with me** (hover a tab for its name). The tab you pick is remembered in this browser. **Recent** now lists the 20 notes most recently edited — by people or AI clients; a note never edited counts from when it was created or renamed — each with where it lives, instead of the two notes most recently created or renamed. While you search, the tabs make way for one flat list of matching notes, each with its location and the matched text highlighted; press Esc or the ✕ in the search box to return to your tab. The collapsible My notes, Shared with me and Workspace sections are gone; each group in the Workspace tab still collapses.
- Deleting a note now moves it to the trash instead of deleting it right away (`DELETE /api/notes/:id` too): **Delete note** in a note's `⋮` menu is now **Delete**, it no longer asks for confirmation, and **Undo** in the message that follows brings the note right back (if your role can delete group notes but not edit them, you can't bring it back yourself, and the message says who can instead). A note in the trash disappears from lists, search, links, its URL and its public link, and from every MCP tool except `list_trash` and `restore_note`; its attachments still count toward storage. It can be restored — with its shares, public link and history — or permanently deleted from the **Trash** tab (or `/api/trash`); notes are permanently deleted automatically after the site's retention period (7 days by default; **Site admin → Storage plans → Trash**, or `PATCH /api/admin/trash/settings`). Only the owner sees a personal note in the trash; for a group note, members whose role can both edit and delete notes — the description of a role's **Delete** permission now says so. Deleting a group with **Delete everything** still deletes its notes permanently, including those in its trash, and its dialog now counts them.
- Items in `GET /api/trash` carry the path of the folder the note is in (`folderPath`; MCP's `list_trash` doesn't show it), and restoring a note — MCP's `restore_note` included — puts it back in that folder, re-creating the path if the folder has been deleted since.
- Deleting a group with **Give them to an admin** keeps its folders: they move, with the group's top-level notes, into a new folder named after the group at the top level of that person's notes.
- The `/api/mcp` challenge and both OAuth metadata documents list `notes:delete`; `POST`/`PATCH /api/auth/tokens` and the OAuth decision accept the two new scope values (#181).
- The personal destination in a note's **Copy to…** menu is now called **My notes** (it was **Personal space**), matching the sidebar tab.

### Removed

- An admin can no longer create an account with a temporary password (**Site admin → Users → Create user**, `POST /api/admin/users`, and its optional `handle`; people can rename themselves afterwards). Use an invitation instead. Accounts already created that way and not yet changed still ask for a new password on their next sign-in (#285).

### Fixed

- Disabling an account now refuses with an error when it is the site's last enabled admin, the same protection removing admin rights already had; two admins disabling each other at the same moment can no longer leave the site with no enabled admin (#250).
- The docs no longer say a plain `http://` deployment can authorize MCP clients over OAuth with `mcp-remote --allow-http`: current clients refuse to send the token exchange to a server that isn't `https://`, so on plain http, connect with a personal token (#159).

## [0.12.0] - 2026-10-15

### Upgrade notes

The full checklist is under **Upgrading to v0.12** in [Upgrading and rolling back](docs/self-hosting.md#upgrading-and-rolling-back).

- There is no database migration.
- In a clone of the repository, `docker compose up -d` now runs the prebuilt image `ghcr.io/sw-willie-wu/knotebook` (the tag in `KNOTEBOOK_VERSION`, `latest` if unset) instead of building one: after updating the clone, run `docker compose pull`, then `docker compose up -d`; `docker compose up -d --build` keeps building from source. A `docker-compose.override.yml` that doesn't set `image:` runs the prebuilt image too; `image: !reset null` in it keeps the setup of earlier versions, where the image is built in your clone (#284).

### Added

- Prebuilt Docker images on the GitHub Container Registry: each release is published as `ghcr.io/sw-willie-wu/knotebook` for linux/amd64 and linux/arm64, tagged with its version (`0.11.1`), while `0.11` points at the highest patch release of that line and `latest` at the highest release; v0.11.1 is the first. `docker-compose.yml` now runs that image — the tag set by the new `KNOTEBOOK_VERSION` in `.env`, `latest` if unset — so installing and upgrading pull it instead of building it (`docker compose pull`, then `docker compose up -d`); `docker compose up -d --build` still builds from source. Each GitHub Release from this one on also carries a `docker-compose.yml` that runs that release's image and an `env.example`, so installing and upgrading need only those two files, not a clone of the repository; with your own PostgreSQL, the image also runs on its own with `docker run`. See [The app image](docs/self-hosting.md#the-app-image) (#284).

### Changed

- Code blocks and diagrams: the code block's language menu and the diagram's **Edit** (or **Show source**) button now sit inside the block's top-right corner instead of above it, so the blocks no longer leave an empty strip above themselves. They still stay hidden until you point at the block or move to them with the keyboard; the language menu also appears while the cursor is in the code, which makes it reachable on a touch screen — tap into the code first. When they appear, they have a solid background and a border, so they stay readable over code and diagrams in both light and dark mode; on a note you can only read, the code block's language is still shown as plain text, without the border. While you edit a diagram's source, the hint for finishing now sits below the source box.

### Fixed

- Site admin → Users and a group's Members: the name column no longer takes most of the width, leaving the email column too narrow on wide screens. The sign-in services and AI providers tables likewise give their long columns (issuer, base URL) more room.
- Settings and admin tables: the divider after the name column now only shows when the table actually scrolls sideways.

## [0.11.0] - 2026-10-15

### Upgrade notes

The full checklist is under **Upgrading to v0.11** in [Upgrading and rolling back](docs/self-hosting.md#upgrading-and-rolling-back).

- The first start after upgrading adds the **Instruct** action, enabled, with no model of its own, so it uses the same model as any other action without one: the default model, or, when no default is available (none is marked, or it or its provider is disabled), the earliest-added enabled chat model. On any site where AI actions already work, every editor can send free-form instructions right away, whether or not a model is marked as the default; disable the action in **Site admin → AI agents** if you don't want that.
- On a new install, the built-in **Rewrite** and **Translate** actions show a preview first, like the other built-in actions, instead of applying directly. Upgrading doesn't change an existing site's actions: there, Rewrite and Translate keep the apply mode they have — direct, unless an admin changed it — and an admin can switch them to preview under **Apply mode** in **Site admin → AI agents**.
- If you roll back to 0.10, the Instruct action stays in the database and 0.10 lists it as an ordinary quick action that only fills in `{{text}}`: the literal `{{instruction}}` and `{{focus}}` would reach the model, without the guard. Disable the action before rolling back (#263).
- Migration 0024 adds the time each account was last active and fills it in from the last sign-in time, so after the upgrade **Last active** shows when someone last signed in until they next use the site. Accounts with no recorded sign-in show **Not recorded** until then. Rolling back to 0.10 is harmless for the database: 0.10 doesn't read or write the new column.
- Automatic versions are now saved only after a note has had no new changes for a while — 5 minutes by default, set in **Site admin → Storage plans → Keeping automatic versions** (1–60 minutes); the version appears within about half a minute after that. Which notes were read-only for their group, and who owned each group note, can't be recovered afterwards. If you go back to that build after upgrading, it still starts on the migrated database but can't serve notes any more — loading a note or the note list fails with a server error — because columns it reads are gone; restore the dump instead. ### Added

- Groups (#103, #175): a group owns its notes. A note created in a group belongs to the group, not to a person — it lives at `/g/<group id>/<name>` (the name is unique within the group), and what each member can do with it comes from their role in the group. The sidebar gains a collapsible **Workspace** section with one section per group (each with a `⋮` menu, and a "new note here" button when your role can create and edit notes), and the other three sections (Recent, My notes, Shared with me) can be collapsed too. **Settings → Groups** lists your groups and, per group, its members — people whose role allows it can rename the group, add and remove people, and change their roles; anyone except the group's last admin can leave. See [Sharing](docs/sharing.md).
- Group roles (#175): every group starts with two roles: **Admin** (can do everything — edit and delete any note in the group, turn its public links on and off, give a note a custom URL name through the API, manage members and the group itself) and **Member** (can read, create and edit notes). People whose role allows it can define more roles on the group's **Roles** tab in **Settings → Groups**, choosing any of six permissions for each (every role can read the group's notes); the built-in Admin role can't be changed, and deleting a role moves its members to Member.
- The Share dialog on a group note has no per-person sharing: it explains who has access and links to the group's settings, plus a **Public link** switch when your role can manage public links (a group note has no custom public URL) (#175).
- Moving and copying notes (#175): an existing personal note can be moved into a group (its per-person shares and public link are removed, and its old address forwards to the group address for a month) or copied into one, and any group note you can read can be copied to your own notes — a copy gets its own copies of the note's attachments, which count against your upload limit. No single note can be moved out of a group (deleting a group can give all of its notes to an admin).
- Deleting a group (#175) either gives all its notes to one of its admins — they become that person's personal notes, their public links are turned off, and their old `/g/` addresses forward that admin to them for a month — or deletes the notes with it.
- Groups over the API and MCP (#175): every note response (`NoteDto`) now reports what you can do with it in a `permissions` object, and `GET /api/notes/by-group-path/:groupId/:slug`, `GET /api/groups/:id/roles`, `POST /api/groups/:id/roles`, `PATCH /api/groups/:id/roles/:roleId`, `DELETE /api/groups/:id/roles/:roleId`, `POST /api/notes/:id/move` and `POST /api/notes/:id/copy` are new, alongside the group and member endpoints (`DELETE /api/groups/:id` takes `{mode: "transfer", transferTo}` or `{mode: "delete"}`). MCP clients see group notes in `list_notes`/`search_notes`, can edit them when their role allows, and can create a note in a group by passing `create_note` the new `groupId` argument (when their role can create notes there); they can't move or copy notes, and no MCP tool lists your groups — see the [API contract](docs/api.md), [MCP](docs/mcp.md) and [Known limitations](docs/known-limitations.md).
- The sidebar can be resized: drag the gap between the sidebar and the note — or reach it with Tab and use the left and right arrow keys (16 pixels a step), Home and End — to make the sidebar anywhere from 200 to 480 pixels wide; double-click the gap to go back to the default 256. The gap stays invisible until you drag it or give it keyboard focus, when a thin line appears; hovering it only changes the pointer. The width is remembered in this browser. On narrow windows, where the sidebar opens as a drawer, the drawer keeps its fixed width. The width doesn't adapt to the window, so a sidebar widened on a large screen can leave too little room on a small one — see [Known limitations](docs/known-limitations.md).
- Every note in the sidebar has its own `⋮` menu with the same items as the `⋮` at the top of an open note: **Copy link**, **AI edit history**, on group notes **Copy to my notes**, and, on notes you can delete (your own, or a group note when your role allows it), **Delete note** — so the sidebar can delete notes again. Used on the note you have open, it does what the top-of-note menu does (deleting takes you back to the home page). Used on another note, **AI edit history** opens that note with its history already showing, and deleting it leaves you where you are. Deleting a note from the sidebar while that note is still loading, and screen-reader names for notes that share a title, are covered in [Known limitations](docs/known-limitations.md).
- A request that has waited 10 seconds for a free database connection now fails with a server error instead of waiting indefinitely, and two optional settings, `DATABASE_POOL_MAX` (default 10 connections) and `DATABASE_POOL_CONNECTION_TIMEOUT_MS` (default 10000), set how many database connections the server opens and how long a request waits for one — see [Self-hosting](docs/self-hosting.md) (#175).

## [0.4.0] - 2026-09-14

### Added

- You can now create **API tokens** to let a script or an AI assistant work with your notes on your behalf. Settings → Account → API tokens issues a token that acts as you on a small set of note endpoints — listing your notes, reading a note's details, and (optionally) creating one; the token is shown once, stored only as a hash, and can be revoked at any time. Tokens are deliberately limited: they work on that short allow-list of endpoints and nothing else, so a leaked token cannot take over the account, change your password, or manage sharing. They are also independent of your password — changing it does **not** revoke them, the same way personal access tokens work elsewhere; revoke them here instead. Token requests are rate-limited separately from browser sessions, so a runaway script cannot lock you out of the web UI. See [API tokens](docs/api-tokens.md) (#107).

- API tokens (and Apps authorized over OAuth) can now **read a note's content** as markdown — the whole note or a single section, together with an outline and per-section fingerprints that a later write can use to avoid overwriting concurrent edits. Reading does not change any of the note's content. See [API tokens](docs/api-tokens.md) (#106, #136).

- Signing in now takes you back to the page you were trying to open. Previously, following a link to a note (or any other page) while signed out sent you to the login page and then dropped you on the home page, and you had to find your way back by hand. This works for both password and SSO sign-in; the destination is validated as a page path on this instance, so a link can never use it to bounce you to another site, and on the SSO route it is validated a second time when you come back from the identity provider. Three cases still land you on the home page: an account that has to change its password on first sign-in, a destination that fails validation, and signing out (where leaving is the point) (#107).

- **MCP clients can now authorize themselves** instead of you pasting a token. Knotebook includes an OAuth 2.1 authorization server, designed for an MCP client running on your own machine — such as Claude Code connecting directly, or Claude Desktop through a local stdio bridge — to discover the server, register itself, open a consent page in your browser, and, once you press Allow, receive its own credential; verified end to end with `mcp-remote --allow-http` against a plain-`http://` deployment. Claude Code's built-in HTTP transport needs an `https://` deployment — on plain http it walks through consent and then refuses to send the token request — see [How to connect](docs/mcp.md#how-to-connect) for both commands. That credential appears under Settings → Account → API tokens as an *App* row beside your personal tokens and can be revoked there; re-authorizing the same app replaces its previous credential. The consent page shows the app's self-reported name (marked as unverified) and the loopback address it will return to — only apps running on your own machine can be authorized, which is what keeps unauthenticated registration from becoming a phishing surface. Apps unused for 30 days are cleaned up automatically. See [API tokens](docs/api-tokens.md) and the OAuth entries in [Known limitations](docs/known-limitations.md) (#107, #132).

- API tokens and authorized Apps can now **write note content**: replace the whole note, replace/insert after/delete one section, or append — each guarded by the fingerprint returned by a read, so concurrent human edits are never silently overwritten, and a note can now be created with its text in the same request. Changes appear live in every open browser tab. Every successful write is recorded, and can be reverted — through the API, and from the app (see the entry below) — while the note has not moved on and the row is still among the at most 100 rows a note keeps; the note now remembers who edited it last, and whether that was a person or a program. See [AI editing](docs/ai-editing.md) (#106, #137).

- **AI edits are now visible in the app.** While an API token or an authorized App works on a note, everyone who has that note open watches its cursor move, briefly labelled `username (agent)` after each change (hover the cursor to bring the name back); the title bar shows who edited the note last and whether that was a person or a program; the ⋮ menu's new **AI edit history** lists the writes the API made — a note keeps at most 100 — and lets you revert one; and Settings → Account renames the agent shown for each credential (the default is the first word of the token's or app's name). Presence exists only while somebody has the note open and fades after two minutes of quiet — the edit history is the lasting record. See [AI editing](docs/ai-editing.md) and the presence entries in [Known limitations](docs/known-limitations.md) (#106, #138).

- **An MCP client can now read and write your notes.** Point Claude Code, Claude Desktop, or any other client that speaks MCP at `/api/mcp` — by letting it authorize itself over OAuth, or, if the client lets you set an `Authorization` header, with a personal API token — and it gets six tools: `list_notes` and `search_notes` to find a note, `read_note_outline` and `read_note_section` to read one a section at a time, and, with a `notes:write` credential, `edit_note` and `create_note` to change one or make a new one. A read-only credential simply never sees the last two. Reading is always sectioned — no tool hands back a whole note, and one call returns at most 4000 characters of text or 100 section headings — which caps any single answer rather than how much an assistant can read in total. `edit_note` goes through the same path the API already used, so a change lands live in every open tab and is recorded in that note's **AI edit history**, where you can undo it while the note has not moved on and it is still among the at most 100 rows a note keeps; every operation but `append` also has to hand in a fingerprint, which is what stops it overwriting what somebody just typed. A `create_note` carrying `content` is recorded the same way; one without it simply makes an empty note and records nothing. The rate limits are the ones API tokens already had, counted per tool call — except the 300-reads-a-minute one, which one `POST /api/mcp` spends once no matter how many tools it calls, because the endpoint always declares read access. See [MCP](docs/mcp.md) for the tools, the commands for each client, and the exact limits — and the MCP entries in [Known limitations](docs/known-limitations.md) (#108).

### Changed

- `POST /api/notes` now rejects unknown body fields with `400 invalid_body` instead of ignoring them, so a misspelled `content` field is reported rather than silently creating an empty note (#106, #137).

## [0.3.3] - 2026-09-02

### Added

- Every account now has a **username** — a short, URL-safe name (lowercase letters, numbers, hyphens) shown and changeable under Settings → Account, for both password and SSO accounts. Existing accounts get one derived from their email's local part on upgrade; SSO sign-ups prefer the identity provider's `preferred_username` claim when the ID token carries it, and admins can set one when creating an account via the API. Renaming is allowed 5 times a day, and a released name is **permanently retired — nobody can ever take it, including you changing your mind** — so links shared under an old name can never start serving someone else's content. The username appears in Settings and the admin user list, and every new-form note URL carries it (`/n/<username>/<slug>` — see the note-URL entry below; old-form `/notes/…` links don't and are rename-proof); it can also appear in a public share's URL when you opt in (see the custom-public-URL entry below).

- Note URLs are now human-readable: `/n/<username>/<slug>` — no uuid suffix. The slug follows the note's title automatically (renaming the note moves its URL, collisions among your own notes get a numeric suffix), or you can pin a custom one in the Share dialog, which now shows the three states honestly: the input is empty unless you've set a custom slug, its placeholder always shows the automatic URL you'd get, and a "Use automatic URL" button appears only when there's a custom slug to give up. Slugs are unique **per user** rather than instance-wide, so `slug_taken` now only ever means another of your own notes. Every previously shared `/notes/…` link keeps working forever (the pre-revamp slug is frozen as a permanent alias, and uuid-suffixed links resolve as before); the sidebar's "current note" highlight now tracks the note itself rather than the URL, so it survives renames. One API-visible behaviour change: `PATCH /api/notes/:id` with `slug: null` now means "back to an automatic slug recomputed from the title" rather than clearing it, and counts against the slug-change rate limit. One upgrade-time note: the migration derives slugs from titles in SQL, which handles ASCII only — a note with a non-ASCII title comes out as `untitled(-n)` and its URL shifts once more, silently, on its first title save afterwards. The other costs that come with human-readable URLs — automatic URLs moving with the title, one level of grace for custom slugs, slug re-use within an account, and username renames breaking `/n/` links — are recorded in [known limitations](docs/known-limitations.md) (#122).

- A note can now be shared with a public link — anyone who has it can read the note at `/p/<token>`, no account needed. The Share dialog gains an access selector with three levels: **Private** (only you; picking it while members exist asks for confirmation first — covering the link too when one is on — and removes the link before the members so an interrupted switch never leaves the link live; with no members it just turns the link off), **Members only** (the existing email invitations, unchanged), and **Public link**, which shows the URL with copy and regenerate buttons. The public page is strictly read-only, shows the note's title, content and its uploaded images, requires no login, carries `X-Robots-Tag: noindex`, and renders none of the editing machinery; regenerating or turning the link off makes the old URL answer an indistinguishable 404 immediately. The link token is unguessable (256-bit), never appears in server logs, and the public endpoints are rate-limited in a way that doesn't reveal whether a token exists. What anonymous readers see is a snapshot that can lag active editing by a few seconds — the full behaviour, and its recorded trade-offs (Yjs state exposure, cross-note images, browser-cached images after revoke, `TRUST_PROXY` behind a reverse proxy), are documented in [Sharing](docs/sharing.md) and [known limitations](docs/known-limitations.md) (#72).

- A public share can now also have a **custom public URL**: `/p/<username>/<name-you-choose>`, set from a new row in the Share dialog while the public link is on. It serves the same read-only page as the token link (images included) and is an addition, not a replacement — the token link keeps working, **Regenerate link** replaces the token without touching the custom URL, removing the custom URL leaves the token alive, and switching to Members only/Private deletes both. The trade-off is spelled out in the dialog itself: a readable URL is a guessable URL, and it reveals your username — for anonymous sharing, use the token link. Names are unique per account (yours can't collide with another user's), validated like note slugs, and share the slug-change rate limit. Renaming your account kills the old custom URL immediately (old usernames are never forwarded) — the name itself survives and keeps serving under your new username. The custom-URL page carries the same `noindex` and the same indistinguishable-404 discipline as the token page; the finer print (username disclosure, doubled read quota for a note reachable both ways) is in [Sharing](docs/sharing.md) and [known limitations](docs/known-limitations.md) (#122).

- Knotebook now sends a Content-Security-Policy with the page. A script injected into a note's content does not run, plugin content (`<object>`/`<embed>`) is refused, `fetch`/XHR/WebSocket can only reach Knotebook itself, and the app can no longer be framed by another site. Images, audio and video embedded by URL keep working, over both http and https — that is a deliberate policy choice, since a note can already reference an external image on purpose, and the same holds for diagrams; a note's content can therefore still cause requests to an outside host by referencing one. Two consequences worth knowing if you self-host: stylesheets, fonts and scripts have to come from Knotebook itself, so a reverse proxy that injects an analytics script into the page, or assets moved to a separate CDN, will be blocked, and Knotebook can no longer be embedded in an iframe — see [Self-hosting](docs/self-hosting.md#content-security-policy). Pages also carry `Referrer-Policy: no-referrer`, so a site hosting an image you embedded no longer learns which note is being read, and `X-Content-Type-Options: nosniff` (#101).

- The backlinks strip at the bottom of a note is now a single row — the "Mentioned in N notes" label sits inline with the source chips, which scroll sideways when there are more than fit — and it is always present, showing "No mentions yet" when nothing links here. Previously the label sat on its own line above a wrapping list of chips, and the whole strip disappeared when a note had no backlinks, which made the feature invisible on any note nobody had linked to yet and let the note card's height jump around. The row is the same height as the account row at the bottom of the sidebar, so the two line up.

- The note's text column now scales with the window instead of stopping at a fixed 680px: it takes 85% of the scrolling area's width, between 680px and 1056px. Windows up to about 1100px wide keep the column they had — 680px is the floor, and a window narrower than that still gets a full-width column — while on wider screens the article grows with the card instead of sitting as a narrow strip between two large empty margins (#87).

### Fixed

- Redo now works after undoing a note all the way back to empty. Previously, undoing until the note was blank silently discarded the redo history a fraction of a second later — the editor puts the required empty paragraph back into a blank note, and that correction was being recorded as if it were a fresh edit of yours, which is exactly the situation where an editor is supposed to throw redo away. That correction is no longer treated as an edit, and redo brings your text back reliably, including undoing and redoing across the same boundary repeatedly. Deliberately deleting everything in a note is still a normal, undoable edit. This closes the one known gap in the undo fix shipped alongside it (#100).

- Typing `[[` to link another note now works when the two brackets arrive together rather than one at a time. Previously the menu only opened if the editor saw each `[` as its own separate keystroke, so it failed when you typed quickly and the browser batched them, and it failed every time under a Chinese input method — where committing the pending characters sends the whole run, brackets included, as a single edit. The workaround people found (pressing `[` a few more times until one landed on its own) is why it looked intermittent rather than broken. Detection now looks at what sits before the cursor once the input lands, so anything the input method commits alongside the brackets is kept instead of being swallowed. Typing `[` over a selection still replaces the selection and opens the menu, as before (#98).

- Undo works again in the editor. Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl/Cmd+Y did nothing at all — silently, with no error — on every note, in every browser. Notes are collaborative documents, so undo is handled by Yjs rather than by the editor's own history, and the piece of Yjs that records what you changed was being torn down and never reconnected the moment a note finished loading: it stopped listening before you could type your first character. Undo history is per note and only ever takes back your own edits, never a collaborator's. Redo works too, with one exception that is still open: if you undo all the way back to an empty note, redo cannot bring the text back (undo itself is fine, including undoing to empty) — see [Known limitations](docs/known-limitations.md) and #100 (#97).

## [0.2.0] - 2026-08-25

### Security

- An embedded image, video, audio or file URL is now checked again when it is rendered, not only when it is typed into the embed field. Note content is a collaborative Yjs document, so any collaborator with edit access can write block properties directly and bypass the input check entirely — a `javascript:` or `data:` URL written that way went into every other reader's document unfiltered (inert in an image or media `src`, but it had no business being there). Uploaded files keep working: the render-side check deliberately accepts the relative URLs uploads produce. A URL that fails the check renders as a broken image or player rather than being fetched (#12).
- An AI provider's stored API key is now cryptographically bound to the provider it belongs to, so a key that ends up under the wrong provider is reported as undecryptable instead of being used. The ciphertext was AES-256-GCM but carried no associated data, so a key copied into another provider's row decrypted just fine and that provider would happily send it upstream — which is how a row restored from an old backup, or a hand-written `UPDATE`, could silently start billing someone else's account. This is an integrity check rather than a defence against an attacker who can already write to the database: anyone who can move ciphertext between rows can also point a provider's base URL at a host they control and read the key in plaintext. Old ciphertexts still decrypt and are rewritten in the new format on the next start (including disabled providers; a failed rewrite is logged and retried next time, never blocking startup). **The rewrite is one-way** — see [Known limitations](docs/known-limitations.md) before rolling back to an older version (#14).
- Changing an AI provider's Base URL now clears its stored API key. The key is sent in plaintext to whatever host that field names — by design, that is what a provider is — so until now any administrator could point an existing provider at a host they controlled, press Test, and receive a key they were never able to read back through the UI. Supplying a new key in the same edit keeps the provider working in one step, the Settings UI warns before saving, and a provider with no key stored now says so on its card. Editing a provider without touching its URL does not clear anything. This does not make an untrusted administrator safe — they can still point a provider somewhere and wait for a key to be entered again, which is now visible rather than silent, and logged with the account and the old and new host. See [Known limitations](docs/known-limitations.md) (#46).
- Copying a note block to the clipboard, and the markdown handed to an AI quick action, now pass embedded media URLs through the same check that rendering does. The #12 fix guarded every place a URL enters this app's own pages, but export took the raw stored URL — so copying a block a collaborator had poisoned pasted `<a href="javascript:…">` or `<img src="javascript:…">` into whatever application received it, and an AI action sent the raw URL upstream. Not an XSS in Knotebook itself (that path was already closed), but poisoned content should not leave the app either. A URL that fails the check is exported as `about:blank`; uploaded files and ordinary web links export unchanged (#43).
- The server now notices when a note's document contains a media URL with a scheme like `javascript:` or `data:`, and says so in the log. Note content is writable by any collaborator with edit access, and the client-side guards (#12, #43) replace such URLs everywhere they could do harm — but the string itself stays in the document indefinitely, invisible to whoever runs the instance. On save, the server scans media-URL fields and logs one warning per note per load cycle naming the note, the schemes and the block types (never the URL itself, and never more than one line however often the note saves). It deliberately does not rewrite or reject anything: teaching the server to validate document content is a design decision this change does not make. See [Troubleshooting](docs/self-hosting.md#troubleshooting) (#44).
- A collaboration connection that keeps sending messages the server cannot handle is now dropped. The collaboration library's reaction to such messages — an unknown message type, a type its enum names but its handler has no case for (`SyncStatus`/`Ping`/`Pong`), or an authentication message of a kind only servers send — is to write an unstructured error line and carry on, without closing the connection or counting against any of this app's log throttles; a signed-in user connected to their own note could therefore write to the server's log at close to line speed for as long as they liked. Those messages are now classified against the set the library actually handles and dropped before they reach it; a connection that accumulates ten of them is forcibly disconnected, leaving one log line naming the note, address and message type — that line itself capped process-wide at ten per minute, since it can be triggered before anyone is signed in. The tolerance exists because an unknown type can also be a newer client talking to an older server during an upgrade; the flip side, recorded in [Known limitations](docs/known-limitations.md), is that a future client version introducing a frequent new message type would see its connections dropped until the server is upgraded too. As a second layer, the compose file now caps the `app` container's log size (50 MB × 5 files) so any future log-writing path degrades into rotation rather than a full disk (#50).

### Fixed

- Test-only: the note page's error screen now has an integration test pinning that opening and closing the settings dialog on top of it does not trigger a page reload. The error boundary added in #66 deliberately keys its "user navigated away, reload to recover" behaviour on the note reference from the URL rather than the router's location key, because closing the settings dialog navigates back to a saved location and that produces a fresh location key — keying on it would turn "close the dialog" into a surprise full-page reload. That choice was only recorded in code comments; switching it back would have kept every existing test green. The new test walks the real route tree through open-settings/close-settings on a failed note page and asserts zero reloads, alongside positive controls proving the reload spy actually intercepts the boundary's default reload path on both lifecycle routes. The same change also hardens two pre-existing settings-dialog tests that waited on the note page's real lazy import with the default one-second timeout — the only such waits in the suite, and intermittently red under a cold, loaded worker even without this branch (#68).
- A note page whose code chunk fails to load — the tab is offline, or a deploy rotated the asset hashes out from under an open tab — no longer strands the user on a blank white page. The note editor's code is loaded on demand (#19), and a failed load used to escape as an uncaught render error that unmounted the entire app. Now, when the failure looks like a deploy rotation (the network is up and this tab's one automatic retry hasn't already been spent), the page reloads itself once — picking up the new asset hashes, usually without the user noticing; the retry budget is re-armed each time a chunk load succeeds, and a genuinely broken deploy degrades to an error screen instead of a reload loop. In every other case — offline, retry exhausted, storage unavailable, or a crash inside the note page itself rather than a chunk failure — the app shell stays up with a message and a retry button, and navigating to another note from the sidebar — when the network is up — recovers via a reload too. As a backstop, the whole app is now wrapped in a top-level error boundary, so *any* unhandled render error shows a "Something went wrong — Reload" screen instead of a white page. The chunk-failure detection matches known browser, bundler and reverse-proxy error messages (a failed load of this chunk usually surfaces as Vite's CSS-preload error, not a bare failed import) and the one-reload budget lives in per-tab session storage — both edges are recorded in [Known limitations](docs/known-limitations.md) (#66). While the tab is offline, the retry and reload buttons are disabled — without a service worker, reloading offline would land on the browser's network-error page instead of back in the app — and they re-enable the moment the browser reports the connection is back.
- An AI quick action that fails because its OpenAI-compatible provider has no API key stored now says so — "AI provider is unavailable — ask an admin to re-enter the API key" — instead of the unrelated "The AI provider returned an error". A provider with no key is a legitimate configuration for a local vLLM or Ollama, so the request is still sent; but since changing a provider's Base URL clears its key (#46), "models attached, key gone" became an easy state to reach, and the resulting upstream 401 deserved a message pointing at the actual cause. The mapping is deliberately narrow: only an upstream 401/403 on a provider with no stored key — a provider whose key was revoked upstream still reports a provider error, not a missing one (#53).
- Test-only: the backlinks endpoint's two safety properties — readers only see source notes they have access to, and the list is capped — now have a combined regression test pinning their order. Each property was tested separately, but nothing failed if the implementation ever capped first and filtered after, which would show readers an empty or incomplete list while burying the titles they may see under a stranger's flood of newer notes. The new case floods past the cap with inaccessible sources and asserts the reader still gets exactly their few visible ones; rewriting the query cap-first was verified to turn it red (#25).
- Test-only: the end-to-end tests' shared note-creation helper now waits for the "Connected" badge before handing the note over for typing, instead of borrowing that precondition from #48's read-only-until-synced behaviour. The flake this guards against — text typed before the collaboration handshake completed was silently lost on reload — was closed as a side effect of #48; the explicit wait keeps the suite stable if editing before first sync ever comes back (#33).
- The integration test harness now drops each throwaway database it creates instead of leaving it behind. Every test provisions its own `test_<random>` database and only closed its connection pool afterwards, so a single full run accumulated several hundred databases in the one Postgres container — until `CREATE DATABASE` started failing partway through and the run went red in a way that looked like a flake but cleared on a rerun (a fresh container). Each database is now dropped when its test finishes, with `WITH (FORCE)` to evict any straggler connection and a drop failure logged rather than allowed to fail an otherwise-green test (#51).
- The editor no longer looks connected while it is offline, and no longer lets you type into a note that never loaded. Previously the badge read "Connecting" identically at second 1 and minute 30, and the editor accepted typing the whole time — worst of all when a note failed to load at all, where you could type into a blank document and lose it on reload. Now a note that has never synced is read-only until it loads, and once a connection has dropped for more than a few seconds the badge escalates to a warning: "Editing offline — changes not synced yet" when there is synced content to merge back, or "Not loaded — offline" when there is not. Brief reconnects (a few hundred milliseconds) do not flash anything (#48).
- A rejected collaboration handshake no longer tells people they lost access to a note when they did not. The server had one rejection reason for three different situations, and the client turned all of them into "You no longer have access to this note", closed the note and returned to the list. So an account that was disabled, or whose sessions were invalidated by a password change elsewhere, produced that notice instead of a sign-out; an unexpected server-side error produced it too. The server now separates a genuine access decision from "this token cannot be used right now", and the client only acts on the former — anything else retries the handshake on the same widening delay used for token failures, which for a revoked session converges on a sign-out within seconds. A revoked share still converges on the same notice it always did. Relatedly, a note that finished deleting while a tab was in its reconnect backoff now says the note was deleted rather than blaming the person's access, for a two-minute window after the delete; past that the server deliberately cannot tell the two apart, because distinguishing them for everyone would turn the connection into a way to ask whether any given note id exists (#35).
- A collaboration token response that arrives after switching notes is now ignored instead of being applied to the note now on screen. The request for the previous note stayed in flight across the switch, and its role landed in the current note's state — worst case, the previous note's `none` arrived while the current one was in its post-revocation retry window and ejected someone from a note they had every right to be in (#36).
- A note that cannot fetch its collaboration token now keeps trying instead of sitting on "Connecting" forever. When the token request kept failing past its retry budget, the connection was left open but unauthenticated with nothing scheduled to try again — so a server hiccup during a page load meant that tab stayed dead until it was reloaded, even after the server recovered. It now restarts the whole handshake on a widening delay, and resets that delay once a connection succeeds (#39).
- A reconnect that was slow to close no longer wedges the connection. The one-second safety net that covers "the socket was already gone" used to give up waiting for the real close event; if that event then arrived, it was read as an ordinary disconnect and nothing reconnected, leaving the editor on "Connecting" until reload (#34).
- Losing access to a note before its collaboration connection is established no longer parks the editor on "Connecting" forever — whether the note was still opening or the connection happened to be reconnecting at the time. When the share is revoked before that handshake completes, the server rejects the handshake itself rather than sending the close message the client was waiting for, and that rejection carried no state change at all. The client now reads it, retries once with a fresh token, and then shows the same "You no longer have access to this note" notice and returns to the note list as any other revocation (#6).
- A single SSO sign-in no longer spends two units of the same rate-limit quota. `GET /api/auth/oidc/login` and `GET /api/auth/oidc/callback` shared one 30-per-minute-per-IP bucket, and a complete sign-in always goes through both — so the usable number of sign-ins was half the advertised one, which offices behind a shared outbound IP hit first. Each endpoint now counts against its own bucket (#16).
- The failed-login throttle no longer grows without bound. Its account and IP records were only dropped when the same key happened to be touched again after 15 idle minutes, so a spray of distinct accounts or addresses left entries behind for the life of the process. Both tracks now share the same bounded map the other limiters already used, and the record evicted first is always the one whose last failure is oldest — the one closest to expiring anyway (#15).
- Deleting an AI provider now also drops it from the degraded set. Nothing else clears that entry — re-entering an API key is the only other path — so the id lingered for the life of the process (#17).
- The password-length hint is generated from the shared `MIN_PASSWORD_LENGTH` constant instead of being written out in each translation, so raising the minimum can no longer leave the UI advertising the old one (#22).

### Changed

- The first page load no longer downloads the note editor. The editor and its collaboration machinery — two thirds of the previous 1.6 MB bundle — only matter once a note is actually opened, but they shipped in the initial bundle that the sign-in page, the note list and the settings dialog all had to wait for. The note page is now loaded on demand: the initial bundle drops to roughly a third of its former size (about 495 KB to 167 KB compressed), opening the first note fetches the editor chunk with the same loading indicator the page already shows while fetching the note, and a CI check now pins both the entry-bundle ceiling and the presence of the split-out chunk so neither regresses silently (#19).
- Email lookups — sign-in, adding a share by email, OIDC account linking — now use an index. Every one of them compares `lower(email)`, but the schema only indexed the raw column, so each lookup walked the whole users table; unnoticeable on a small instance, a real cost as accounts accumulate. The new index is deliberately non-unique: case-variant duplicate emails are allowed to exist, and OIDC sign-in depends on being able to detect that situation rather than having the database reject it — a test pins both the index and that property (#18).
- The re-verification deadline that closes a collaboration connection when its holder loses access is now documented as what it actually is: deliberately shorter than the client's worst-case token-retry backoff (5s vs 7.5s), so a revocation never waits out a retrying client. A false positive costs the affected client a reconnect — and if the backend is still failing, its usual restart backoff and an offline badge until things recover — but never mislabels them as having lost access. The comment next to the constant used to claim the margin covered that backoff, which was false and would mislead anyone tuning either number. Both constants now live in the shared package, and a test pins the deadline-shorter-than-retries relationship so changing either side forces a conscious revisit (#40).
- A refused collaboration connection now leaves a line in the server log — which note, which account, which of six causes, and whether it was refused while connecting, closed after a permission re-check, or closed because the client did not answer that re-check in time — and an unexpected error inside the handshake is logged with its stack trace instead of being flattened into a generic rejection. Since a refusal now navigates the person away rather than leaving them stuck on "Connecting", the report that reaches the maintainer is "I got kicked out", with nothing on either side to say why. The refusal lines are capped per account, with errors on their own budget and a warning when the cap bites, and refusals decided before the token identifies anyone are logged at `debug` so an anonymous socket cannot drive them at all. (The line written when a client misses a re-check is not capped — it is bounded by how many connections that re-check covered.) See [Troubleshooting](docs/self-hosting.md#troubleshooting) (#37).
- A few stray simplified-Chinese characters and one garbled sentence in source comments (#34).
- **Breaking for reverse-proxy deployments:** `X-Forwarded-For` is no longer believed by default. It used to be trusted from any source, which let anyone forge their apparent address and walk around the per-IP login lockout and the OIDC endpoint limits. The new `TRUST_PROXY` setting turns it back on — a list of trusted proxy addresses (IPs, CIDRs, or `loopback`/`linklocal`/`uniquelocal`), a hop count, or `true` for the old behavior. **If you run behind a reverse proxy and do not set it, every visitor arrives as the proxy address and shares one rate-limit bucket**, so five bad passwords from anyone lock out everybody. The server logs a warning at startup when `PUBLIC_URL` is https while the setting is off, and once at runtime when it sees a forwarding header it was told not to trust. Note that your proxy has to send `X-Forwarded-For` for the setting to do anything (nginx does not by default), and a proxy that rewrites `Host` and relies on `X-Forwarded-Host` will now fail image uploads with 403 until `TRUST_PROXY` is set (#13).
- The collab-token rate limit stays keyed on the user, not the note, and the reasoning is now recorded next to it: the limit exists to bound what one signed-in user can cost the database, keying it per note would multiply an attacker's allowance by their note count, and keying it on the address would penalise offices behind one outbound IP (#24).
- The AI session's context value is memoised, so a streaming response no longer rebuilds every consumer — including the portal-mounted toolbar — on each delta (#20).
- `POST /api/auth/login` and `GET /api/auth/me` are typed against the shared `UserDto`, and `GET /api/auth/config` against `AuthConfigDto`. A change to those shapes now fails the build in `apps/server`, where the mistake is, rather than in the web app that consumes them (#21).
- A stray simplified-Chinese character in a source comment (#23).

**Admin AI configuration**
- Provider/model/action CRUD (`/api/admin/ai/*`) with a connection-test endpoint, shared model resolution, and `GET /api/ai/actions` (only actions that currently resolve to a usable model).
- AI provider API keys encrypted at rest (AES-256-GCM, key derived from `APP_SECRET`); four built-in actions (rewrite/translate/summarize/continue) seeded idempotently at boot, renameable/disableable but not deletable.

**Settings modal**
- Notion-style Settings modal (Account, Users, AI) opened over the background route from the user menu, replacing the standalone `/admin/users` page; shares its password-change form with the standalone `/change-password` page used for forced resets.

**End-to-end testing**
- Playwright end-to-end test suite (`e2e/`) exercising bootstrap, notes, live collaboration, sharing/revocation, AI quick actions, and OIDC login against a stub identity provider, runnable locally via `scripts/test-e2e.sh` and wired into CI as a dedicated `e2e` job on pushes to `main` (and manual dispatch).

### Changed
- Email matching (login, sharing, admin user creation, OIDC account linking) is now case-insensitive: every write path normalizes the address to lowercase, and every lookup compares via `lower(email)`. `alice@example.com` and `Alice@example.com` now resolve to the same account.

### Fixed
- Hocuspocus setup hash-busy handling and collab hook contract corrections found in final review.
- Router `maxParamLength` raised to 512 so astral (surrogate-pair) characters in note references don't 404.
- Toast id generation no longer depends on `crypto.randomUUID`, which is unavailable in non-secure contexts such as LAN plain-http.
- Viewport-locked app shell so the editor, AI panel, and backlinks regions scroll independently instead of the whole page.
- `/admin/users` now redirects (`<Navigate replace>`) to `/settings/users` instead of 404ing, so old bookmarks/links keep working.
- AI action reorder buttons are disabled while a move is in flight, preventing rapid double-clicks from writing duplicate `sortOrder` values that made ordering unrecoverable from the UI.

### Security
- CSRF protection on uploads scoped to `Origin` header validation, with a documented exemption for requests that carry no `Origin` at all (matching legitimate non-browser clients).
- Byte-capped request body draining and an embed-URL scheme whitelist to bound abuse from unauthenticated or rejected requests.
- Outbound AI provider requests (connection test and streaming) use `redirect: "manual"` so a 3xx from a misconfigured/malicious upstream can't cause the custom `Authorization` header to be forwarded to a third-party host — undici only strips `Authorization`/`Cookie` automatically on redirect, not custom-named auth headers.
- AI provider API keys are never serialized into any API response (admin endpoints return a derived `hasKey` boolean instead of the ciphertext).
