# API contract summary

All endpoints are served by the `app` container. Errors use the shape `{ "error": { "code": "...", "message": "..." } }` unless noted. "Auth" = session cookie required; "Admin" = admin session required. Any `Auth`/`Admin` row can also return `401 unauthorized` (missing/invalid session) or, for `Admin` rows, `403 forbidden` (authenticated but not an admin) — these are omitted from the per-row status codes below for brevity.

A few endpoints also accept a Personal API token as `Authorization: Bearer knb_…` — those are marked `Auth / Token(scope)` (see [API tokens](./api-tokens.md)). On those endpoints a request carrying an `Authorization` header is authenticated only by that header and the session cookie is ignored; the two upload endpoints do the same with a transfer token instead (see their rows); everywhere else the header is ignored and the cookie is used. These endpoints expose note metadata and, through the `/content` and `/edits` rows below, note content — both reading it and writing it (writing needs `notes:write`); see [AI editing](./ai-editing.md) for the fingerprints, the five write operations and revert. Token requests are rate-limited per user separately from browser sessions (300 reads/min, 60 writes/10 min); on top of that, `GET /api/notes/:id/content` and `GET /api/notes/:id/edits` share their own, tighter 120-reads-per-minute-per-user budget, and `POST /api/notes/:id/edits`, `POST /api/notes/:id/edits/:editId/revert` and `POST /api/notes` carrying `content` share a 30-writes-per-minute-per-user one (see their rows below; saving, applying, renaming and deleting a note version, which are session-only, draw on it too), so a token calling them is really capped at 120/min and 30/min. Both tighter budgets are keyed by user and apply to browser sessions too — though in practice the web app never calls the content endpoints itself; it reads and writes note content through the live collaboration connection instead. The MCP tools draw on the same 120-reads-per-minute and 30-writes-per-minute budgets: `read_note_outline`, `read_note_section` and `create_transfer_token` with `download` on the 120-reads-per-minute one, `edit_note` and `create_note` carrying `content` on the 30-writes-per-minute one. `list_notes` and `search_notes` draw on neither; `search_notes` has its own budget, 60 searches per minute per user. Because one `POST /api/mcp` can carry several tool calls, these are counted **per tool call**, not per request (#108). A runaway client cannot lock you out of the web UI, and invalid Bearer attempts are limited per IP (30/min). Endpoints that accept a token answer `401`/`403` with a `WWW-Authenticate: Bearer …` challenge (with `error="invalid_token"` / `error="insufficient_scope"` when a Bearer token was presented, and no `error` when no credentials or a non-Bearer scheme such as `Basic` were sent); the two upload endpoints answer a `401` to a request **carrying an `Authorization` header** with `WWW-Authenticate: Bearer realm="knotebook-transfer"` (with `error="invalid_token"` when a Bearer token was presented; without `error` for anything else, such as `Basic`), and without the header they answer like every other endpoint; every other endpoint answers a plain `401 unauthorized` with no challenge. The challenge's `resource_metadata` always points at `/api/mcp` regardless of which endpoint was called — see [Known limitations](./known-limitations.md); the upload endpoints' challenge carries no `resource_metadata`. Scope has exactly two values: `notes:read` and `notes:write` (which includes read). Tokens are issued only by this server (no external identity providers), can never mint a collaboration token (`POST /api/notes/:id/collab-token` is session-only) nor rename an agent (`PATCH /api/auth/tokens/:id`, like the rest of `/api/auth/tokens`, is session-only), and revoking one deletes it outright.

Besides personal tokens, an MCP client can obtain its own credential through the built-in **OAuth 2.1 authorization server** (`/.well-known/*`, `/oauth/*` — see the OAuth rows below and [API tokens](./api-tokens.md)). Besides those endpoints, every error body on this server is the `{error:{code,message}}` shape — with `/api/mcp` as a partial exception: everything its HTTP layer rejects (`401`, `403`, `413`, `429`, a `415` from the content-type guard, and a malformed or empty body's `400`) uses the normal shape, while its `405` on `GET`/`DELETE`, the MCP transport's own answers (a `415` when no `Content-Type` was sent at all, a `406` when `Accept` is missing `text/event-stream`) and every tool-level error are JSON-RPC. The OAuth endpoints answer in the RFC 6749 §5.2 / RFC 7591 form `{error, error_description}` (with `Cache-Control: no-store`), including their `404`/`415`, because that is what OAuth clients parse — except `/oauth/authorize`'s pre-redirect responses, which are plain text because they are read by a human, not a client. The issuer, the resource identifier (`<issuer>/api/mcp`) and every endpoint URL are derived from `PUBLIC_URL`'s origin, never from the `Host` header. The two consent-page endpoints under `/api/oauth/*` are ordinary session endpoints with the normal error shape.

Body/query validation failures generally return `400 invalid_body`. Passwords must be at least 12 characters (`password_too_short` otherwise). Globally: any state-changing request (`POST`/`PUT`/`PATCH`/`DELETE`) that carries a body must set `Content-Type: application/json`, or the server rejects it with `415` before it reaches the route handler. Outside `/oauth/*` and `/.well-known/*` that is `415 unsupported_media_type`, and the exceptions are `POST /api/notes/:id/uploads` and `PUT /api/admin/auth/providers/:id/icon`, which require `multipart/form-data` instead (and reject `application/json` there with the same `415`). Under `/oauth/*` and `/.well-known/*` the `415` is in the OAuth form (`{error: "invalid_request", error_description}`), and the exception is `POST /oauth/token`, which requires `application/x-www-form-urlencoded` instead (see the OAuth rows).

**Note objects.** Note objects returned by `/api/notes` (`GET` and `POST`), `/api/notes/:ref`, `/api/notes/by-path/…`, `/api/notes/by-group-path/…`, `PATCH /api/notes/:id`, `POST /api/notes/:id/move` and `POST /api/notes/:id/copy` carry, besides the note's own fields: `ownerId` and `ownerHandle` (both `null` on a group note — a group note has no owner), `groupId` and `group: {id, name}` (both `null` on a personal note), your `role`, and `permissions` — seven booleans saying what you can do with this note: `read`; `edit`; `delete`; `manageShares` (the per-person sharing endpoints — only a personal note's owner); `managePublicLink` (the `public-link` endpoints); `changeSlug` (a `PATCH` carrying `slug` — if the same body also carries `title`, `edit` is needed as well); and `moveToGroup` (`POST /api/notes/:id/move` — only a personal note's owner).

**Roles and groups.** Your `role` on a personal note is `owner` or the role of a per-person share. On a group note it comes from your role in the group — `editor` if the role can edit, `viewer` if it can only read — and is never `owner`; `permissions` spells out what that role allows on this note. A group has two built-in roles — Admin, which allows everything on the group's notes except `manageShares` and `moveToGroup` and can't be changed, and Member, which starts out allowing `read` and `edit` on them and creating notes in the group — and any number of custom roles (see the `…/roles` rows above). Every role allows `read`; Member's and the custom roles' other flags are whatever the group set them to.

**Group endpoints.** On `/api/groups/:id…`, a `404 not_found` is byte-identical whether the id is malformed, the group doesn't exist, or you aren't a member (and aren't a site admin). A site admin can manage every group on these endpoints — members, roles and the group itself — whether or not they're a member; `GET /api/groups` still lists only groups they belong to, and a rename by a site admin who isn't a member reports `myRole: null` (with `canManageMembers`/`canManageGroup` true). A malformed `roleId` — in a body or in the path — answers `404 role_not_found`; so does a well-formed one that isn't in the group, once the body is valid. `409 builtin_role` means the request would change the built-in Admin role, rename the built-in Member role, or delete either. `409 role_name_taken` has two causes, which the response doesn't tell apart: another role in the group already has that name (ignoring case), or the name is a built-in role's display name. The body — including the name's length and display-name checks — is validated before the role is looked up, so a rename to one of those names answers `role_name_taken` whichever role it targets (either built-in role, or a well-formed `roleId` that isn't in the group), and a bad body answers `400` before an unknown well-formed `roleId` would answer `404 role_not_found`. On `DELETE /api/groups/:id`, `409 not_admin` means `transferTo` isn't someone the notes can go to — it isn't a user id, the person isn't a member, or their role isn't the built-in Admin role (a custom role with every permission doesn't count, and neither does being a site admin); the response doesn't tell these apart.

**Storage quotas.** Every personal space (a user's own notes) and every group has a storage plan; its limit (a plan can also have none) counts the bytes of the attachments stored in that space's notes. A note's attachments are every file uploaded to it or copied into it, whether or not its content still shows them: removing an image from a note doesn't free its space, which stays counted until the note is deleted (see [Known limitations](./known-limitations.md)). Note text, note versions, AI edit history and sign-in service icons don't count. An attachment counts against the space of the note it's in: uploading into someone else's note that's shared with you uses the owner's space, and a copy counts against the place it's copied into. An upload, a copy, a move into a group or a group transfer that would add attachment bytes to a space is refused with `409 storage_quota_exceeded` when the space's usage plus the new bytes would go over the limit (exactly reaching it is allowed); nothing that is already stored is ever deleted because of a plan, and moving or copying a note that has no attachments, or transferring a group that has none, is never refused for space. The response carries a top-level `storage` object: `incomingBytes` (the bytes this request would add, or `null` when the request was refused before they were measured) and, only if you can see that space's usage — it's your personal space, you can manage the group, or you're a site admin — `usedBytes` and `quotaBytes`. On a group transfer the space is the receiving admin's personal space, so only that person and site admins get the numbers.

**Note versions.** Every note has a numbered history of versions, each a full copy of its content (`/api/notes/:id/versions`). A version is saved automatically only when there is something new to save — the content differs from the version it is based on, or, for a note not based on any version, it has changed since the server last loaded the note and isn't empty — and then at these moments: while the note is open, once nobody has edited it for about 5 minutes; when everyone has left it; before an AI or API write (`POST /api/notes/:id/edits`, a revert, `POST /api/notes` with `content`, and the MCP `edit_note` and `create_note` tools); and after such a write has changed the content. `POST /api/notes/:id/versions` makes a manual version even when there is nothing new to save (see its row). A note saves versions automatically only while both the site-wide switch (`/api/admin/versions/settings`) and its space's switch are on — the owner's for a personal note (`PATCH /api/auth/profile`), the group's for a group note (`PATCH /api/groups/:id`); all of them are on by default. A note that is open when a switch changes keeps its previous behaviour until everyone has left it or it is moved to another space. Versions don't count towards storage plans. Copying a note doesn't copy its versions; moving a note into a group, or deleting a group by transferring its notes, clears their history and starts the numbering again from 1; deleting a note deletes its versions. Only people who can edit a note can see or use its versions, and only from a signed-in session (a Bearer token gets `401`).
