# API contract summary

All endpoints are served by the `app` container. Errors use the shape `{ "error": { "code": "...", "message": "..." } }` unless noted. `message` is an English sentence for people and may be reworded; scripts should check `code`. "Auth" = session cookie required; "Admin" = admin session required. Any `Auth`/`Admin` row can also return `401 unauthorized` (missing/invalid session) or, for `Admin` rows, `403 forbidden` (authenticated but not an admin) — these are omitted from the per-row status codes below for brevity.

A few endpoints also accept a Personal API token as `Authorization: Bearer knb_…` — those are marked `Auth / Token(scope)` (see [API tokens](./api-tokens.md)). On those endpoints a request carrying an `Authorization` header is authenticated only by that header and the session cookie is ignored; the two upload endpoints do the same with a transfer token instead (see their rows); the four bulk transfer endpoints take only a transfer token and never the cookie (see **Bulk transfer** below); everywhere else the header is ignored and the cookie is used. These endpoints expose note metadata, the folders you can see (`GET /api/folders`: their names and how they nest) and, through the `/content` and `/edits` rows below, note content — both reading it and writing it (writing needs `notes:write`) — and a note's comments (the comment rows below); see [AI editing](./ai-editing.md) for the fingerprints, the five write operations and revert. Token requests are rate-limited per user separately from browser sessions (300 reads/min, 60 writes/10 min by default; every figure in this document for the token-read, token-write, content-read, edit, search, upload, AI, bulk-download and bulk-write-back budgets is such a default, and a site admin can lower it in Site admin → Site limits, see `/api/admin/limits`); on top of that, `GET /api/notes/:id/content` and `GET /api/notes/:id/edits` share their own, tighter 120-reads-per-minute-per-user budget, and `POST /api/notes/:id/edits`, `POST /api/notes/:id/edits/:editId/revert` and `POST /api/notes` carrying `content` share a 30-writes-per-minute-per-user one (see their rows below; copying a note and saving, applying, renaming and deleting a note version, which are session-only, draw on it too — creating, renaming, moving and deleting folders and filing a note in a folder don't: they draw on a separate folder budget, `FOLDER_LIMIT`=600 per minute per user, and adding or removing a favorite draws on another of its own, `FAVORITE_LIMIT`; adding or removing a tag on a note, and managing a space's tags, draw on one of their own too, `TAG_LIMIT`), so a token calling them is really capped at 120/min and 30/min. Both tighter budgets are keyed by user and apply to browser sessions too — though in practice the web app never calls the content endpoints itself; it reads and writes note content through the live collaboration connection instead. The MCP tools draw on the same 120-reads-per-minute and 30-writes-per-minute budgets: `read_note_outline`, `read_note_section`, `read_note_image`, `read_comments`, `list_notifications` and `create_transfer_token` with `download` on the 120-reads-per-minute one, `edit_note` (except `rename`), `create_note` carrying `content`, `copy_note`, `delete_note` and `restore_note` on the 30-writes-per-minute one; `create_folder`, `rename_folder`, `move_folder`, `move_note_to_folder` and `delete_folder` on the folder budget; `post_comment` on the 60-writes-per-10-minutes token budget and, like posting or editing a comment over the API, on the comment budget, 30 per minute per user, shared with the web app. `list_notes`, `search_notes`, `list_trash`, `list_folders` and `open_notes_as_files` draw on neither; `search_notes` has its own budget, 60 searches per minute per user, which it shares with `GET /api/search` (browser sessions and tokens alike) and with `GET /api/knowledge/refs` (browser sessions only). Because one `POST /api/mcp` can carry several tool calls, these are counted **per tool call**, not per request (#108). The bulk transfer endpoints have budgets of their own (see **Bulk transfer** below). A runaway client cannot lock you out of the web UI, and invalid Bearer attempts are limited per IP (30/min). Endpoints that accept a token answer `401`/`403` with a `WWW-Authenticate: Bearer …` challenge (with `error="invalid_token"` / `error="insufficient_scope"` when a Bearer token was presented, and no `error` when no credentials or a non-Bearer scheme such as `Basic` were sent); the two upload endpoints answer a `401` to a request **carrying an `Authorization` header** with `WWW-Authenticate: Bearer realm="knotebook-transfer"` (with `error="invalid_token"` when a Bearer token was presented; without `error` for anything else, such as `Basic`), and without the header they answer like every other endpoint; the four bulk transfer endpoints answer every `401` with that same challenge, with or without the header (with `error="invalid_token"` when a Bearer token was presented); every other endpoint answers a plain `401 unauthorized` with no challenge. The challenge's `resource_metadata` always points at `/api/mcp` regardless of which endpoint was called — see [Known limitations](./known-limitations.md); the challenge of the upload and bulk transfer endpoints carries no `resource_metadata`. There are four scopes: `notes:read`, `notes:write` (which includes read), `notes:move` and `notes:delete` (each of the last two comes only with `notes:write`, and they are independent of each other); a credential holds one of `notes:read`, `notes:read notes:write`, `notes:read notes:write notes:move`, `notes:read notes:write notes:delete` or `notes:read notes:write notes:move notes:delete`. Tokens are issued only by this server (no external identity providers), can never mint a collaboration token (`POST /api/notes/:id/collab-token` is session-only) nor rename an agent or change a credential's scope (`PATCH /api/auth/tokens/:id`, like the rest of `/api/auth/tokens`, is session-only), and revoking one deletes it outright.

Besides personal tokens, an MCP client can obtain its own credential through the built-in **OAuth 2.1 authorization server** (`/.well-known/*`, `/oauth/*` — see the OAuth rows below and [API tokens](./api-tokens.md)). Besides those endpoints, every error body on this server is the `{error:{code,message}}` shape — with `/api/mcp` as a partial exception: everything its HTTP layer rejects (`401`, `403`, `413`, `429`, a `415` from the content-type guard, and a malformed or empty body's `400`) uses the normal shape, while its `405` on `GET`/`DELETE`, the MCP transport's own answers (a `415` when no `Content-Type` was sent at all, a `406` when `Accept` is missing `text/event-stream`) and every tool-level error are JSON-RPC. The OAuth endpoints answer in the RFC 6749 §5.2 / RFC 7591 form `{error, error_description}` (with `Cache-Control: no-store`), including their `404`/`415`, because that is what OAuth clients parse — except `/oauth/authorize`'s pre-redirect responses, which are plain text because they are read by a human, not a client. The issuer, the resource identifier (`<issuer>/api/mcp`) and every endpoint URL are derived from `PUBLIC_URL`'s origin, never from the `Host` header. The two consent-page endpoints under `/api/oauth/*` are ordinary session endpoints with the normal error shape.

Body/query validation failures generally return `400 invalid_body`. Passwords must be at least 12 characters (`password_too_short` otherwise). Globally: any state-changing request (`POST`/`PUT`/`PATCH`/`DELETE`) that carries a body must set `Content-Type: application/json`, or the server rejects it with `415` before it reaches the route handler. Outside `/oauth/*` and `/.well-known/*` that is `415 unsupported_media_type`, and the exceptions are `POST /api/notes/:id/uploads` and `PUT /api/admin/auth/providers/:id/icon`, which require `multipart/form-data` instead (and reject `application/json` there with the same `415`), and `PUT /api/transfer/notes`, which requires `text/markdown` (and rejects anything else with the same `415`). Under `/oauth/*` and `/.well-known/*` the `415` is in the OAuth form (`{error: "invalid_request", error_description}`), and the exception is `POST /oauth/token`, which requires `application/x-www-form-urlencoded` instead (see the OAuth rows).

**Note objects.** Note objects returned by `/api/notes` (`GET` and `POST`), `/api/notes/:ref`, `/api/notes/by-path/…`, `/api/notes/by-group-path/…`, `PATCH /api/notes/:id`, `POST /api/notes/:id/move`, `POST /api/notes/:id/copy` and `PUT /api/notes/:id/folder` carry, besides the note's own fields: `ownerId` and `ownerHandle` (both `null` on a group note — a group note has no owner), `groupId` and `group: {id, name}` (both `null` on a personal note), your `role`, and `permissions` — seven booleans saying what you can do with this note: `read`; `edit`; `delete` (moves the note to the trash); `manageShares` (the per-person sharing endpoints — only a personal note's owner); `managePublicLink` (the `public-link` endpoints); `changeSlug` (a `PATCH` carrying `slug` — if the same body also carries `title`, `edit` is needed as well); and `moveToGroup` (`POST /api/notes/:id/move` — only a personal note's owner). They also carry `folderId`, the folder the note is in as you see it (`null` = the top level): for your own notes and group notes, the folder it is in; for a note someone else shared with you, the folder you filed it in yourself with `PUT /api/notes/:id/folder` — the owner's folders are never shown to you. `GET /api/notes` also gives each note `sizeBytes`: the bytes of the note's stored editing state plus all of its attachments (every file counted as in **Storage quotas** below). The editing state also keeps traces of earlier edits, so a short note that has been edited a lot can come out larger than its text suggests. `GET /api/notes` also gives each note `tags`: `[{id, name, color}]` in the order the tags were added, `[]` for a note without tags (a note shared with you shows its owner's tags); the single-note endpoints don't carry it. `GET /api/notes` also gives each note `hasKnowledge`: `true` when the note has knowledge entries in the knowledge index (see `GET /api/knowledge/index/me`), `false` otherwise; the single-note endpoints and search results don't carry it.

**Roles and groups.** Your `role` on a personal note is `owner` or the role of a per-person share. On a group note it comes from your role in the group — `editor` if the role can edit, `viewer` if it can only read — and is never `owner`; `permissions` spells out what that role allows on this note. A group has two built-in roles — Admin, which allows everything on the group's notes except `manageShares` and `moveToGroup` and can't be changed, and Member, which starts out allowing `read` and `edit` on them and creating notes in the group — and any number of custom roles (see the `…/roles` rows above). Every role allows `read`; Member's and the custom roles' other flags are whatever the group set them to.

**Group endpoints.** On `/api/groups/:id…`, a `404 not_found` is byte-identical whether the id is malformed, the group doesn't exist, or you aren't a member (and aren't a site admin). A site admin can manage every group on these endpoints — members, roles and the group itself — whether or not they're a member; `GET /api/groups` still lists only groups they belong to, and a rename by a site admin who isn't a member reports `myRole: null` (with `canManageMembers`/`canManageGroup` true). A malformed `roleId` — in a body or in the path — answers `404 role_not_found`; so does a well-formed one that isn't in the group, once the body is valid. `409 builtin_role` means the request would change the built-in Admin role, rename the built-in Member role, or delete either. `409 role_name_taken` has two causes, which the response doesn't tell apart: another role in the group already has that name (ignoring case), or the name is a built-in role's display name. The body — including the name's length and display-name checks — is validated before the role is looked up, so a rename to one of those names answers `role_name_taken` whichever role it targets (either built-in role, or a well-formed `roleId` that isn't in the group), and a bad body answers `400` before an unknown well-formed `roleId` would answer `404 role_not_found`. On `DELETE /api/groups/:id`, `409 not_admin` means `transferTo` isn't someone the notes can go to — it isn't a user id, the person isn't a member, or their role isn't the built-in Admin role (a custom role with every permission doesn't count, and neither does being a site admin); the response doesn't tell these apart.

**Storage quotas.** Every personal space (a user's own notes) and every group has a storage plan; its limit (a plan can also have none) counts the bytes of the attachments stored in that space's notes and, in a personal space, of the owner's profile pictures — the original file and the display image of every candidate, not only the one in use (a group has no profile pictures). A note's attachments are every file uploaded to it or copied into it, whether or not its content still shows them: removing an image from a note doesn't free its space, which stays counted until the note is permanently deleted — moving it to the trash doesn't free it (see [Known limitations](./known-limitations.md)). Note text, note versions, AI edit history and sign-in service icons don't count toward the limit. The size of a space's note content and of its versions and automatic backups (AI edit history left out) is reported separately, for display only: as `content` by `GET /api/storage` and `GET /api/groups/:id/storage`, and as `contentBytes` in the admin users and groups lists. It includes notes in the trash and is the recorded size, not disk usage. An attachment counts against the space of the note it's in: uploading into someone else's note that's shared with you uses the owner's space, and a copy counts against the place it's copied into. An upload, a copy, a move into a group or a group transfer that would add attachment bytes to a space is refused with `409 storage_quota_exceeded` when the space's usage plus the new bytes would go over the limit (exactly reaching it is allowed); nothing that is already stored is ever deleted because of a plan, and moving or copying a note that has no attachments, or transferring a group that has none, is never refused for space. A profile picture upload is refused the same way when the original plus the display image don't fit; a re-crop is refused only when its new display image is larger than the old one and the difference doesn't fit, so a space that is full can still re-crop to a smaller image; deleting a profile picture gives its bytes back. The response carries a top-level `storage` object: `incomingBytes` (the bytes this request would add, or `null` when the request was refused before they were measured) and, only if you can see that space's usage — it's your personal space, you can manage the group, or you're a site admin — `usedBytes` and `quotaBytes`. On a group transfer the space is the receiving admin's personal space, so only that person and site admins get the numbers.

**Profile pictures.** Each person has a list of candidate pictures and at most one is in use. The user object's `avatar` is `{id, v, pending}` for the one in use, or `null`. A picture's address is built from `id` and `v` only: `/api/avatars/<id>?v=<v>`; `v` is the picture's version and goes up each time its display image changes, so an address that carries the current `v` can be cached for a year. `pending` is true while the picture has no display image yet; until then only its owner can read it. The original file is kept in the server's uploads directory and isn't an attachment: it can't be read through `/api/uploads/:id` and deleting notes or emptying the trash doesn't touch it; the display image is kept in the database. These endpoints take the session cookie only: a request with just an API token or a transfer token gets `401 unauthorized`. Apart from `GET /api/avatars/:id`, they act on your own candidates, and a candidate that belongs to someone else, doesn't exist or has an id that isn't a UUID gets the same `404 not_found` (on `PUT /api/auth/avatar`, a `candidateId` that isn't a UUID is `400 invalid_body` instead). Other people's pictures appear in lists as an `avatar` field, `{id, v}` or `null`, built the same way (`/api/avatars/<id>?v=<v>`) and without `pending`: group members (`GET`, `PUT` and `PATCH` on `/api/groups/:id/members…`), a note's shares (`GET` and `PUT` on `/api/notes/:id/shares`), user suggestions, the site admin's user list (`GET /api/admin/users` and `PATCH …/storage-plan`), the `editors` of a note's versions, and the entries of `GET /api/notes/:id/edits`. It is `null` when the person has no picture in use, and also while the picture in use has no display image yet (nobody else can read it until it has one). A picture's `v` goes up when its display image changes, so an `avatar` you have read earlier can be out of date until you read the list again. The version and edit entries carry the picture of the account itself, also for a write made through a token. The `avatar` references are returned to an API token on `GET /api/notes/:id/edits` (scope `notes:read`), but the image address stays session-cookie-only, so a token can't fetch the picture.

**Note versions.** Every note has a numbered history of versions, each a full copy of its content (`/api/notes/:id/versions`). A version is saved automatically only when there is something new to save — the content differs from the version it is based on, or, for a note not based on any version, it isn't empty and has changed since the server loaded the note (for changes already waiting to be saved: since the load during which the first of them was made) — and then only once the note's content has gone `autoWaitMinutes` minutes (`/api/admin/versions/settings`, 5 by default) without a new change, whoever made the changes — a person in the editor, or an AI or API write (`POST /api/notes/:id/edits`, a revert, `POST /api/notes` with `content`, and the MCP `edit_note` and `create_note` tools); changes from several people and assistants within that quiet stretch go into one version. The server checks for such notes every 30 seconds, up to 100 at a time, so the version appears within about half a minute after that. Leaving a note doesn't save a version, and neither does an AI or API write by itself. Block and inline attributes that merely restate the editor's defaults (for example a paragraph aligned left) do not count as a difference. `POST /api/notes/:id/versions` makes a manual version even when there is nothing new to save (see its row). A note saves versions automatically only while both the site-wide switch (`/api/admin/versions/settings`) and its space's switch are on — the owner's for a personal note (`PATCH /api/auth/profile`), the group's for a group note (`PATCH /api/groups/:id`); all of them are on by default. A note that is open when a switch changes keeps its previous behaviour until everyone has left it or it is moved to another space. Versions don't count towards storage plans; their size is reported as part of `content` (see **Storage quotas**). Copying a note doesn't copy its versions; moving a note into a group clears its history (and its comments) and starts the numbering again from 1 unless the request sets `keepHistory: true` (then the versions, their numbering and the comments stay), and deleting a group by transferring its notes always clears their history and starts the numbering again from 1; permanently deleting a note (from the trash) deletes its versions. Only people who can edit a note can see or use its versions, and only from a signed-in session (a Bearer token gets `401`).

**Trash.** Deleting a note (`DELETE /api/notes/:id`, or MCP's `delete_note`) moves it to the trash. Who can see a note in the trash — and so restore it or permanently delete it — is narrower than who can see the note: for a personal note only its owner, for a group note the members whose role can both edit and delete notes (a role that can delete but not edit can move a group note to the trash, but not see it there). Site admins have no special access. To anyone else, `GET /api/trash`, `POST /api/trash/restore` and `POST /api/trash/purge`, and MCP's `list_trash` and `restore_note`, treat a note in the trash exactly like a note that doesn't exist. While a note is in the trash it is left out of `GET /api/notes`, search and wikilink suggestions; links from it don't appear among other notes' backlinks; every endpoint for the note answers as it does for a note you can't see — mostly `404 not_found`, and `404 in_trash` (with the note's id as `noteId`) from `GET /api/notes/:ref` and the two `by-path` rows to people who can restore it; the MCP tools other than `list_trash` and `restore_note` answer as for a note that doesn't exist; its public link (both forms, and their images) answers like a link that doesn't exist; and `GET /api/uploads/:id` answers `403 forbidden` for its attachments, the same as for an upload you can't see. Its attachments still count toward storage, and its address and custom public URL stay taken (see [Known limitations](./known-limitations.md)). Restoring it brings all of that back as it was, its shares and public link included — unless its group was deleted with `mode: "transfer"` while it was in the trash, which changes its owner and address and removes its public link (see the sentence on `mode: "transfer"` below). Only a note in the trash can be permanently deleted — with `POST /api/trash/purge`, or automatically once it has been there longer than the site's retention period (`/api/admin/trash/settings`). Deleting a group with `mode: "delete"` permanently deletes all of its notes, including those in its trash, without moving them to the trash; with `mode: "transfer"`, the group's notes in the trash become the receiving admin's personal notes and stay in the trash — that person's — with their original deletion time (and, like every transferred note, without a public link). A note in the trash stays in its folder until that folder is deleted, and then keeps the folder's path as it was at that moment; `folderPath` in `GET /api/trash` shows the folder's current path in the first case and the kept one in the second. Restoring a note puts it back in its folder. If the folder has been deleted, the folders of the kept path are found or created again, from the top level down, in the note's space: a folder already there with the same name (ignoring case) is used, so notes from the same deleted folder end up together again; the folder limits (see **Folders**) don't apply here; and only folders on a restored note's path come back. In the rare case that a group is transferred while a restore of one of its notes whose folder was deleted is being processed, that note — if you can still restore it — is restored at the top level of the receiving person's notes instead, and its kept path is dropped.

**Folders.** Notes can be filed in folders (`/api/folders`, `PUT /api/notes/:id/folder`). There are three kinds of space, each with its own folders: your notes (`space.kind` `"personal"`), notes shared with you (`"shared"`) and each group (`"group"`). Your folders in your notes and in notes shared with you are seen only by you; a group's folders by every member of the group (every role can read notes). Site admins have no special access. A folder you can't see answers exactly like one that doesn't exist — `404 folder_not_found`, also for a malformed id. What you can do is in the folder object's `permissions`:

- **Your notes**: everything (`manage`, `deleteNotes` and `createNote` are all `true`).
- **Notes shared with you**: your folders there hold the notes other people shared with you (as editor or viewer); you can create, rename, move and delete them and file those notes in them (`manage` and `deleteNotes` are `true`), but not create notes in them (`createNote` is `false`). Where you file a shared note is yours alone; the owner's folders and yours are separate.
- **A group**: a role that can edit notes can create, rename, move and delete the group's folders and file the group's notes in them (`manage`). Deleting a folder that still has notes outside the trash also needs a role that can delete notes (`deleteNotes`); without it the whole request is refused. Creating a note in a group folder, or copying or moving one into it, needs a role that can both create and edit notes (`createNote`).

A folder's name is trimmed and normalized to Unicode NFC, then must be 1 to `FOLDER_NAME_MAX`=80 characters counted in Unicode code points, with no line break, tab or other control character (including U+2028/U+2029 and the bidirectional-text controls), NUL or unpaired surrogate; otherwise the answer is `400 invalid_body`. Within the same parent folder, or among the top-level folders of a space, names are unique ignoring letter case (`409 folder_name_taken`) — for letters outside ASCII, as far as the database's locale treats them as upper and lower case of each other. Folders nest up to `FOLDER_DEPTH_MAX`=5 levels, a top-level folder being level 1: creating or moving a folder deeper is `409 folder_too_deep`, and moving a folder into itself or one of its own folders is `409 folder_cycle`. Each space holds at most `FOLDERS_PER_SPACE_MAX`=1000 folders (`409 folder_limit`). The depth is checked only when you create or move a folder, and the count only when you create one: restoring from the trash (see **Trash**) and transferring a group can make a tree deeper or a space hold more, and renaming in such a tree still works. Creating, renaming and moving folders, and filing notes in them, don't change any note's address, `updatedAt`, versions, sharing or who can see it.

When a group is deleted with `mode: "transfer"` and it has folders — or notes in its trash whose folder was deleted — a new top-level folder is created in the receiving person's notes and the group's folders, with the notes in them, and the group's top-level notes all go into it; notes in the trash keep their paths inside it. The new folder is named after the group: the group's name without control characters, normalized to NFC and trimmed, and cut so it fits within 80 characters with a suffix; if nothing is left, `群組` when the `Accept-Language` of the request deleting the group starts with `zh`, otherwise `Group`; if a top-level folder of that name (ignoring case) is already there, ` (2)`, ` (3)` … is added. A group with neither gets no such folder, and its notes land at the top level of that person's notes. With `mode: "delete"`, the group's folders are deleted with it.

Wherever a request names a folder, whether you can see it (`404 folder_not_found`) is checked before whether it's in the right space (`400 folder_cross_space`), and both before any `403 forbidden` or `409` about the folder; the body is checked first, and the note in the path — including a `403 forbidden` about the note — before the folder. The folder error codes:

| Code | Status | Meaning |
|---|---|---|
| `folder_not_found` | 404 | The folder id is malformed, no such folder, or you can't see it. |
| `folder_cross_space` | 400 | You can see the folder, but it's in another space than the request needs. |
| `folder_delete_blocked` | 403 | The folder has notes outside the trash that you can't delete. |
| `folder_name_taken` | 409 | A folder with that name, ignoring case, is already there. |
| `folder_too_deep` | 409 | The folder would be deeper than `FOLDER_DEPTH_MAX` levels. |
| `folder_cycle` | 409 | A folder can't be moved into itself or one of its own folders. |
| `folder_limit` | 409 | The space already has `FOLDERS_PER_SPACE_MAX` folders. |
| `folder_not_empty` | 409 | Only from `DELETE /api/folders/:id` with `onlyIfEmpty: true`: the folder has a folder in it or, in your notes or a group, notes outside the trash in it, or, in notes shared with you, notes filed in it. |

**Bulk transfer.** The MCP tool `open_notes_as_files` issues a transfer token (`knbt_…`) for downloading notes as markdown files and sending changed files back; the four `/api/transfer/*` rows above are the endpoints its `curl` commands call, and [MCP](./mcp.md) describes the download, the files and what sending one back does. These endpoints exist only on a deployment with the collaboration component. They take only such a token, as `Authorization: Bearer knbt_…` — never the session cookie, and not an API token or an upload or download transfer token. Each request checks again your account, the scope the token's credential has at that moment, and what you can see at that moment. A `PUT` is checked for `Content-Type` and `Origin` before the token is looked at.

- No `Authorization` header: `401`, message `A transfer token is required.`; it doesn't count against the per-IP limit on invalid Bearer attempts.
- An API token (`knb_…`): `401`, message `This endpoint doesn't accept API tokens. Get a transfer token from the MCP tool open_notes_as_files.`
- A token that is malformed, unknown, expired or revoked, whose credential was revoked or has expired, or whose account is disabled or has to change its password: `401`, message `The transfer token is invalid, expired or revoked. Get a new one from the MCP tool open_notes_as_files.` A scheme other than Bearer gets `401` too, with message `Not signed in.`
- An upload or download token from `create_transfer_token`: `403 forbidden`, message `This transfer token can't be used for this action.`
- `PUT` with a token whose `access` is `read`, or whose credential no longer has `notes:write`: `403 insufficient_scope`, message `This token's scope doesn't allow this action.`
- Every `401` to a request that carries an `Authorization` header counts against the per-IP limit on invalid Bearer attempts (30 per minute); once it is used up, the answer is `429` with `Retry-After` and no challenge.

`PUT /api/transfer/notes` reads the body as a file. A UTF-8 byte order mark and `\r\n` line endings are accepted. The file has front matter when it starts with a `---` line and, within its first 200 lines, has another line that is exactly `---` with a line starting `knotebook`, `id` or `base` followed by `:` (spaces or tabs before the `:` are allowed) between the two; a file that starts with a `---` line and has such a line within its first 200 lines, but no closing `---` line among them, is refused with `400 invalid_body`; otherwise the whole file is the new note's text. In the front matter only `id`, `base`, `title`, `folder_id` and `tags` are read, each named up to its line's first `:` without the spaces or tabs before it, and other lines are ignored. A value that starts with `"` is read as a JSON string, one in single quotes as a YAML single-quoted string, and anything else as it stands, without the spaces around it. A file with an `id` must also have a `base` (16 lowercase hex characters); front matter with a `base` but no `id` is refused with `400 invalid_body`; a file without either creates a new note. With no `title` line, the title doesn't change (a new note is called `Untitled`). A `tags` line is a JSON array of strings: a file whose `tags` differ from the copy's sets the note's tags (a name the note's space doesn't have yet is created), a file with no `tags` line leaves them alone, and `tags: []` removes them all; the rules are under *Sending a file back* in [MCP](./mcp.md#sending-a-file-back). The reply to a file written back is `200 {id, created: false, result, applied, same, editIds, renamed, renameFailed?, tagsChanged, tagsFailed?, knowledge?, unboundWikilinks, base: null}` (`result` is `unchanged`, `renamed`, `tagged` when only the tags changed, or `applied`); to a new note, `201 {id, created: true, result: "created", base: null, knowledge?, unboundWikilinks}`; to an identical new-note file sent again within 30 minutes, `200 {id, created: false, result: "unchanged", base: null}` (see [MCP](./mcp.md) for what each field means).

Every `429` from these four endpoints carries `Retry-After`, in seconds, at least 1. The budgets: a download counts against 10 per user per hour by default, and only one download runs on the whole site at a time; fetching one note counts against the 120-reads-per-minute content-read budget; a file whose text, title or tags differ from the copy it was downloaded as, or that creates a note, counts against 30 per user per minute by default (`TRANSFER_WRITE_LIMIT`), which is separate from every other write budget; and a file that changes nothing counts against the 300-reads-per-minute token budget. A file whose text differs counts against the 30 before the server parses that text, so it counts even when it is then refused with a `400` for what the text contains; one that turns out to change nothing (it only adds blank lines, for example) is given back and counts against the token budget instead. So once the 30 are used up, every file whose text, title or tags differ, or that creates a note, answers `429` — even one that would change nothing — unless a check made before the budget refuses it first (for example `409 base_unavailable` with `note_changed`, `409 not_mergeable`, `403` or `404`); a file the same as its downloaded copy still answers `unchanged`, and a new-note file identical to one that created a note in the last 30 minutes still returns that note.
