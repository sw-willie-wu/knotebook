# Knowledge info

Facts a heading carries about what it says: when to read it, a conclusion, a basis, when it was last verified and its status. Part of [Known limitations](../known-limitations.md); how it works is in [Knowledge info](../knowledge.md).

- **Turning a knowledge heading into a paragraph, or merging it into the paragraph above, removes its knowledge info.** **Undo** brings it back; nothing else does.
- **Pressing Backspace at the very start of a knowledge heading turns it into a paragraph, and its knowledge info goes with it.** **Undo** brings it back. (Enter at the start doesn't do this: it adds an empty paragraph above the heading.)
- **Public pages and presentations show no knowledge info.** The server removes it before it sends the note to a public link, and the presentation mode doesn't show it either.
- **Knowledge info can only be added to a heading at the top level of a note.** A heading inside a column, a list or a quote can't carry it. When a knowledge heading is moved into one of them, its info stays in the note but isn't shown; moving the heading back to the top level shows it again.
- **A phone has no drag handle, so the way in is `/info` or the icon.** The `⋮` menu has no entry for it.
- **Tab indents a block in an editable note, so you can't Tab from the text to a status icon while you type.** To open the form from the keyboard, use `/info`. Tab in the first block of a note moves the focus out of the editor, and Tab in a knowledge heading indents it, which takes it off the top level: its icon is no longer shown, and the info stays in the note until the heading is moved back.
- **A heading you change in the previous version loses its knowledge info after you go back to it.** The previous version doesn't show knowledge info and drops it from any heading you change there (typing in it, moving it, changing its level or color); headings you don't touch, including ones where you only edit the paragraphs below, keep theirs, and it comes back after upgrading again. See [Self-hosting](../self-hosting.md#upgrading-and-rolling-back).
- **After a change that only turns the heading's text italic or into inline code, the icon can sit a little off for a moment.** The icon is placed when the heading's text, or the size or order of the blocks, changes; a change to the look of the letters alone doesn't trigger that, so it catches up the next time something does, such as typing in the heading or resizing the window.
- **While it is faded, the status icon has a lower contrast than 3:1 against the page.** The icon is faded until you point at it or focus it, so that a note full of knowledge stays calm; pointing at it or focusing it shows it at full strength, and on a screen with no hover it is always faded. The state is also in the icon's name, which screen readers read.
- **In a very large note, typing in a heading is slower.** Every change to a heading works out the knowledge info of the whole note again, so the cost grows with the number of knowledge headings: with several thousand of them, each letter typed in a heading can take tens of milliseconds longer. Typing in a paragraph isn't slowed by your own keystrokes, but each change a collaborator makes arrives as an update that works out the info again, wherever in the note it lands.
- **A very large note is slower to open as a public page if its headings were added or edited after this version, or its text mentions the word "knowledge".** The server then decodes the document, takes the info off and encodes it again on every view; nothing is kept between views.
- **A card that is open while someone else changes the info keeps what it showed when it opened.** Pointing at the icon again shows the new values.
- **If the window crosses the phone width while the form is open, what you had typed and not saved is lost.** On a phone the form is a bottom sheet instead of a card; resizing a window, or turning a tablet, across that width opens the other one with the saved values.
- **A heading can only be marked as replaced by a knowledge heading of the same note.** The list holds all of that note's knowledge headings, outdated ones included, so one can be marked as replaced by another that is itself outdated.
- **The last verified date can be a date in the future.** Only a date that doesn't exist, such as 31 February, is refused.
- **A colored collapsible knowledge heading reads without its comment.** It is read as a block of HTML, which has no place for the comment. Rewriting the part it is in, with `edit_note` or a file, removes its knowledge info, and the reply lists it in `knowledge.removed`.
- **A knowledge heading with no text reads as `## ` and comes back as a paragraph.** The markdown parser doesn't read a heading with no text as a heading, so rewriting the part it is in leaves a paragraph that holds `##`, and the knowledge info goes with the heading.
- **The rule that keeps the knowledge info of a heading sent without a comment goes by level and text only.** A heading whose text you changed needs a comment of its own. When the part a write replaces has several headings with the same level and text, the info can end up on a different one of them than the one it was on, for example when an earlier one is removed in the same write.
- **A write whose markdown has a `<plaintext>` tag ignores every knowledge comment in it, the ones before the tag too.** The reply counts them in `ignoredComments`.
- **Stored knowledge info that wouldn't pass today's checks is written back as it is, until you change it.** That covers a state left by two people editing at once, such as an outdated heading with no replacement, and a value stored before a check existed. Changing any of its six values applies the checks.
- **Knowledge info with a NUL character or an unpaired surrogate in a value can be read but not written back.** Only the collaboration editor can store such a value; a write that carries it is refused with `invalid_knowledge`.
- **A `superseded_by` with a space at either end is refused once any value of that knowledge is changed.** Written back unchanged, it is accepted. Only the collaboration editor can store one; the web form removes the spaces.
- **A write doesn't repair what is already wrong in the note.** A knowledge id that two headings already shared is left as it is (only an id a write adds is renumbered when it repeats), and a heading whose stored knowledge id is a temporary `k_new:…` one is left as it is.
- **The `knowledge` lists in an `edit_note` or `create_note` reply have a size budget.** A list that goes over it is cut and the reply carries `truncated: true`; the REST and file replies aren't cut.
