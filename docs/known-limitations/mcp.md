# AI assistants over MCP

What an assistant can reach, prompt injection, transfer tokens and paging through live data. Part of [Known limitations](../known-limitations.md).

- **An assistant tricked by a prompt injection can send your notes' images off-site.** `create_transfer_token` puts a short-lived token in the assistant's context, its shell commands and the client's transcript. An assistant steered by instructions hidden in content it reads (for example a note someone shared with you) can ask for a download token for every note it can read and send the images' bytes anywhere — a path that did not exist before, when an API token or app credential could not fetch a note's images at all. It can also fill notes it can edit with uploads: at most 5 unused upload tokens per credential at once, and up to the 60-per-10-minutes token write budget — with the default limits, about 600 MiB of 10 MiB files every 10 minutes (a site admin can lower the budget and the upload size limit). Uploads work in the other direction too: it can put image files from your machine, such as screenshots, into a note other people can read (for example a group note, or one someone shared with you as an editor) — through your Knotebook address, which you have probably let it reach with `curl`. Short lifetimes, one note per token, keeping the token out of URLs and Claude Code's prompt before it runs a shell command limit this; none of them prevents it (#200).
- **An assistant tricked by a prompt injection can move your personal notes into a group, or copy notes into one.** This needs the `notes:move` scope: an MCP client whose token or app credential has it gets `move_note_to_group`, and can pass `group_id` to `copy_note`. A credential only gets `notes:move` when you ask for it — by turning on **Move to groups (can't be undone)** when you create a token or later on its row in **Settings → Authorization**, by ticking it on the consent page, or through `POST`/`PATCH /api/auth/tokens` — and no credential gets it automatically, including those issued before it existed. Moving hands a private note to everyone in the group and removes its per-person shares and public link, which don't come back, and also its version history unless the call passes `keep_history: true` (then the group's editors see the versions and who edited them), and a single note can't be moved back out. Copying can put the content of a note someone shared with you into one of your groups, where the members who can read the group's notes see it. This is what **Move to…** and **Copy to…** do in the web app — the tools can also move or copy into a group where your role can create notes but not edit them — except that no one has to click. Mitigations: leave `notes:move` off unless a program really needs it — a credential without it doesn't have `move_note_to_group`, and its `copy_note` refuses `group_id` with `insufficient_scope`; Claude Code asks before a tool call unless you've allowed the tool or turned prompts off — that is not a defense. `notes:move` covers handing over an existing note and copying a whole note into a group, not writing into a group's notes: a `notes:write` credential can still put what it has read into a group's notes — for example with MCP's `create_note` (with `group_id`) and `edit_note`, or the REST `POST /api/notes` (with `groupId`) and `POST /api/notes/:id/edits` (#180, #239).
- **An assistant tricked by a prompt injection can move your notes to the trash.** This needs the `notes:delete` scope: an MCP client whose token or app credential has it gets `delete_note`, `restore_note` and `delete_folder`. A credential only gets `notes:delete` when you ask for it — by turning on **Move to trash (can be restored)** when you create a token or later on its row in **Settings → Authorization**, by ticking it on the consent page, or through `POST`/`PATCH /api/auth/tokens` — and no credential gets it automatically, including those issued before it existed. It can move any note your account could move to the trash in the web app: your own personal notes, and the notes of groups where your role can delete notes. While a note is in the trash, someone who can restore it can bring it back, in the web app or with `restore_note`; but it is deleted permanently once it is due under the site's trash setting — the shorter the retention period, the less time there is to notice — unless the site is set not to empty the trash on its own, and someone can delete it permanently sooner in the web app. A group note can only be brought back by a member whose role can both edit and delete notes, so if your role can delete but not edit, neither you nor the assistant can see or restore the group notes it moved there. No MCP tool deletes a note permanently or empties the trash. Mitigations: leave `notes:delete` off unless a program really needs it — a credential without it doesn't have `delete_note`, `restore_note` or `delete_folder`; Claude Code asks before a tool call unless you've allowed the tool or turned prompts off — that is not a defense (#181).
- **An assistant tricked by a prompt injection can delete your folders, or rearrange them.** With the `notes:delete` scope, one `delete_folder` call deletes a folder and every folder inside it and moves every note in them that isn't in the trash yet to the trash, all at once — in your personal folders, and in a group's folders when your role there can edit and delete notes (in your folders for notes shared with you, it only removes the folders). Those notes can be brought back while they are in the trash, re-creating the folders on the way to each one, as in the "Undoing a folder deletion…" entry in [Folders](./folders.md); folders that held no notes don't come back. Without `notes:delete`, a credential with `notes:write` can't delete folders, but it can create, rename and move them and file notes in them (`create_folder`, `rename_folder`, `move_folder`, `move_note_to_folder`) — and in a group where your role can edit notes, every member who can read the group's notes sees those folders, names included. Mitigations: leave `notes:delete` off unless a program really needs it, and `notes:write` too when it only has to read; Claude Code asks before a tool call unless you've allowed the tool or turned prompts off — that is not a defense.
- **`read_note_image` shows an image only if you can read the note it was uploaded to.** It needs read access to the `note_id` you pass and to the note the image belongs to — the same rule as fetching `/api/uploads/<id>` in the browser — so an image block copied from another note shows only if you can read that note. An image written with an external URL can't be read through it (#200).
- **A file uploaded but never written into a note is still an attachment.** An upload made with a transfer token that `edit_note` never references — or whose reference is later removed — keeps its file and its `uploads` row until the note it belongs to is permanently deleted, and its size counts toward that note's storage space (see "Removing an image from a note doesn't free its space"). A transfer-token upload that fails after the server has started reading the file (`413`, `415`, `400`, or a `409` — `storage_quota_exceeded` because the file doesn't fit, or `server_busy`) still uses the token up (#200).
- **The `curl` commands `create_transfer_token` and `open_notes_as_files` return are built from `PUBLIC_URL`.** If `PUBLIC_URL` doesn't match the address the assistant can reach, its uploads and downloads, and the files it sends back, go to the wrong place — the same family as "A wrong `PUBLIC_URL` makes MCP requests that carry an `Origin` header answer `403`" (#200).
- **On a plain-http `PUBLIC_URL` (for example a LAN deployment), transfer tokens cross the network unencrypted,** exactly as API tokens do there (#200).
- **An MCP connection made with the browser's sign-in session has no `create_transfer_token` or `open_notes_as_files`.** The tools need a token or app credential to tie their transfer tokens to; the web app uploads and shows images with its own session instead (#200).
- **A per-minute read limit is not a per-turn context budget.** MCP reads are capped per call — 4000 characters of section text, 100 sections, 100 notes, 200 characters of heading (as written in JSON) — and per minute, at 120 content reads per user by default. Nothing caps the total: an assistant that keeps calling can pull roughly 480 000 characters of note text a minute (or, on a note built entirely of headings, considerably more heading text than that). If that matters for your deployment, the lever is the credential's scope, what is shared with the account and which groups it belongs to, not the rate limit (#108).
- **Notes other people shared with you, and your groups' notes, end up in your assistant's context.** `list_notes` and `search_notes` return everything your account can read, which includes notes shared with you and the notes of your groups; `search_notes` also hands over excerpts of their body text, and `read_note_section` will hand their text to whatever model is driving the client. A credential's reach is your reach — there is no per-note or per-owner scope. Each result carries `owner` and `role` so a well-behaved client can tell whose content it is looking at, but nothing enforces that it does (#108).
- **There is no cross-note view of what an assistant changed.** The **AI edit history** is per note: to review a run of edits across several notes you have to open each one. The closest thing to an overview is the `lastEdited` that comes back with every `list_notes` result: it names the account that touched each note last and, when the write came from a credential rather than a browser session, the agent name it came under (#108).
- **A wrong `PUBLIC_URL` makes MCP requests that carry an `Origin` header answer `403`.** The endpoint's DNS-rebinding guard compares both the request's `Origin` and its `Host` against the host in `PUBLIC_URL`, never against each other — comparing two values that both come from the request would guard nothing. Behind a reverse proxy the `Host` side depends on `TRUST_PROXY` being set correctly too. Command-line MCP clients normally send no `Origin` and are unaffected, so this shows up as "it works from the terminal but not from that one client", answered with a `403` whose body does not mention `PUBLIC_URL` (#108).
- **A client's cached tool list does not shrink on its own.** The set of tools is decided per request from the credential's scope, but `tools.listChanged` is `false` — the server is stateless and has no channel to push a change — so a client that connected with a `notes:write` credential keeps showing the writing tools after you revoke it and switch to a read-only one. Calling one then gets an explanatory "tool not found" result rather than a permission error. Restarting the client refreshes the list (#108). The same goes for changing a credential's scope in place in **Settings → Authorization** (or with `PATCH /api/auth/tokens/:id`), although the change itself applies from the next request: after raising it, the tools it gained only show up once the client is restarted; after lowering it, a tool it lost answers "tool not found" in the same way — except `copy_note`, which a `notes:write` credential keeps, and which then refuses `group_id` with `insufficient_scope`. Tool descriptions stay as the client first fetched them, too: after you add `notes:move`, `copy_note`'s still says that copying into a group needs `notes:move` (#239).
- **`list_notes` pages through live data, not a snapshot.** The cursor is a position in "most recently updated first" order, and only two things move a note in that order: creating one, and renaming it — changing its title or its URL name. Both stamp the note with the current time, which puts it above the cursor you are holding, where no later page reaches it. **Editing a note's content does not move it** — a content write lands in the collaborative document and in the note's own last-edited fields. So the run that silently misses notes is not "list a page, edit those notes, ask for the next page"; it is a run during which somebody creates or renames notes — a person in the browser, or an assistant: `edit_note`'s `rename` moves the note it renames to the top, and a note `copy_note` creates appears at the top. A note that gets shared with you mid-run — directly, because you were added to its group, or because its owner moved it into one of your groups — can be missed the same way, since it joins the listing at its own unchanged position rather than at the top (moving a note into a group, or deleting a group and giving its notes to an admin, can give a note a new URL name, but does not move it in this order). A note restored from the trash mid-run — in the web app, or with `restore_note` — can be missed too: restoring doesn't change its place in this order, so it comes back at its old position rather than at the top. A copy made with **Copy to… → My notes** or **Make a copy**, or copied into a group, is a new note, so it appears at the top. To enumerate everything, page all the way through before you do anything else, and page through again afterwards if other people are working in the same notebook (#108).
- **`read_note_outline` pages through live positions, not a snapshot.** A section's offset is its position in the document, and any edit that adds or removes a section shifts everything after it — so paging an outline while editing the same note can repeat or skip sections. Same remedy: list every page first, then edit (#108).
- **`read_note_section` pages through live text, not a snapshot.** Each call re-reads the note, so a section rewritten between two pages hands back the second half of the *new* text after the first half of the old — the assistant has now read a mixture that never existed as such. The `fingerprint` that arrives with the final page is computed from the section **as the note holds it at that moment** — not from the spliced text the assistant assembled — so a following `edit_note` built on it usually **matches and succeeds**, silently writing that spliced text into the note. `fingerprint_mismatch` only follows if the section is changed *again* after that last page arrived — it catches the next edit, not the one that already happened mid-read (#108).
- **`list_trash` and `list_folders` page through live data, not a snapshot.** Each page is read when it is asked for. `list_trash` lists the newest first, so a note moved to the trash while an assistant pages lands above the cursor it holds, where no later page shows it. `list_folders` lists folders grouped by space and then by id, not by when they were made, so a folder created while an assistant pages may or may not show up on a later page. To be sure of having everything, page all the way through again.
- **`delete_note` and `restore_note` can use up their budgets without changing anything.** With a token, each call spends one token write before the note is even looked up — MCP write tools spend it first, right after checking the credential's scope, except `copy_note` given a `folder_id`, which checks that folder before that and spends nothing when it refuses it — and once the access check has passed (for `delete_note`, also once the site's trash setting has been read) it also spends one write from the 30-writes-per-minute budget. A call that then fails without moving or restoring the note — for example because the check made again inside the transaction no longer passes (`not_found` or `forbidden`), or because the transaction gave way to a concurrent one (`server_busy`) — has still used both. And a call whose note was moved or restored, but which can't read it back afterwards — for example because someone changed it again in the meantime — answers `not_found` although it did act (#181).
