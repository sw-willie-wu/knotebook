# Trash

Moving notes to the trash, restoring them and permanent deletion. Part of [Known limitations](../known-limitations.md).

- **A note move to the trash that fails partway still ejects everyone who had it open.** Deleting a note — which moves it to the trash — closes every live connection to it *before* the transaction that moves it runs, and each of those tabs converges on "this note was deleted" and returns to the note list. If the transaction then fails and rolls back, the note is still where it was, not in the trash — but nothing calls those people back, and they were told something untrue. Reopening the note works (the server releases its delete gate as soon as it sees the transaction failed), so the cost is the wrong message and the interruption, not lost work.
- **Moving a note to the trash from the sidebar while that same note is still opening doesn't always end the same way.** If you click a note and use its sidebar `⋮` to move it to the trash before the page has found the note, the page treats it like moving a different note and doesn't leave on its own. What follows depends on timing: if the page finds the note already in the trash, it shows "This note is in the trash" with **Restore** — or, when your role in the group can delete notes but not edit them, says "This link is invalid or the note doesn't exist." and takes you to the home page; if the page found the note just before the move, it says "This note has been deleted." and takes you to the home page. Either way the note is in the trash.
- **Notes in the trash are deleted for good after the retention period, usually within an hour of it.** Deleting a note (`DELETE /api/notes/:id`) moves it to the trash; it stays there for the site's retention period (7 days by default — see [Trash](../self-hosting.md#trash)), counted from the moment it was moved. The server clears out expired notes in a background pass once an hour (the first one 5 minutes after it starts), at most 2,000 notes per pass, oldest first. So a note usually outlasts its expiry time by up to an hour; when more than 2,000 are due at once — after the retention period is shortened, for example — the rest wait for later passes and it takes several hours to clear them all, and nothing is cleared while the server is down. Clearing out deletes the note with its shares, versions, history and attachments; files are removed from disk best-effort after the transaction commits, and one that can't be removed is orphaned — see "Uploaded file cleanup is not automatic" in [Uploads, images and storage](./uploads.md). With the retention period set to keep notes until someone deletes them, notes stay in the trash indefinitely, and their attachments keep counting toward storage.
- **A note in the trash still holds its URL and its custom public URL.** While it's in the trash, another note in the same space (yours, or the same group's) given the same title gets a numbered URL (such as `…-2`), setting another note's custom URL to it answers `409 slug_taken`, and its custom public URL name can't be given to another note (`409 public_slug_taken`) until the note is permanently deleted. Restoring it brings both back unchanged. This also means a group member who can't see the group's trash (their role can edit but not delete, for example) and changes a note's title or URL to one a note in the trash holds learns that a note they can't see has that URL — only that the URL is taken, never that note's title or content. This is accepted: freeing the URL instead would make restoring a note fail whenever its URL had been reused.
- **Deleting a group with Delete everything also permanently deletes the notes in its trash.** They don't go to anyone's trash first; nothing in the group can be restored afterwards.
- **Someone whose role can delete notes but not edit them can't get back a note they deleted.** A group's trash is visible only to members whose role can both edit and delete notes, so a note such a person deletes disappears for them; a member whose role has both, such as an Admin, can restore it. Right after the deletion, the web app's message says who can restore it instead of offering **Undo**. Over MCP it is the same: after such a person's `delete_note`, `list_trash` doesn't list the note and `restore_note` answers `not_found`.
- **An image copied into another note breaks while the note it was uploaded to is in the trash.** Access to an image is decided by the note it was uploaded to (see "An image block copied and pasted into another note…" in [Uploads, images and storage](./uploads.md)), so where it was copied into another note it fails to load (`403`) until that note is restored, and for good once that note is permanently deleted. Conversely, in the read-only preview of a trashed note (`/trash/:id`), only images uploaded to that same note load (through `GET /api/trash/:id/uploads/:uploadId`); images copied in from another note fail to load in the preview until the note is restored.
- **A direct write can land in a note that is being moved to the trash.** Moving a note to the trash waits up to 5 seconds for the server to close the note's live document. If that doesn't happen in time while a write that doesn't go through the editor is in progress — `POST /api/notes/:id/edits`, a revert, applying a version, or MCP `edit_note` — the note is moved anyway and that write can end up in the note in the trash. Nothing is lost: it shows once the note is restored.
- **The date a note in the trash is due to be deleted can change.** `purgeAt` — in `list_trash`, in the replies of `delete_note` and `delete_folder`, and in `GET /api/trash` — is worked out from the site's trash setting as it is when you ask, not fixed when the note was moved there; the clean-up uses the setting as it is when it runs. A site admin who shortens the retention period, or switches from not deleting automatically to a number of days, moves every note's date, and notes that are then past it start being deleted at the next clean-up pass. A `purgeAt` an assistant read earlier can therefore be later than the real one; `list_trash` shows the current date for the notes you can restore (#181).
