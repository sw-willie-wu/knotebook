# Sending notes back as files (MCP bulk transfer)

Downloading notes as files with `open_notes_as_files` and sending them back. Part of [Known limitations](../known-limitations.md).

- **Only a note with nothing in it at all counts as empty.** Sending a file back to a note with no blocks replaces its content with the file's. A note whose only block is an empty paragraph also downloads with a blank body, but sending text back to it puts the text in front of that paragraph, so the note ends with an empty paragraph.
- **A block the file didn't change can still be replaced when the file changes a large part of the note.** When a file changes so much that the server can't line up every line, it matches the unchanged parts by lines that appear only once. Blocks made only of lines that also appear elsewhere in the note, such as repeated `***` dividers or the same short paragraph, are still matched when unchanged text next to them is; they may fail to match only when everything around them changed too, and are then written back with the file's copy. The copy takes over the old block's id when it matches it by the rules in [Which blocks keep their ids](../ai-editing.md#which-blocks-keep-their-ids), as an unchanged divider does; otherwise it gets a new id.
- **When a note has the same paragraph twice and the file keeps only one, the copy kept isn't always the one you meant.** If the two are next to each other, or everything between them is removed too, the first one is kept. Otherwise the one kept is the one that fits where the file's other paragraphs put it.
- **Moving a long stretch of paragraphs in a file is written back as removing and re-adding the paragraphs on the shorter side of the move.** Those paragraphs get new ids, and so do two or more changed blocks next to each other (see [Which blocks keep their ids](../ai-editing.md#which-blocks-keep-their-ids)).
- **An assistant tricked by a prompt injection can send every note you can see off-site.** `open_notes_as_files` gives an assistant a token that downloads, with one command, every note you can see — your own, the ones shared with you and your groups' notes, up to 3 000 — as files on the machine it runs on, where its shell commands can send them anywhere. With `notes:write`, it can also change, one file per request, any of those notes your role lets you edit, and create notes. A token lasts at most 30 minutes, its range can be narrowed with `space`, `group_id` or `folder_id`, and it stays out of URLs; none of that prevents it.
- **Text someone is typing can be lost when a file replaces the block it is in.** The server refuses a file when the note has changed since the download, but it only sees what has reached it: what someone was typing into a block in a browser and that hadn't reached the server yet when the file was written can be lost if the file replaces or removes that block.
- **A download is not a snapshot.** Each note is read when its turn comes, so the notes in one download can be from different moments, and a note moved to the trash, out of the range or out of your sight while the download runs is left out and listed in the manifest's `skipped`.
- **A download that nobody reads holds up every other download on the site.** Only one download runs on the whole site at a time, and the server has no time limit on it: a client that starts a download and then neither reads it nor closes the connection keeps that one place, so everyone else's downloads answer `429` until that connection drops or the server restarts. Only someone with a valid bulk transfer token can do this. A later version will have downloads wait their turn on the server instead (#396).
- **Revoking a bulk transfer token, or the credential that asked for it, doesn't stop a download that is already running right away.** The server checks the token and your account only before each batch of 50 notes, so the batch being written when you revoke still arrives, and a download of 50 notes or fewer can arrive whole.
- **A downloaded copy can be sent back only while the server still keeps what it needs of it.** For each person and note, the server keeps the 10 most recently downloaded copies, and removes a copy that hasn't been used for 30 days when a note is next downloaded. Sending back a copy it no longer has answers `409 base_unavailable`; download the note again.
- **A downloaded copy carries its changes back only once.** After a file's content has been written, sending the same copy again with other changes to the text answers `409 base_unavailable`; download the note again and change the new copy.
- **A note that has changed since the download refuses every changed file.** Any change to the note's title or content after the download — even in another part of the note — makes a changed file answer `409 base_unavailable` with `reason: "note_changed"`, and nothing in the note changes; download the note again and redo the change. That includes changes that leave the text the same: formatting or a color, a block replaced by an identical one with a new id, or typing into an empty paragraph and deleting it again. A note that had nothing in it at all when it was downloaded and now has a single empty paragraph — what opening it in the browser leaves — counts as unchanged. In a note marked `mergeable: false`, which can only be renamed with a file, the note is compared as it downloads, so a renamed linked note, or a linked note that went out of your sight, counts as a change there too.
- **Two new notes made from the same file within 30 minutes are one note.** A file with no `id` creates a note, and sending exactly the same file again within 30 minutes returns that note instead of creating another, which is what makes resending safe. So two notes made from one template, without changing either copy, end up as one note.
- **Moving, renaming or deleting a downloaded file changes nothing on the server.** The note a file goes back to is decided only by the `id` in its front matter; to rename a note, change `title` there. A file left out deletes nothing.
- **Attachments aren't in the download.** Images and files stay links (`/api/uploads/<id>`) in the markdown; fetch an image with `create_transfer_token`.
- **A path in the download can be longer than Windows' default limit of 260 characters.** Each folder and file name is cut to 64 characters, but nothing limits a whole path.
- **Windows' own `tar.exe` skips notes whose file names it can't represent.** `C:\Windows\System32\tar.exe` leaves out files whose names have characters the system's code page can't represent — on a system using code page 950, for example emoji, simplified Chinese characters, Korean and Japanese kana — and exits with an error. Unpack with the `tar` in Git Bash or WSL, and compare with `.knotebook/manifest.json`. PowerShell's `Expand-Archive` only unpacks `.zip`, and the download is only offered as `.tar.gz`. How the download unpacks on a Mac hasn't been checked.
- **A file that changes many places can push older rows out of a note's AI edit history.** Each place a file changes is one row, and a note keeps its 100 most recent rows; a file that changes more than 100 places keeps only its own latest 100, and the reply's `editIds` lists only those.
- **Files sent back have a budget of their own, separate from the token write budget.** A credential's 60 writes per 10 minutes (the default) doesn't cap files sent back with its bulk transfer tokens; those count against 30 files per minute per person (the default), and a file the same as the copy it was downloaded as counts against the 300-reads-per-minute token budget (the default) instead, even when the 30 are used up. A file whose text differs counts against the 30 before the server parses it, so a file refused with a `400` for what it contains still counts; one that turns out to change nothing, such as a file that only adds blank lines, is given back — but once the 30 (or the lower number a site admin set) are used up, it too is answered `429` (unless an earlier check refuses it first, such as a note that has changed since the download), because the server can only tell that it changes nothing by parsing it.
- **A copy whose changes were reverted is no longer accepted at all, not even to rename the note.** Once any of the AI edit history rows a file wrote has been reverted, sending that copy again — unchanged, or with only a new `title` — answers `409 base_unavailable` with `reason: "reverted"` instead of `unchanged` or `renamed` (with other changes to the text it answers `already_sent`, as any copy already sent back does). To change the note, download it again.
- **A file near the size limit may not fit once it is a note.** A file sent back can be at most 262 144 bytes. The file the note downloads as afterwards can be a few bytes longer than the one sent, and then goes over the limit; the manifest marks such a note `tooLargeToSend: true`, and it can only be changed with `edit_note`.
- **A viewer's file is refused even when it is unchanged.** Sending back any file for a note your role can only view answers `403`, whether or not the file changes anything; a file that isn't UTF-8 or whose front matter is malformed answers `400 invalid_body` first.
- **Spaces at the start of a note's title stay in its file name.** A file is named after the note's title with spaces and dots at the end removed, but spaces at the start are kept.
- **Blocks nested under a list item come out of it when a file changes that item.** A list item with a paragraph nested under it is one item in the file; when the file changes it, the paragraph comes back as a block of its own, after the item.
- **A toggle becomes a bullet when a file changes it.** The file has a toggle as a bullet item, and that is what comes back. `edit_note` does the same with a toggle read with `read_note_section` and written back.
- **Some blocks come back different when a file changes the part of the note they are in.** Their markdown doesn't read back as the same block, for example: a relative link with non-ASCII characters and no scheme is lost, runs of spaces and spaces at the end of a line are collapsed, a code block with no language becomes `text`, an empty checklist item becomes a bullet, and a file block becomes a paragraph with a link. Blocks in parts the file didn't change aren't affected.
- **A list with colored items is one block in the file.** A run of list items that includes colored items is written as one block of HTML, so changing one item rewrites the whole run. The items that keep their text, and one edited item between them, keep their ids ([Which blocks keep their ids](../ai-editing.md#which-blocks-keep-their-ids)); the others get new ids.
- **A note with a great many knowledge headings can download as a file too large to send back.** Each knowledge comment adds lines to the file, so a note with thousands of knowledge headings can pass the 262 144-byte limit of a file sent back; the manifest then marks it `tooLargeToSend: true`, and it can only be changed with `edit_note`.
- **A few notes can't be written back as files.** When a note's blocks can't be lined up with its markdown at download time, the manifest marks it `mergeable: false`, and a file that changes its content answers `409 not_mergeable`; change it with `edit_note`. Sending it back unchanged, or with only a new `title`, still works.
- **An empty paragraph can't be added by adding a blank line, and removing blank lines removes empty paragraphs.** A file that only adds blank lines changes nothing; a file that removes the blank lines an empty paragraph stood for removes that paragraph.
- **If recording a file's changes fails after they were merged, the note is changed with no row in its AI edit history.** The reply is `500`. Sending the same file again answers `409 base_unavailable` with `reason: "note_changed"` — the note now has the file's changes — and doesn't apply them a second time; download the note again to check it.
- **HTML comments in a file, other than a knowledge comment, are dropped, and can turn the lines below them into plain text.** Text after a comment, on its line and on the lines right below it, becomes plain text that can run on into the text after a later comment; a blank line after each comment, with nothing after it on its line, keeps the lines below it as markdown. A file that changes a part into only comments removes it, and a comment added on a line of its own, with blank lines around it, changes nothing. A comment opened with `<!--` and not closed can hide the text after it; when that leaves a changed part with nothing in it, the whole file is refused with `400 empty_content`. `edit_note` parses markdown the same way. A [knowledge comment](../ai-editing.md#knowledge-info) is read, not dropped.
- **A code block a file opens and never closes gets the whole file refused.** When a line the file added or changed opens a code block (```` ``` ```` or `~~~`) that runs to the end of the file, the file is refused with `400 invalid_body` and nothing is written; close the block, or use inline code. A note that has a paragraph whose text is ```` ``` ```` can still be sent back, as long as that paragraph isn't changed.
- **The check for an unclosed code block has gaps.** It doesn't notice an unclosed `<pre>`; it can refuse a file that has a code block after a `<textarea>` or `<script>`; in a note with two paragraphs whose text is ```` ``` ````, it can let such a block through; and whenever the file adds or changes a line that looks like the start of a code block, the whole file is parsed for it, which can be slow for markdown that is slow to parse, such as long runs of `*a _b`.
- **An indented line after a blank line can read differently when a file changes the part it is in.** Under a list item, an indented line after a blank line belongs to the item when the whole file is read, but can come back as a block of its own when a file changes the part it is in.
- **After `APP_SECRET` changes, every downloaded copy answers `409 base_unavailable`.** Download the notes again. A new-note file sent again after the change creates another note.
- **Changing only the spaces at the end of a line doesn't write anything.** That includes no-break and ideographic spaces; inside a code block too.
- **Changing where a numbered list starts doesn't write anything.** A file that changes `5. a` to `1. a`, or the other way round, changes nothing; use `edit_note`.
- **A copy of a `mergeable: false` note downloaded before #386 or #379 was fixed can't send back a new title.** For such a note, the server checks that the note hasn't changed by writing it out the way a download does now and comparing that with the copy; a note with text that #386 or #379 changed how it is written (characters that are now escaped — since #379 also a `<` that could start an HTML tag or comment — or line breaks now written `<br>`) no longer matches, so sending back that copy with only a new `title` answers `409 base_unavailable` with `reason: "note_changed"`. Download the note again.
- **Reverting a removed part and an added part at the same place can put them back in a slightly different order.** When a file removes blocks and adds blocks right after the same unchanged block, reverting their rows puts the removed blocks back close to, but not always exactly at, where they were.
- **Don't revert the AI edit history rows of files sent back over MCP while v0.14 runs.** In v0.14, a `file_sync` row for a part a file rewrote or added can show a **Revert** button, and reverting it reports success but puts nothing back; the row is then marked as reverted, so it can't be reverted after upgrading again either. To undo such a write, upgrade again first, then revert it. A `file_sync` row for a part a file only removed shows as not revertable in v0.14. See [Upgrading and rolling back](../self-hosting.md#upgrading-and-rolling-back).
