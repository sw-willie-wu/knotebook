# Uploads, images and storage

File uploads, embedded media, attachments of copied notes, and storage quotas. Part of [Known limitations](../known-limitations.md).

- **A media URL that fails the safety check shows up as a broken image, with no explanation.** Image, video, audio and file blocks only render URLs that resolve to `http(s)` — anything else (a `javascript:` or `data:` URL written straight into the collaborative document, bypassing the embed field) is replaced with an inert placeholder at render time, so it looks exactly like a broken link. The check runs in each reader's browser: the offending string stays in the document and is still delivered to everyone, there is no UI that shows or clears it, and the only fix is to delete the block.
- **Pasting a right-click-copied image is blocked.** Copying an image from a web page or another app with your browser/OS's "Copy Image" and pasting it into the editor gets intercepted with a "please save the file first, then drag it in" toast, even though it looks like a plain image paste. The clipboard in that case carries an HTML representation alongside the image file, and the guard treats "file plus a usable text/HTML representation" as ambiguous and blocks it outright rather than guessing which one you meant. Work around it by saving the image to disk first and dragging the file in, or by using your OS's "Copy image as file" if it has one. Dragging an image straight off a web page (no save step) embeds it by its external URL instead of uploading it — see "External images embedded by URL" below. The same guard also blocks pasting a file copied from a file manager (e.g. Windows Explorer) whenever the clipboard additionally carries a plain-text filename representation, for the same first-match-wins reason.
- **Uploaded file cleanup is not automatic.** Orphaned blobs on disk (a DB row was never created, or was deleted, but the file wasn't removed) can accumulate from: an `INSERT` failing after the file was already written (best-effort unlink, which can itself fail); the best-effort post-commit unlink failing when a note is permanently deleted from the trash or cleared out after the retention period, and the same for deleting a group with **Delete everything**; a note copy that fails after it has already written some attachment files, when the best-effort unlink of those fails too (#175); and a known upstream BlockNote behavior where, during a multi-file drag-and-drop under live collaboration, a block can be removed (by undo, a manual delete, or a remote collaborator) while its upload is still in flight — the editor's own `updateBlock` then throws, aborting the rest of that batch and leaving any already-uploaded files in that batch orphaned. Profile pictures add five more ways to leave a file behind, with the same effect: the server stops after writing a picture's original file but before saving its row; removing the original file fails after a picture has been deleted (the request still succeeds); removing the replaced original file fails after a sign-in picture was replaced in place (by the background fetch after a sign-in, or by **Use my … picture** in Settings; the replacement itself succeeds); removing a just-downloaded sign-in picture fails after it turned out not to be needed; and an account removed by hand in the database takes its picture rows with it but not their files. Such a file has a random UUID for a name, with no extension (or `.tmp` if the server stopped while it was being written), in the same uploads directory; it is in neither `uploads` nor `user_avatars.original_file`. None of this corrupts data; it just wastes disk space. Automatic orphan cleanup is planned for a future release. Such files don't count toward storage quotas.
- **An image block copied and pasted into another note still points at the note it was originally uploaded to, not the note displaying it.** (Copying a whole note — **Copy to… → My notes**, or copying it into a group — is different: the copy gets its own copies of the note's own attachments.) BlockNote's image blocks store a plain `/api/uploads/:id` URL, and copying that block into a different note copies the URL, not the file. Two consequences: permanently deleting the *source* note deletes the blob too, permanently breaking the image everywhere else it's been copied, with no way to recover it (while the source note is only in the trash, the image is broken until it's restored); and a reader who can see the note the image is copied into, but not the note it was originally uploaded to, gets `403` trying to load it — access is checked against the upload's owning note, not wherever it's currently displayed.
- **Storage quotas count attachments and profile pictures only, per space.** Every personal space and group has a storage plan (with a limit, or none); a limit counts attachment bytes and, in a personal space, the bytes of its owner's profile pictures (the original file and display image of each, not only the one in use; a group has none), and nothing else (not note text or version history, whose size is only shown — see "The notes and history sizes are display only" — and not files left on disk without a database row — see "Uploaded file cleanup is not automatic"). Someone a personal note is shared with as an editor uploads into the owner's space: they can fill it, after which the owner can't add attachments either, until a site admin gives a larger plan or space is freed — by permanently deleting notes that have attachments (moving them to the trash doesn't free anything), moving them into a group, or deleting profile pictures. The per-user upload rate limit still applies on top — 120 files per 10 minutes, where a copy counts one per attachment of the note it copies (a note with more than 120 is capped at one window's worth; an attachment whose file is missing still counts) and a profile picture upload or re-crop counts one.
- **Removing an image from a note doesn't free its space.** Every file uploaded to a note (or copied into it with the note) stays recorded against that note, and keeps counting toward its space, until the note itself is permanently deleted (moving it to the trash doesn't free it) — whether or not the note's content still shows it. So a note whose images have all been removed still carries their size: moving it into a group adds that size to the group (and can be refused when the group is full), and only permanently deleting the note frees that size for good (moving a personal note into a group frees it from the personal space by handing it to the group).
- **Storage usage is the recorded size, not disk usage.** A space's usage adds up the sizes recorded for its attachments and, in a personal space, its owner's profile pictures; it doesn't look at the disk. The notes and history sizes are recorded sizes too.
- **The notes and history sizes are display only.** **Settings → Storage** and a group's **Storage** page show the recorded size of the space's note content as the **Notes** row in **By type**, and of its saved versions and automatic backups as **Current backups** in **Version history**. **Site admin → Users** and **Groups** show the two added together under the usage. These numbers aren't part of the usage, don't count toward the storage limit and never block anything. They include notes in the trash until they are permanently deleted, leave out the records AI edits keep, and are recorded sizes, not disk usage. The app doesn't show a size per note.
- **A group's By member can credit the wrong person for files from before v0.10.** It counts each file for whoever brought it into the group — uploaded it into one of the group's notes, or moved or copied its note in — but nothing recorded who moved a note before v0.10, so the files of notes moved into a group before the upgrade still count for the people who uploaded them. (Copies made before the upgrade aren't affected: a copy already recorded the person who copied it.) If the server was rolled back to v0.9 for a while, files uploaded or copied while v0.9 ran count under **Deleted user** after upgrading again (until their note is next moved into a group, which counts every file of the note for the person who moves it), and notes moved into a group while v0.9 ran keep counting for whoever they counted for before (usually the people who uploaded them).
- **An image block copied from another note into yours doesn't count against your space.** It still points at the other note's attachment, which stays in that note's space (see "An image block copied and pasted into another note…" above).
- **Adding attachments to the same space happens one at a time.** Uploads, copies, moves and transfers that add attachments to one space (and profile picture uploads and re-crops that make the picture larger) wait for each other; while a large group is being transferred to someone, their own uploads can wait, and after 5 seconds they are answered `409 server_busy` (retry).
- **A plan change can race an upload already in progress.** An upload that read the old limit a moment before an admin changed it is judged by the old limit.
- **Copying into a full space can be refused even when nothing would be copied.** Before copying anything, a copy that has attachments to copy (the note's own attachments that its content links to as `/api/uploads/<id>`) checks whether the place it goes into is already at or over its limit, and if so answers `409 storage_quota_exceeded`. That check counts the note's attachments as recorded in the database, so a note whose attachment files are all missing on the server — which the copy would skip — is still refused when the space is full.
- **Anyone who can read a note can re-store its attachments without having uploaded them.** Copying a note counts against the copier's upload limit, so copying attachments you uploaded yourself costs about what uploading them did. But anyone who can read a note — a viewer it's shared with, or a group member whose role can only read — can copy it, storing new copies of files other people uploaded. Per user that is capped at 120 copied files every 10 minutes, with one exception: a note with more than 120 attachments is copied whole, as long as none of the current 10-minute window's upload limit has been used, and the copy then uses up that window. Each copy also counts against the limit of 30 writes per minute. Repeatedly copying a note with many attachments can therefore use up storage faster than uploading could (#175). Copied attachments count against the copier's personal space (or the group copied into), so re-storing someone else's attachments uses up your own storage quota.
- **External images embedded by URL are hotlinked, not proxied.** BlockNote's image block also accepts a plain external URL (not just an uploaded file) — Knotebook renders that URL directly in the reader's browser rather than fetching and re-serving it, so the external host sees the reader's IP address on every view. It does not learn which note that is: pages are sent with `Referrer-Policy: no-referrer` (#101). Treat this the same as embedding any external image in any other tool.
- **Uploads have no CSRF check when the request carries no `Origin` header.** `POST /api/notes/:id/uploads` and the sign-in service icon upload (`PUT /api/admin/auth/providers/:id/icon`, which only admins get through to) reject a mismatched `Origin`, but a request with *no* `Origin` header at all is allowed through, matching how legitimate non-browser API clients behave. This is a deliberate trade-off documented for completeness, not an oversight.
- **Revoked upload access can still be served from a browser's cache.** `GET /api/uploads/:id` sets `Cache-Control: private, max-age=31536000, immutable` so a browser never re-checks it — appropriate for a URL that never changes content, but it also means a viewer whose share was just revoked can keep seeing an image they already loaded until that cache entry is evicted on its own, well past any revocation SLA the rest of the system aims for.
- **The editor's file panel still uploads only images; the other kinds go in through the API or MCP.** The server accepts audio, video, PDFs, Office and OpenDocument files and text files (`POST /api/notes/:id/uploads`, or `create_transfer_token` over MCP), but audio, video and file blocks in the editor only embed a URL.
- **Copying a note doesn't rewrite every link to its attachments.** A copy gets its own copy of an attachment only when the attachment belongs to the note being copied and a block's URL is exactly `/api/uploads/<id>`. In the copy, these still point at the original attachment, so access to them is still decided by the note that attachment belongs to (once that note is in the trash or permanently deleted the image breaks, and someone who can't read that note gets `403`): an image block pointing at **another** note's attachment (for example one copied and pasted from another note — see "An image block copied and pasted into another note…" above), an upload URL inside a text link, and an image whose URL is written out in full as `https://<host>/api/uploads/…`. An attachment whose file is already missing on the server is skipped, and the copy keeps its original URL (#175).
- **Copying a note with many attachments doubles their disk usage.** The copy duplicates the attachment files it copies (sharing the disk blocks where the filesystem can) before the database transaction that creates it, so the original is not held while files are copied, and a copy that the space already can't hold is usually refused before any file is copied. Apart from the upload limit (see "Anyone who can read a note can re-store its attachments…" above) and the storage quota of the place the copy goes into, nothing caps how many attachments one copy duplicates (#175).
- **Audio and video are stored as uploaded, and playback depends on the viewer's browser.** Nothing is transcoded. HEVC video — often a `.mov` from a phone, sometimes an `.mp4` — doesn't play in Chromium or Firefox on most systems: the player shows but can't play it, and the file still downloads. A video a browser can't play gets no fallback.
- **Text that isn't UTF-8 can only be downloaded.** A text file opens in the browser only when its whole content is valid UTF-8; a Latin-1 or other legacy encoding, and UTF-16, are sent as a download, since a browser would have to guess the encoding. A text file with a NUL byte is refused (UTF-16 text, which has them, is accepted when it starts with a byte-order mark). Text is never shown as HTML: a `.txt` that holds HTML or SVG markup is shown as plain text.
- **Some formats are refused.** Macro-enabled, template and slideshow OOXML files (`.docm`, `.xlsm`, `.pptm`, `.dotx`, `.ppsx` and the like) and OpenDocument templates, raw `.aac` (ADTS) audio and Matroska (`.mkv`) video are not accepted, and neither is any file whose content matches no accepted type. A file with a text extension that happens to start with the signature of a format that isn't accepted (for example text beginning with `MZ`) is kept as text, while a text file that starts like an accepted format (for example `%PDF`) is stored and named as that format. A legacy `.doc`, `.xls` or `.ppt` and OpenDocument files are accepted whether or not they contain macros; they are only ever sent as a download.
- **A refused upload may show as a network error.** When the server refuses a file before it has received all of it (too large, not an accepted type, no room in the space), it closes the connection instead of reading the rest. A browser that is still sending often reports that as a network error without the reason. A reverse proxy that buffers request bodies receives the whole file before the server can refuse it (see [Uploads](../self-hosting.md#uploads)).
- **A dropped upload starts again from the beginning.** A file is sent in one request: a lost connection, a closed tab or a proxy timeout stops it, and there is no resuming.
- **A restart in the middle of an upload leaves a temporary file until the next start.** A file being received is written as `<id>.tmp` and renamed when complete; the server deletes `.tmp` files older than one hour when it starts, so those from an interrupted upload stay until a start at least an hour later.
- **A crash in the middle of copying a note can leave a stray attachment file.** Copied files are renamed to their final names just before the transaction commits; a crash in that short window leaves files that no row refers to, the same as a crash during an ordinary upload's rename, and nothing removes them yet (#225).
- **An audio, video or file attachment inserted as a link isn't copied with the note and can't be opened from a public page.** Over MCP such a file goes into a note as a plain link to `/api/uploads/<id>`. Copying the note leaves that link pointing at the original attachment (see "Copying a note doesn't rewrite every link to its attachments"), and a public page doesn't rewrite it, so an anonymous reader is refused.
