# Collaboration and presence

Editing with others in real time, reconnecting, and the people and AI assistants shown in a note. Part of [Known limitations](../known-limitations.md).

- **A tab that cannot reach the collaboration server keeps retrying in the background; edits made while offline are still lost if you reload before it recovers.** When the collab token cannot be fetched — or when the server rejects the handshake for a reason that is not an access decision, such as a token that failed to verify or an unexpected server-side error — the tab restarts the whole handshake every 5, 15, then 60 seconds (jittered) for as long as it stays open, which recovers on its own once the underlying problem is fixed. The connection badge escalates to a warning after a few seconds ([issue #48](https://github.com/sw-willie-wu/knotebook/issues/48)): if the note had already synced once, it reads "Editing offline — changes not synced yet" and the editor stays writable, and those edits merge back **when the connection recovers**; if it never synced (the note failed to load at all), the editor is read-only and the badge reads "Not loaded — offline", so you cannot type into a blank document at all; a read-only viewer sees a plain "Offline" rather than an editing message. The remaining data-loss window is the first case: there is no `y-indexeddb`, so anything typed while "Editing offline" lives only in that browser tab and is lost if you reload or close it before the connection comes back. Those retries count against the per-user collab-token rate limit, which is shared across every open tab, so a user with many stuck tabs can exhaust their own quota. This is also what a server-side error during the handshake looks like from the browser, which is why it is logged on the server — see [Troubleshooting](../self-hosting.md#troubleshooting).
- **The notification bell updates live only with a single app instance.** The server keeps the open notification sockets in its own memory, so with more than one `app` process a notification made on one reaches only the tabs connected to that one; the others see it when the page is reloaded or the window regains focus. Running several instances isn't supported anyway (see [Single-instance warning](../self-hosting.md#single-instance-warning)) (#289).
- **A notification that arrives while the bell is opening can be marked seen without being shown.** Opening the bell loads the list and then marks everything up to that moment as seen; a notification made in the instant between the two is marked seen too, so it appears in the open list without **New** and, if the bell is closed first, never adds to the badge (#289).
- **Clearing notifications in the bell also clears them for your agents.** A notification addressed to one of your agents (a mention of `@you/claude`) is listed in your bell, and **Clear all** and ✕ delete it for the agent too, so `list_notifications` no longer returns it. The bell has no way to clear only your own (#289).
- **A note's title is not part of the real-time collaborative document.** The block editor content syncs live over Yjs/Hocuspocus, but the title is a separate field updated via `PATCH /api/notes/:id` with last-write-wins semantics — two people renaming a note at the same moment can silently overwrite one another, unlike the CRDT-merged body. A rename made over MCP is the exception on its own side: it carries the fingerprint of the title it replaces and is refused if the title is no longer the text it had when that fingerprint was taken — a title changed and then changed back to the same text counts as unchanged (#381) — but a rename in the web app still overwrites whatever title is there, including one an MCP client just set.
- **A collaboration client that sends ten messages the server doesn't recognize gets disconnected — including a hypothetical newer client version.** The server classifies incoming collaboration messages against the set its bundled library version actually handles and force-drops a connection after ten unrecognized ones (see [Troubleshooting](../self-hosting.md#troubleshooting)); this is the guard against a signed-in account flooding the log (#50). The ten-message grace absorbs incidental noise, but if a future client version ever introduces a *frequent* new message type, browsers running it against an older server would be disconnected and reconnect in a loop until the server is upgraded too. In practice the web client and server ship in one image, so the realistic skew — a stale browser tab across a deploy — runs an *older* client against a newer server and never sends unknown types.
- **An AI's presence is only visible to people who have the note open at that moment, and it fades after 2 minutes.** The cursor is attached to the live collaborative document, so a token reading or writing a note nobody is looking at creates nothing at all — and leaves nothing to look at afterwards; the lasting record is the note's edit history. Presence is refreshed by each token-authenticated content read or write and removed after 2 minutes without one. `GET /api/notes/:id/edits` deliberately does not refresh it, and a cookie-authenticated request never creates it (#106, #138).
- **The presence registry and its counters live in the server process, so a restart leaves an already-open browser unable to see the AI until the page is reloaded.** Each AI cursor carries a counter that only ever moves forward, and a browser silently discards any update whose counter is not higher than the last one it accepted. After a restart the server counts from the beginning again while the browser still remembers the higher number, so that AI simply never reappears in that tab. Reloading the note builds fresh state and fixes it. The same applies across two server instances, which is one more reason [only one is supported](../self-hosting.md#single-instance-warning) (#106, #138).
- **That counter map is never trimmed.** It keeps one small entry per distinct (note, credential) pair the process has ever seen, and nothing removes entries — not presence stopping, not the note unloading, not the registry evicting an old cursor to stay under its 500-cursor cap. Its size is bounded only by the life of the process. This is deliberate: keeping the counter is exactly what lets an AI reappear after an idle stop, and dropping it produces the failure described in the entry above (#106, #138).
- **The AI's name tag is only lit for about two seconds at a time.** The cursor itself stays put, but the name beside it appears for roughly two seconds after each thing the AI does (and after each 10-second keep-alive) and then collapses to a bare caret; hovering the cursor shows it again. This is the editor's behaviour for every collaborator, human or not — there is no special case for API writers, and the one editor option that would pin labels open is the same option that disables the mechanism lighting them up, so there is no setting that shows the name permanently (#106, #138).
- **A token reading a note whose first block has no text puts no AI cursor in the note.** The cursor has to point at text; when the first block is empty, or is an image or a divider, there is none to point at — no matter how much content follows it — so no cursor is sent, and with no cursor the editor draws nothing, not even the name. The most common shape of this is exactly "brand-new empty note, read it, then write it": the read puts no cursor in the note, and the AI's cursor only appears with the write. The AI still appears in the note header's row of people, but clicking it doesn't scroll anywhere while it has no cursor (#106, #138, #293).
- **Viewers have no cursor, so clicking a viewer in the header's row of people doesn't scroll.** Knotebook doesn't share where a viewer is in the note, even while they click into it or select text to copy. Viewers still appear in the row, with their role (#293).
- **Someone who changes their display name keeps showing the old one in the header's row of people until they reopen or reload the note, or until its connection drops and comes back.** The name travels with their collaboration connection, which is set up when the note opens; the same is true of the name on their cursor (#293, #312).
- **Someone whose tab loses its network stays in the header's row of people on other screens for up to about half a minute.** Closing the tab or a crash removes them at once, also after their connection had dropped and come back. Only a lost network isn't noticed right away: they leave the row when their presence goes stale — 30 seconds after the last update, checked every 3 seconds (#293, #312).
- **A tab that has to send the server more than the collaboration message limit (11 MiB by default) at once keeps reconnecting, and almost none of its later changes reach the server.** One message on the collaboration connection is limited to twice the largest note size the server can be set to, plus 1 MiB (see [Note size](../self-hosting.md#note-size)), and a larger one closes the connection. The editor keeps each addition within the note size limit, but undo and moving a block are not checked and send a message about as large as what they change. So the limit can be hit by a single change in a note that is already larger than the message limit — such notes exist from before the limit, after `NOTE_MAX_BYTES` was lowered, or from custom clients, and the server's startup log lists the ones over the note size limit — for example undoing the deletion of most of the note, or moving one very large block; it can also be hit by a great many edits made offline. What already reached the server before that (such as the deletion) stays. Reload the note. To bring back content that was lost, open an earlier version of the note in [version history](../versions.md) (if one was saved — automatic versions can be turned off), preview it and copy back what fits within the note size limit. Applying such a version is refused, because it would make the note larger than the note size limit; an administrator can instead set `NOTE_MAX_BYTES` temporarily to more than the version's size (it also raises the message limit; it takes effect after a restart), apply the version, then set it back (#312).
- **A collaborator who already knows an AI cursor's identifier can keep that AI out of view in tabs that are open at the time.** Once an AI has appeared in an open note, the server owns its cursor and refuses anyone else's update for it. Before that, a collaborator who learned the identifier earlier (it is visible to everyone who saw that AI in the note) can send an update for it with a very high counter. The server still shows the AI correctly, but tabs that received the earlier update discard the AI's updates until the AI's own counter passes that number, so those tabs don't show the AI until they reload the note. The effect is bounded: what those tabs show in the meantime carries the sender's own name and role, never the AI's, and the sender can't touch the AI's cursor after that (#312).
- **While someone's collaboration connection is gone, a collaborator's fresh connection that has no presence entry yet can take over that person's entry, and the person is then not shown to others after they come back.** Their presence is refused until that other connection closes or they reload the note; the effect is bounded, since the collaborator's entry still shows the collaborator's own name and role, and it takes a deliberately written client (#312).
- **Tabs that were open before the upgrade to 0.11 don't show the reload notice — they keep trying to connect.** From 0.11 on, when an upgrade changes how the editor stores notes, a tab opened before it is refused and shows a notice asking you to reload. Tabs opened before the upgrade to 0.11 don't have that notice yet: they keep retrying in the background, showing "Connecting…" and then an offline warning, and edits made in them that hadn't synced are lost when you reload. Reload every open tab after upgrading (#269).
