# Search

Body-text search in the sidebar, the API and MCP. Part of [Known limitations](../known-limitations.md).

- **The result count may not be announced by a screen reader when you type the first character of a search.** The sidebar's search results and their count appear together, and some screen readers skip a live region that is inserted with its text already in place; the count is announced when it changes on later keystrokes. The count now covers title and body-text matches together and changes once the body-text search has finished (while a newer search is still running it shows only the title matches); it is the one live count line. The line saying the body-text search is running or has failed is also a live region, with the same gap when it appears with its text already in place. The "load more" error line and the "no notes match" line are not live regions, and neither is the "Searching note text…" line shown while the search code is still downloading.
- **Body-text search can lag the editors by a few seconds.** The sidebar's search, `GET /api/search` and `search_notes` find a note's body text as the collaboration server last saved it — during active editing that's roughly the 2-second save debounce, up to about 10 seconds under continuous typing, and at once when the last person with the note open disconnects. A write made through the REST API or an MCP tool, including a file sent back with `write.curl`, is indexed before its reply comes back. If indexing a save fails (the `app` log shows a warning starting `全文索引更新失敗`), that note's body text stays as it was last indexed until the note is saved again after another edit, or until the server next starts (#93).
- **Attachments, text in images, media captions and file names, and link addresses aren't searched.** Body-text search covers the text of a note's blocks — code blocks, the source of mermaid diagrams and links to notes (by their own text, or the text they were made with — see below) included. It doesn't look inside uploaded files or images, and it skips what a block keeps as a setting rather than as text: an image, video, audio or file block's caption, file name and URL, and the address a link points to (the link's own text is searched) (#93).
- **Only about the first million characters and the first 2000 sections of a note are searchable.** Body-text search indexes at most 1,048,576 UTF-16 code units of a note's text — most emoji count as two, and the line break between two blocks of the same section counts as one — and at most 2000 sections that have text. What gets left out is the **end** of the note: everything after the point where either limit is reached. A log-style note that keeps growing through `append` therefore loses its **newest** text from search first. A note that was cut has `capped = true` in its `note_search_state` row (so does a note from the block-id entry below) (#93).
- **The sidebar searches body text only from the second character, 20 notes at a time.** With one character typed (after trimming spaces), the sidebar matches titles only and says so; with more than 200 (counted in UTF-16 code units, as `GET /api/search` counts them, so most emoji count as two) it also matches titles only. It shows title matches and body-text matches together in one list with one entry per section that contains the text: each entry has three lines (the note's title, its location, and the excerpt around the match), where the location is the same label the rest of the sidebar uses, such as My notes, a group's name or Shared with me, followed by the folders. The server reports only the first match in each section, so several hits inside one section are one entry, which jumps to the first of them, and a note shows at most three sections: a note whose text appears in more sections shows only the first three, one after another in the order the server sent them, each repeating the title and location. A note that matches only by title is one entry of two lines (title and location) and opens the note without jumping anywhere; a note that matches both ways is listed only by its body-text entries. Notes whose title matches come first (in the sidebar's order), then the rest in the server's order. Once the body-text results have arrived (and aren't out of date because you kept typing), the count above the list is the number of entries, not of notes (“N results”); until then it is the number of notes whose title matches (“N title matches”). Body-text matches come 20 notes at a time — **Load more** gets the next 20, and a note whose title matches gets its excerpts only once the page that holds its body-text match has loaded — and only notes that are also in the sidebar's own note list, so until that list refreshes, a note created elsewhere a moment ago may be missing, and one renamed or moved elsewhere is shown as it was. Every body search, including **Load more**, counts against the same 60-searches-per-minute budget as `search_notes`; when it runs out, the sidebar says so and title matching goes on working (#93).
- **Clicking a body-text match jumps to the first block in its section that contains the search text; if none is found it stops at the section heading, also scrolled to the middle (or, for a match before the first heading, at the top of the note), and a reload jumps there again.** A section runs from one heading to the next heading of the same or a higher level; deeper headings don't start a section of their own, and a heading inside a side-by-side column doesn't either. The note opens and goes straight to the first block of that section (nested list items and column contents included — the innermost block that actually holds the text; a table cell, code, or diagram source counts as its block's text) whose own text contains the search text, scrolling it to the middle of the note's scrolling area and marking it (it flashes twice (clearly, under 2 seconds in total, once the scrolling has settled — also when your system asks for reduced motion, since it is a locating cue that flashes only twice) and then stays highlighted, in the same colour and strength, until you press Esc, close the search by clearing the box (or, when the box is already empty, switching sidebar tab), click another search result, or leave the note; closing the navigation drawer on a narrow screen doesn't count as closing the search, and an Esc that a dialog, menu or selection mode already used doesn't clear it; the mark follows the block when the note is edited or someone else changes it, and goes away if the block is deleted; links to a section or between notes still just flash for two seconds) (a block near the start or the end of the note, without enough content above or below it, can't be brought to the middle and stays where the note stops scrolling; for a block taller than the scrolling area, such as a list item with many sub-items or a long code block, the scroll centres that block's own first line, and when that line itself is taller than the area it goes to the top; ordinary `#` section links, links between notes, and copied links still put their target at the top); the matching words themselves aren't highlighted in the note. If that block sits inside a collapsed toggle, the flash is on the outermost collapsed toggle, since its contents are hidden. The comparison is the one used to mark words in the excerpt: letters are compared lower-cased only (no full-width/half-width folding, so `ａ` and `a` are different, as they are for the search itself). When nothing in the section matches that way, the page stops at the section heading instead. That can happen when a link to a note whose target was renamed and has no label shows the new title where the index has the old one, for a text such as `İ` whose lower-casing changes its length, or when the search index is behind the note's current text. The search text travels in the browser's navigation state, not in the address, so a copied link only scrolls to the section; the browser keeps that state in the history entry across a reload, so reloading the page jumps to the block again (the search box is empty after a reload, so clear that mark with Esc), the same way it scrolls again to a `#` section link (#93, #367).
- **Right after an upgrade, older notes can be found by title only until the server has indexed them.** The first start of a version with body-text search indexes the existing notes in the background, after the server is already answering requests; the `app` log shows `全文索引回填開始` when that starts and `全文索引回填完成` when it is done. Until it gets to a note, the sidebar's search, `GET /api/search` and `search_notes` find that note by its title only. Stopping the server partway through is safe: the next start carries on with the notes not yet done (#93).
- **How far search ignores case depends on the database's locale.** Matching lower-cases both your text and the note's using the database's own rules. The database image in Knotebook's compose file is initialized with the `en_US.utf8` locale, under which letters outside ASCII match regardless of case too (`Ä` finds `ä`, `Σ` finds `σ`); in a database created with the `C` locale, only ASCII letters do. Title search works the same way (#93).
- **Searches without three letters or digits in a row read through all the body text the searcher can see.** A query with three letters or digits in a row is looked up in a trigram index first (on a database whose LC_CTYPE is C, only ASCII letters and digits count). Shorter queries, and on such a database queries without three ASCII letters or digits in a row, still look through every section of every note the caller can see, so their cost grows with the amount of text visible to that account. When searches get slow — a 95th percentile above 500 ms — or the body text visible to one account grows past about 200 MB, it is time for a different approach (#93).
- **A link to a note with no text of its own is searchable under the text it was made with, not under the note's current title.** The index stores a link to a note as its own text when it has some, and otherwise as the text the link was made with — the title its target had then, for a link made with `[[` or one whose text was that title — so after the target note is renamed, searching for the new name doesn't find such a link, and searching for the old name still does. The first start of 0.11 indexes every note again in the background (the `app` log lines are the ones described above); until it gets to a note, a note that hasn't changed since the upgrade is searched as the previous version indexed it (#93, #269).
- **Sections with a duplicated or malformed block id aren't searchable, and neither is any body text of a note with a top-level block whose id isn't a non-empty string.** A section's text is indexed only when the id of the block that starts it is a valid section id (1–64 letters, digits, `_` or `-`) that no earlier section of the note uses; a section that fails either test can't be found by its body text. If any top-level block's id is not a string, or is empty, none of the note's body text is indexed — its title still is. `read_note_outline` and `read_note_section` can't read such a note either (#93).
