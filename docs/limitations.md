# Limitations worth knowing

These are the limitations to know before you deploy Knotebook or trust it with your notes: where data can be lost, what cannot be undone, which security trade-offs are deliberate, and which common features are missing. Each item links to the page of [Known limitations](./known-limitations.md) that holds its entry; Known limitations is the complete reference of every known rough edge and deliberate trade-off. Entries there have no anchor of their own, so each link below is labelled with the entry's bold heading; search that page for it.

## Deployment and scaling

- **Run exactly one `app` container.** Live collaboration state is held in the server's memory with no sync between processes, so with two or more instances, edits to the same note silently diverge. Rate limits and login lockouts are per-process too, and restarting the container clears them. See the [single-instance warning](./self-hosting.md#single-instance-warning) and [In-memory rate limiting and login lockout reset on restart](./known-limitations/limits.md).

- **Some settings in `.env` only apply the first time.** `POSTGRES_PASSWORD`, `ADMIN_EMAIL` and `ADMIN_PASSWORD` take effect only while the database is empty, and changing them later does nothing; for `ADMIN_EMAIL` and `ADMIN_PASSWORD` there is not even an error or warning. To change the database password afterwards, change it in Postgres and update `DATABASE_URL`. `docker compose down -v` discards every named volume, the uploads included: every uploaded image is gone and, with the bundled database, every note as well. See [Compose services and volumes](./self-hosting.md#compose-services-and-volumes), [Setting `POSTGRES_PASSWORD` after the first `docker compose up` has no effect](./known-limitations/operations.md) and [`ADMIN_EMAIL`/`ADMIN_PASSWORD` only take effect on first initialization](./known-limitations/operations.md).

- **Uploaded images live in a Docker named volume.** The default `docker-compose.yml` mounts it; if you customize the compose file and drop the `uploads` mount, uploaded images vanish the next time the `app` container is rebuilt. See [The uploads directory is a Docker named volume](./known-limitations/operations.md).

- **Behind a reverse proxy, set `TRUST_PROXY`.** Without it every visitor shares the proxy's address, so one client can lock out logins or rate-limit the public share pages for everyone behind that proxy. See [Deployment prerequisites](./self-hosting.md#deployment-prerequisites) and [Behind a reverse proxy with `TRUST_PROXY` unset, one client can rate-limit the public share pages for everyone](./known-limitations/operations.md).

- **A plain-http deployment gives up more than encryption.** Passwords, session cookies, API tokens and transfer tokens cross the network unencrypted, so anyone on the same network segment can read or tamper with the traffic. MCP clients cannot sign in over OAuth (use a personal API token instead), and Chrome and Edge do not offer to install Knotebook as an app. See topology (a) in [Deployment prerequisites](./self-hosting.md#deployment-prerequisites), [On a plain-http `PUBLIC_URL` (for example a LAN deployment), transfer tokens cross the network unencrypted](./known-limitations/mcp.md), [OAuth for MCP clients only works for clients that run on your own machine](./known-limitations/api-tokens-and-oauth.md) and [In Chromium-based browsers, Knotebook can only be installed as an app when it is served over HTTPS](./known-limitations/web-app.md).

- **Rolling back to an older Knotebook version can remove content.** An earlier version that doesn't know about side-by-side columns deletes every row of columns, with what is in it, the first time a note that has them is opened, and saves the note that way. Back up before rolling back. A heading with knowledge info that you change on an older version loses that info. See [Rolling back to an earlier version deletes side-by-side columns](./known-limitations/side-by-side-columns.md) and [Upgrading and rolling back](./self-hosting.md#upgrading-and-rolling-back).

- **The note list is not paginated.** Wikilink suggestions, the live titles of links to notes and the instant conversion of a pasted link to a note all work from that one list, so with a very large number of notes they only know about what the list returns. See [The note list has no pagination](./known-limitations/links.md).

## Editing and collaboration

- **There is no offline mode.** Edits made while a tab has lost its connection are kept only in that tab and merge back when the connection returns; reloading or closing the tab first loses them. The installed app needs the server too. See [A tab that cannot reach the collaboration server keeps retrying in the background](./known-limitations/collaboration.md) and [The installed app doesn't work offline](./known-limitations/web-app.md).

- **A note's title is last-write-wins.** The body merges everyone's edits in real time, but the title is a separate field, so two people renaming a note at the same moment can silently overwrite each other. See [A note's title is not part of the real-time collaborative document](./known-limitations/collaboration.md).

- **Some edits made at the same moment as someone else's can lose their typing.** Dragging blocks; removing or flattening columns with the keyboard, **Ungroup columns**, or moving blocks with Ctrl+Shift+↑ or ↓; and a file sent back over MCP that replaces a block can each drop what another person is typing in those places at that moment. Version history may hold an earlier copy of the note. See [A collaborator's edits to the blocks you are dragging can be lost](./known-limitations/editor.md), [Editing a row while someone else edits the same row can lose their typing](./known-limitations/side-by-side-columns.md) and [Text someone is typing can be lost when a file replaces the block it is in](./known-limitations/bulk-transfer.md).

- **Applying a version replaces the whole note.** It overwrites changes nobody saved as a version, other people's included, and Ctrl+Z can't undo it; to go back, apply another version. It usually also makes earlier AI edits impossible to revert. See [Version history](./known-limitations/version-history.md).

- **Shared note addresses can break, or start pointing at another note.** Unless you set a custom URL, a note's address follows its title and changes, with no redirect, whenever anyone with edit access renames it. A freed address can later be taken by another of the owner's notes, and a username you rename away from can be taken by someone else, so old links can open a different note. Links to notes inside Knotebook are not affected. See [A note's automatic URL changes the moment its title does](./known-limitations/note-urls.md), [A released slug can be re-used by the same owner's other notes](./known-limitations/note-urls.md) and [A username you rename away from is free for anyone to take](./known-limitations/note-urls.md).

- **The editor's file panel still uploads only images.** Audio, video and file blocks only embed a URL; the other kinds go in through the API or MCP. See [The editor's file panel still uploads only images](./known-limitations/uploads.md).

## Data and retention

- **The trash empties itself.** A note in the trash is deleted for good, with its versions, history and attachments, once the site's retention period is up (7 days by default), unless the site is set to keep notes until someone deletes them. Deleting a group with **Delete everything** also permanently deletes the notes in its trash. See [Trash](./self-hosting.md#trash), [Notes in the trash are deleted for good after the retention period](./known-limitations/trash.md) and [Deleting a group with Delete everything also permanently deletes the notes in its trash](./known-limitations/trash.md).

- **Moving a note into a group can't be undone.** The group takes ownership: you stop owning the note, and what you can do with it depends on your role in the group. Its address changes, and its per-person shares and public link are removed and don't come back. Its version history is cleared too, unless you check **Bring its version history along** in the move dialog (it starts unchecked). A single note can't be moved back out. Copying a note doesn't bring its versions along, and deleting a group and transferring its notes to an admin deletes their versions too. See [Moving or copying a note into a group](./sharing.md#moving-or-copying-a-note-into-a-group) and [Copying a note doesn't bring its versions along](./known-limitations/version-history.md).

- **Removed images keep using space until the note is permanently deleted, and disk isn't tidied automatically.** Every file uploaded to a note counts toward its space whether or not the note still shows it. Files left on disk without a database row, for example when removing a file fails after a note is permanently deleted, are not cleaned up yet. Versions don't count toward storage limits: the retention settings thin out automatic versions only, and manual versions stay until someone deletes them. Their size is shown, together with note content, under **Notes and history** in the storage settings; it isn't counted. Each note's edit history can hold up to 100 full copies of what its edits overwrote. See [Removing an image from a note doesn't free its space](./known-limitations/uploads.md), [Uploaded file cleanup is not automatic](./known-limitations/uploads.md), [Versions don't count toward storage limits](./known-limitations/version-history.md) and [A note's edit history stores a full copy of what each edit replaced](./known-limitations/api-writes.md).

- **Backups and export are mostly by hand.** Back up with `pg_dump` and a copy of the `uploads` volume. There is no restore tool: putting a single note's content back from a snapshot or a `pg_dump` means writing it into the database yourself, following a procedure that can't be run while anyone has the note open. Bulk downloads over MCP leave attachments out (images stay links), and a note too large to turn into Markdown within the parse limits (three times `PARSE_TIMEOUT_MS`, 30 seconds in all by default, and 1024 MiB of memory per parse worker by default) can't be read over MCP or the API or downloaded, though it still opens in the web app; raising `PARSE_TIMEOUT_MS` or the memory per parse worker lets such notes be read. See [Restoring note content from a backup](./backup-restore.md), [Attachments aren't in the download](./known-limitations/bulk-transfer.md) and [A very large note can't be read over MCP or the API, or downloaded](./known-limitations/limits.md).

## Accounts and sign-in

- **Accounts can't be deleted, only disabled.** Deleting an account, including handing over its notes, is not implemented yet ([issue #73](https://github.com/sw-willie-wu/knotebook/issues/73)). See [Admins cannot delete user accounts, only disable them](./known-limitations/accounts-and-sign-in.md).

- **There is no email and no self-service "forgot password".** An admin creates a one-time reset link in **Site admin → Users** and passes it on. A reset signs out the person's other browsers but not their API tokens or connected apps. See [Resetting a password](./self-hosting.md#resetting-a-password) and [Resetting someone else's password takes an admin and a link they send themselves](./known-limitations/accounts-and-sign-in.md).

- **Email addresses are never verified.** Whoever registers an email that has no account yet holds the account for it, and receives what is shared with that email. Registering with a password is on by default, and a sign-in service with **Creates accounts** on lets in anyone its identity provider lets in. On a site that shouldn't be open to everyone, turn self-registration off in **Site admin → Sign-in**, keep **Creates accounts** off for any identity provider that outsiders can sign in to (Google, gitlab.com), and invite people from **Site admin → Users** instead (this needs password sign-in on). See [Someone can take a colleague's email and receive what is shared with it](./known-limitations/accounts-and-sign-in.md), [Registering with a password is on by default, upgraded sites included](./known-limitations/accounts-and-sign-in.md) and [A sign-in service that creates accounts lets in anyone its identity provider lets in](./known-limitations/accounts-and-sign-in.md).

- **Turning sign-in off, or suspending someone at the identity provider, doesn't cut them off.** Turning a sign-in service or password sign-in off leaves existing sessions, API tokens and connected apps working, and a password change doesn't revoke API tokens. Suspending someone only at the identity provider leaves a password they added (usable whenever password sign-in is on) and their API tokens working. When someone leaves, or to stop someone right away, disable their account in **Site admin → Users**. See [Turning a sign-in service off doesn't sign anyone out](./known-limitations/accounts-and-sign-in.md), [Turning password sign-in off doesn't sign anyone out](./known-limitations/accounts-and-sign-in.md), [Adding a password doesn't ask you to sign in again, and suspending someone at the identity provider doesn't revoke their password or API tokens](./known-limitations/accounts-and-sign-in.md) and [API tokens survive a password change](./known-limitations/api-tokens-and-oauth.md).

- **A signed-in browser is enough to hand out full access.** The consent screen, creating a personal API token and raising a token's or app's scope never ask for your password again, so anyone at a browser you left signed in (a shared computer, an unattended browser) can mint a token that acts as you across every note its scope reaches. See [Neither the consent screen, nor creating a personal API token, nor changing a credential's scope asks for your password again](./known-limitations/api-tokens-and-oauth.md).

## AI and agents

- **An administrator can obtain the AI provider keys, and sign-in services' client secrets.** Changing a provider's Base URL clears its key, but an admin can point a provider at a host they control and wait for someone to enter the key again. The server logs every such edit, and nothing prevents it. A sign-in service's client secret can be obtained the same way, by pointing the service at an issuer the admin controls. Treat an administrator as holding every configured provider key and sign-in service client secret. See [An administrator can still obtain AI provider API keys, just not silently](./known-limitations/ai.md) and [An administrator can still obtain a sign-in service's client secret, just not silently](./known-limitations/accounts-and-sign-in.md).

- **Provider error responses go into the server log.** Up to the first 2,048 characters of an error body are logged, and a few gateways and proxies repeat the key in it. Treat the logs as sensitive if you ship them elsewhere. See [An error response from the AI provider is written to the server log](./known-limitations/ai.md).

- **An assistant's access is your whole account's access.** Scopes are not per note or per group, so an MCP client can read every note you can read, including notes shared with you and your groups' notes, and they end up in the assistant's context. See [Scopes cover your whole account](./known-limitations/api-tokens-and-oauth.md) and [Notes other people shared with you, and your groups' notes, end up in your assistant's context](./known-limitations/mcp.md).

- **An assistant tricked by a prompt injection can act with that access.** Instructions hidden in a note it reads can make it send every note you can see, and their images, off-site. With **Create and edit notes** it can also change any note your role lets you edit and create notes; with **Move to groups** or **Move to trash**, it can also move notes into a group, move notes to the trash or delete folders. Leave each of these off unless a program really needs it; the first time you authorize an app over OAuth, the consent page leaves these unticked, so pressing **Allow** straight away gives it read-only access. See [An assistant tricked by a prompt injection can send every note you can see off-site](./known-limitations/bulk-transfer.md) and the other entries starting "An assistant tricked by a prompt injection" in [AI assistants over MCP](./known-limitations/mcp.md).

- **OAuth credentials are long-lived.** Access tokens last 24 hours and refresh tokens never expire; revoking happens in **Settings → Authorization**, by an admin disabling the account, or automatically for apps unused for 30 days. OAuth also accepts only clients that run on your own machine; the claude.ai web and Desktop custom connectors, which connect from Anthropic's cloud, cannot be used. See [OAuth credentials are not short-lived, and there is no revocation endpoint](./known-limitations/api-tokens-and-oauth.md) and [OAuth for MCP clients only works for clients that run on your own machine](./known-limitations/api-tokens-and-oauth.md).

- **There is no overview of what an assistant changed across notes.** The AI edit history is per note, so reviewing a run of edits means opening each note. See [There is no cross-note view of what an assistant changed](./known-limitations/mcp.md).

- **AI quick actions can change formatting, and long Anthropic answers can be cut off.** The selection travels to the provider as Markdown and back, so formatting that doesn't survive that can be altered. Anthropic responses stop at 4096 output tokens with no error. See [AI quick actions round-trip your note content through Markdown](./known-limitations/ai.md) and [Anthropic responses are capped at 4096 output tokens](./known-limitations/ai.md).

## Sharing and groups

- **A public link publishes the note's whole collaborative document.** The public page's data is the note's full editing state, which includes collaboration internals and can include traces of edit history, not only the text shown. See [A public share exposes the note's full CRDT state, not just its rendered text](./known-limitations/public-pages.md).

- **Revoking access doesn't remove images a browser already has.** Images are cached by the browser for a long time, so someone whose share was revoked, or who read a public link before it was revoked, can keep seeing images they already loaded. The note content itself stops at once. See [Revoked upload access can still be served from a browser's cache](./known-limitations/uploads.md) and [Images an anonymous reader already loaded survive revoking the public link](./known-limitations/public-pages.md).

- **A custom public URL shows your username and can be guessed.** Under corporate SSO a username is often the internal account name. Share the token link instead when that matters. See [A custom public URL reveals your username, and is meant to be guessable](./known-limitations/public-pages.md).

- **External images are loaded straight from their host.** An image embedded by URL is fetched by each reader's browser, so that host sees the reader's IP address (but not which note). See [External images embedded by URL are hotlinked, not proxied](./known-limitations/uploads.md).

- **Group notes can't be shared with individual people.** Access comes only through the group, so letting someone in gives them every other note in it too. See [Group notes can't be shared with individual people](./known-limitations/sharing-and-groups.md).

- **Group roles are a convenience, not a security boundary.** Someone whose role can manage members can make anyone, themselves included, an Admin, and someone whose role can manage roles and the group can give their own role Manage members. Give either permission only to people you would trust as an Admin. See [The permissions that manage a group are a convenience, not a security boundary](./known-limitations/sharing-and-groups.md).
